# Sync protocol

How clients and Durable Objects keep shifts, groups and chat in sync. `apps/server` implements signing in, groups, the sockets' handshake and keepalive, a user's own days and patterns between their devices, and their projection into groups (Shifts); the rest is the agreed design and will move into `proto/pochical/v1/sync.proto` as it is built.

## Ownership

| Data | Source of truth | Client storage |
| --- | --- | --- |
| A user's own shifts, patterns, repeating orders and coworkers | That user's User DO | `my_shifts`: writable, changes go through the outbox |
| Members' shifts shown in a group | Projection held by the Group DO, fed by each member's User DO | `member_shifts`: read-only cache |
| Groups, members, chat, read states | Group DO | Read-only cache |
| A user's chat with Pochical's people | Its own Group DO, `support:{userId}` (Chat) | Read-only cache, as a group's chat |

Clients never write to another user's data. A Group DO never edits shifts; it only stores what User DOs push to it.

## Signing in

Every user is signed in, from the first launch: anonymously at first, so nobody has to make an account to use groups, and later linked to Apple or Google to keep the same user on a new phone. better-auth (`apps/server/src/auth.ts`) serves this at `/api/auth/*` in its own JSON shapes, the one part of the server not defined in `proto/`.

- A client signs in with `POST /api/auth/sign-in/anonymous`, sending `Content-Type: application/json` and the body `{}` (better-auth answers 415 without them), and keeps the session token from the response's `set-auth-token` header, with the user's id from its body (`user.id`), as one: iOS in the Keychain and Android in Google Play services' Block Store, so a reinstall comes back as the same user, and so does a new phone the old one is moved to (an encrypted backup or Quick Start on iOS, Block Store's restore on Android). Android's goes to Google's cloud backup only while Block Store can encrypt it end to end (a screen lock set), as only an encrypted backup carries the Keychain's, kept again at each launch so a screen lock set later sends it; a phone moved device to device takes it either way. The Android app is for phones with Google Play services, from which it is installed; without them it cannot keep a session and does not sign in. It is not synced to the person's other devices (iCloud Keychain on iOS): those come in by linking Apple or Google, as one person's Apple ID may be shared by a family.
- Until release, what is kept changes shape without a migration, as the device's database does (AGENTS.md): a kept session the app cannot read is no session, and the app signs in anew, keeping the new session in its place. A store it cannot reach yet (the Keychain before the phone's first unlock, Block Store while Google Play services cannot be reached) is not unreadable: the app forgets nothing and signs in as it the next time it comes to the front. A device makes one anonymous user: a new session it could not keep yet it holds and keeps at the next try rather than signing in again, and one the server made as the app went to the background it keeps before it stops. A user linked to Apple or Google comes back by signing in with it again; an anonymous one is lost, as with a lost token (below).
- It sends the token as `Authorization: Bearer <token>` on every Connect call and socket, and on its own calls to `/api/auth/*`, which send no cookie: better-auth sets its session as a cookie too, and a call carrying one without an `Origin` it refuses as a browser's from another site (403), so the apps neither keep nor send it. Calls without a valid one fail with `UNAUTHENTICATED`; sockets get 401. `UserService.GetMe` says whose token it is.
- A session lasts for good, until the user signs out or deletes their account. An anonymous user's token is their only key, so an expiry would only lock out someone who did not open the app for a while (a widget is enough to keep using it). better-auth puts a session's lifetime on its cookie too, which may last at most 400 days, so the server stores each session to expire a century on and never refreshes it (`apps/server/src/auth.ts`); the apps use the token, not the cookie.
- Each user has a User DO named by their user id. It records the groups they are in.
- A session keeps its token and its user only: better-auth's IP address and user agent are left empty, so the server holds no one's address or device.
- Linking Apple or Google keeps the user: the app gets the provider's ID token (Sign in with Apple; Google through Credential Manager or Google Sign-In) and sends it on the signed-in session to `POST /api/auth/link-social` (`{ provider, idToken: { token, nonce } }`). An anonymous user's email is a placeholder, never the provider's, so the server allows linking a different email (`account.accountLinking.allowDifferentEmails`); the provider must still give an email, or `/link-social` answers `USER_EMAIL_NOT_FOUND`: an ID token carries one only when the app asks for the email scope, which Sign in with Google through Credential Manager does by default and Sign in with Apple does not, so both apps ask for it. The server reads the email to link and keeps none of it (below). The user id stays, and with it their User DO, groups and messages; the user is no longer anonymous once linked. better-auth leaves `isAnonymous` set, so the server clears it as the provider's account is linked, in the same change that builds linking: a linked user still marked anonymous could be deleted through the anonymous plugin's `/delete-anonymous-user` without signing in again, and the switch below would keep the device's anonymous user, as the plugin deletes it only when the account switched to is not anonymous. better-auth's way for an anonymous user to sign in with a provider (`/sign-in/social`), which makes a new user and deletes the anonymous one, is used only to switch to the account's data, below. Sign in with Apple's ID tokens are checked against the iOS app's bundle id (`APPLE_APP_ID`, `apps/server/wrangler.jsonc`) and the Services ID of Apple's web page, through which Android signs in (`APPLE_SERVICES_ID`, below), and the app sends the nonce it asked Apple with, Apple's token carrying its SHA-256. Google's are checked against the Google OAuth clients' ids (`GOOGLE_CLIENT_IDS`, the same file): both apps ask Google for a token for the Web client (iOS: Google Sign-In's `GIDServerClientID`; Android: Credential Manager's server client id, which its build reads from `GOOGLE_CLIENT_IDS`' first), so one audience serves both, and the iOS client's is taken too; the app sends the nonce it asked Google with, which Google's token carries as it is. The iOS app's Google client ids are its build settings (`GOOGLE_IOS_CLIENT`, the iOS client id before `.apps.googleusercontent.com`, and `GOOGLE_WEB_CLIENT_ID`), which its Info.plist reads (`GIDClientID`, `GIDServerClientID`, and the reversed client id as a URL scheme). Client ids are not secret; better-auth takes no client secret for either, as it never runs a provider's redirect itself: Android's Apple sign-in returns to the server's own handoff (below), which needs none, and the server signs a client secret only to revoke Apple's tokens (Deleting an account). Google knows the Android app by its Android OAuth clients, its package and each signing certificate's SHA-1 in the Web client's Google Cloud project, which the app never names and the server never checks. Right after Google Sign-In hands back the token, the app signs out of it (Android: clears Credential Manager's state), so the device keeps no Google session: Pochical needs nothing of Google's after the token. Both apps offer Apple and Google, Sign in with Apple first and the two the same size (App Store Review Guideline 4.8), Apple's black, or white in dark mode, as Apple's guidelines ask, Google's drawn as its branding guidelines ask (its four-color G; white with a gray outline, near-black in dark mode, `googleButton` in design/src/sign-in.ts; both `sizes.signIn` tall), each saying 〜で続ける, and each following a change between light and dark while shown. Both apps have both. Android draws Sign in with Apple's button itself, as there is no system one: Apple's logo (/design's `AppleLogo`) and Appleで続ける in white on black, black on white in dark mode, round ended as iOS's. A user is linked to one provider at most: linking another to a user linked already is refused (better-auth answers 417 to the account hook's `ALREADY_LINKED`), as is `TakeAccount` on a caller linked already (FAILED_PRECONDITION, before anything is deleted), so the apps offer linking only while anonymous. An ID token sent without its nonce is refused, `/link-social` and `/sign-in/social` with `NONCE_REQUIRED` and `PeekAccount` and `TakeAccount` with INVALID_ARGUMENT, as better-auth checks a nonce only when one is sent.
- Android has no Sign in with Apple of its own, so it gets the same ID token from Apple's web page, which posts its answer to the server, and the server hands it on to the app (`apps/server/src/apple-handoff.ts`, `AppleWebSignIn` in the kit). The app makes a verifier and a nonce (each 32 random bytes in hex, as a nonce for Google is), and opens `GET /apple/authorize?challenge=<S256 of the verifier>&nonce=<SHA-256 of the nonce, hex>` in an Auth Tab (androidx.browser), or in a Custom Tab where the default browser has no Auth Tab, never in a WebView, whose page the app could read (RFC 8252). The server sends it on to Apple's authorize page for the Services ID (`APPLE_SERVICES_ID`), `response_type=code id_token`, `response_mode=form_post`, `scope=email`, the nonce hash, the challenge as the state, and `redirect_uri` `{BETTER_AUTH_URL}/apple/callback`. Apple posts `code`, `id_token` and `state` there; the server keeps the ID token and the code under a new one-time code for two minutes, with the challenge (in better-auth's `verification` table, which the daily cron clears of those never redeemed; Apple's answers are held back by the address posting them, `APPLE_CALLBACK_LIMIT`), and answers 303 to `pochical://apple-sign-in?code=<one-time code>&state=<challenge>`; the person cancelling comes back as `error=cancelled`, anything else missing as `error=failed`, and a state that is no challenge as `error=failed` alone, keeping nothing. The Auth Tab hands that URI back to the app (a Custom Tab opens it through the app's intent filter for the scheme, its one activity taking it as a new intent); the app takes only the state it sent, and redeems with `POST /apple/redeem` `{ code, verifier }`, answered `{ idToken, authorizationCode }` once: the code goes at the first try whatever the verifier, and one unknown, used, expired or redeemed with another verifier is answered 400 `HANDOFF_REFUSED`, so a code caught on its way to the app (another app claiming the scheme) is of no use. From the ID token on it goes as iOS's does: linked with `/link-social`, or the account switched to, the nonce sent with it. better-auth's own redirect sign-in (`/sign-in/social` without an ID token, returning to `/api/auth/callback/apple`) is not used: it links or signs in the browser at its callback, where switching (below) needs the ID token in the app.
- When the provider's account belongs to another user already, `/link-social` answers 409 (`SOCIAL_ACCOUNT_ALREADY_LINKED`): that user holds the person's data from elsewhere, as from another phone. The person keeps either that user's data or this device's, and the other is deleted (Switching to an account in use, below).
- The server keeps no provider tokens: the ID token (which carries the person's email), and any access or refresh token, are left out of better-auth's `account` row, as a session keeps no address; Apple's answer for Android waits for the app two minutes, and goes as it is redeemed, or at the next daily sweep. Only which provider account is linked to which user is kept. The app keeps the email the ID token carried on the device, for 設定's アカウント to say which account it is, beside the provider's mark and name: Android keeps it with the session (`StoredSession.linked`), so it goes wherever the session goes. `UserService.GetMe` says which provider the user is linked to (`provider`), so a device that did not sign in itself, as one restored from a backup, still names it, without the email; Android asks it each time it signs in.
- A user who never linked and loses both their phone and its stored token cannot be reached again. That is why the app suggests linking, at moments its screens decide.
- A user Pochical's people suspended (spec/admin.md, ユーザー) signs in nowhere: their sessions are deleted, so their devices get 401 (Reconnecting), and signing in with Apple or Google to them (`/sign-in/social`) is answered 403 with better-auth's `code` `USER_SUSPENDED`, and switching to their account (`PeekAccount`, `TakeAccount`) with PERMISSION_DENIED. The app says either as このアカウントは利用を停止されています (このAppleアカウントではログインできません。, or このGoogleアカウント…, the provider signed in with), not as a failure to try again.
- Cloudflare's rate limiting holds back what an anonymous account makes cheap, by the limiters in `apps/server/wrangler.jsonc` (`ratelimits`, where their numbers are): anonymous sign-ins per client address, answered with 429, and groups made per user, answered with `RESOURCE_EXHAUSTED`. The address is only counted, never kept.

### Switching to an account in use

What the device holds may be a few taps tried before signing in, or months of shifts entered without ever linking, while the account was started on another phone. The person keeps one side whole, its groups and messages with it, and the other is deleted. Nothing is merged: a merge would have to match patterns and coworkers that mean the same thing under different ids, and keep groups of two users, for a case that seldom has data worth keeping on both sides (`apps/server/src/account-switch.ts`).

1. Before anything is deleted, the app asks the server what the account holds (`UserService.PeekAccount`), sending the provider's ID token and its nonce on the anonymous session (`ProviderToken`: the provider, the token and the nonce, as `TakeAccount` takes them too), which proves the person holds that account. The server answers with the account's days with a shift of their own, whether a repeating order is set, its coworkers and its groups; the device counts its own the same way (`Holdings`).
2. It shows both sides' counts in an alert, from which the person can tell a try from months of use (どちらのデータを使いますか？ / アカウント：… / この端末：… / 使わないほうのデータは削除されます。), and offers two answers:
   - アカウントのデータを使う, first, as someone signing in to an account they used is more often after its data. The device signs in to that user with `/sign-in/social` and the same ID token, then deletes the anonymous user with `DeleteAccount` on its old session, as deleting an account deletes it, its groups and messages with it (better-auth's own deletion of it is turned off, Deleting an account). The old session is kept on the device until that deletion is answered (iOS: a Keychain item of its own; Android: in Block Store beside the session, a list written with the session switched to in the one write that switches, and kept whatever the session does after, a deletion of the account switched to included), and if it fails, as when the network drops, the device tries again each time the app comes to the front, forgetting the session once the server deletes the user or no longer knows the session. The device drops what it held and catches up from the account: Android, once the new session is kept, signs in as it, which erases what the user before held as it claims the database (Sockets), so an app ended in between does the same as it starts.
   - この端末のデータを使う (`UserService.TakeAccount`). The server deletes the account's user, as deleting an account deletes it, its groups and messages with it, and links the provider's account to the anonymous user in the same call, clearing `isAnonymous` as linking does. Devices still signed in to the deleted user are signed out, and say so as on a 401 (Reconnecting). While the server answers either, the device stays signed in as before and nothing else changes who it is; a 401 meanwhile waits for the answer, which settles it as on a deletion (Deleting an account). Android runs this in `SyncAccount`'s one command queue: a change begins and is settled there, each for the stretch of the account it was asked in, so an answer for a stretch already over changes nothing, and the account owns it from the moment it is asked, so a screen gone meanwhile never leaves one begun and unsettled.
3. When one side holds nothing the person entered (no day with a shift, no repeating order, no coworkers and no groups), the app does not ask, and keeps the other, the account's first when neither holds anything. A new phone's first launch offers signing in before anything is entered, so most switches go this way. Patterns are not counted, as every user has some.

### Signing out

設定 › アカウント's ログアウト, asked first (ログアウトしますか？ / この端末からデータが消えます。もう一度ログインすれば、同じデータを使えます。), sends what waits in the outbox, ends the session on the server (`/sign-out`, which closes its sockets and drops its push token, Push), erases what the device holds of the user as deleting does, and goes on as a new anonymous user, starting from はじめの設定's welcome as a new phone does (spec/shift-patterns.md, The first run). Signing in with Apple or Google again brings the account's data back, through the switch above, as the device then holds nothing.

### Deleting an account

設定 › アカウント's アカウントを削除 deletes the account and everything of it, as the privacy policy and pochical.app/account/delete say, asked first (アカウントを削除しますか？ / シフト、グループ、チャットがすべて削除されます。元に戻せません。 / アカウントとすべてのデータを削除). It is `UserService.DeleteAccount` (`apps/server/src/account-deletion.ts`), whose steps can be run again, so a deletion cut off part way is finished by trying again, the session going last:

1. A user linked to Sign in with Apple has Apple's tokens revoked first, as Apple asks apps that offer it. The server keeps none of them, so the app asks Apple once more for an authorization code and sends it; the server exchanges it for a refresh token, with a client secret signed by the Sign in with Apple key (`APPLE_SIGNIN_KEY`, `APPLE_SIGNIN_KEY_ID`, from the team) for the client Apple gave the code to, checks the token is of the Apple account linked, and revokes it. iOS's code is for the iOS app; Android's comes through Apple's web page (Signing in, its `authorizationCode`), Apple's page opened once more as for signing in, and is for the Services ID, which `DeleteAccount` says with `apple_code_from_web`. Either matches an account linked on either platform, as Apple gives one person the same id in every client of one team. Without a code, or with one Apple does not take or of another Apple account, nothing is deleted (`FAILED_PRECONDITION`). Which one the user is linked to the app asks the server just before (`GetMe`), rather than going by what the device noted, so a device restored from a backup or one whose note is stale asks Apple exactly when the server will need its code. A user linked to Google is deleted without asking Google again and sends no code: Apple's asking again exists only for revoking its tokens, and the server keeps none of Google's (nor does the device, signed out of Google Sign-In at once), so nothing of Google's is revoked. The person removes Pochical from their Google Account's third-party connections should they want to.
2. In each group the user ever asked to make or join, left ones too, the Group DO takes them out as leaving does, their shifts with them, and marks them `deleted` with no name (`Member.deleted`): every line they wrote is taken back as 送信取消 takes one, their photos deleted, and their reactions and votes come off the lines they were on. The groups are those the User DO knows of in any of its three records: noted before the group hears of the user (`known_groups`), so a group whose news of them never reached their DO (Groups, Membership news) is reached too; listed (`memberships`); or asked to be made (`group_requests`). Leaving finds the group the same way. A group with no one left in it goes whole: the Group DO's storage first, but the membership news it still has to tell those who left before, after which it takes no one joining (`addMember` answers it gone); then its invitation and its photos, which find the group again should its erasure be cut off part way (spec/admin.md, 全消去).
3. Their chat with Pochical's people goes, its photos with it, and its Group DO (`support:{userId}`, Chat) whole, and with it what the app posted of it in Slack (Deleted accounts' chats in Slack, below).
4. The User DO's storage goes: days, patterns, coworkers, groups, push tokens. Its sockets close, and it takes no group's news after.
5. The account is noted as deleted, with when (`deleted_accounts` in D1), for the reports naming it to go a year after (Reports after a deletion, below). Noted again by a retry, it keeps the first time.
6. better-auth deletes the user, their sessions and their provider accounts, which closes what is still open. Their other devices are signed out, as on a 401 (Reconnecting).

アカウントを削除 and ログアウト are offered only while the device has its session: before its first sign-in reaches the server (offline at a first launch, or a Keychain it could not read), both are disabled, saying インターネットにつながると、ログアウトとアカウントの削除ができます。, rather than failing after Apple was asked. A deletion that fails says why, titled アカウントを削除できませんでした, and what to do next, the device signed in as before but where said (`DeletionFailure` in both apps):

- No session yet, the button pressed just before it was disabled: まだサーバーにつながっていません。少し待ってから、もう一度お試しください。
- The account changing, or the device signed out or started afresh while Apple was asked (another window): nothing is deleted, the user it is now included, as the deletion goes only as the session it was asked in: 削除しているあいだにアカウントが切り替わったため、削除していません。
- Apple gave no code (the person canceling says nothing): Appleで確認できませんでした。もう一度お試しください。
- The server refused it (`FAILED_PRECONDITION`, step 1): このアカウントのApple IDか確かめられませんでした。ログインしたときと同じApple IDで、もう一度お試しください。
- The server was not reached (no answer: URLSession failed short of being cancelled, as offline or the connection dropped, or the call timed out): サーバーに接続できませんでした。インターネット接続を確かめて、もう一度お試しください。
- Any other error of the server's: 時間をおいて、もう一度お試しください。, a deletion cut off part way finishing as it is tried again.
- The server does not know the session (401), or a socket said so while Apple was asked: the session ends as on a 401 to a socket, ログアウトされています in place of the app (Reconnecting), with no alert. A retry after a deletion whose answer was lost lands here too, which that screen covers (アカウントが削除されたため).

The device that deleted the account erases what it holds of the user (every table, the outbox and the chats' photos), forgets its token, and goes on as a new anonymous user, as on a first launch, はじめの設定 and all, kept as soon as the deletion is done (so the app ending meanwhile still starts there) and saying アカウントを削除しました over its welcome; its own settings stay. Android shows the erasing in place of the app (アカウントを削除しました / この端末のデータを消しています。, with 再試行 once a try failed), then はじめの設定's welcome, saying アカウントを削除しました over it once (counted as each erasing is done, however briefly it showed). Before anything is erased, whatever the reason (a deletion, ログアウト, はじめから使う), the database notes whom it lets go of and why (`SyncState.erased`, `erasedWhy`), a local write that cannot fail as the store can, then erases what it holds of them, then forgets the session; an app ended at any point after the note, finding its session is of the user noted, goes on erasing as it starts rather than showing their data or ログアウトされています, and never signs in as them again. In the groups, the members left see each line of theirs as 削除されたメッセージ, and a one-to-one chat with them as 相手のアカウントは削除されました, where it takes no more lines. Reports made by or about them stay for a year, as what Pochical's people act on, and then go, as the privacy policy and pochical.app/account/delete say. better-auth's own deletion of an anonymous user (`/delete-anonymous-user`, and after a switching sign-in) is turned off, as it would leave their groups and chats behind.

### Deleted accounts' chats in Slack

A deleted account's chat with Pochical's people also goes from Pochical's people's Slack channel, as far as the app's own token can delete it (spec/admin.md, Slack).

- Every message the app posted in the chat's thread is deleted (`chat.delete`): the user's lines, their reactions' notices, and Pochical's people's answers written on the admin site; every reaction the app put on Pochical's people's replies, the user's and the ✅ saying a reply was sent (`reactions.remove`); and every file the app uploaded there, the user's photos (`files.delete`). The app's messages and files are those its bot posted, as Slack's `auth.test` names it, found in the thread with `conversations.replies`.
- The thread's first message, which held the user's first line, is not deleted but changed (`chat.update`) to say the account was deleted and its messages and photos with it: （このユーザーのアカウントは削除されました。ユーザーのメッセージと写真は、アプリ・管理サイト・Slackから削除されています）, with metadata of the event type `pochical_account_deleted` naming no one, by which a try again sees it done. Pochical's people's replies written in Slack stay under it, which the app's token cannot delete; they last as the channel's retention keeps them, and the marker says why the conversation around them is gone.
- The thread is noted as it is unindexed (`erasing_slack_threads` in D1, in the same transaction as `support_chats` and `support_slack` lose the user), with when and no user's id; a thread whose first message lands after its chat was erased, as the relay keeps it, is noted then instead, finding no chat to keep it on. The erasure is tried at once by the account's deletion and by the account switch, and left to the cron by 全消去. The account's deletion never waits on Slack. A try Slack does not take (refused, busy or out of reach) leaves the note, and the Worker's daily cron (Reports after a deletion) tries it again; each try reads the thread as it is, so it deletes only what is left, and what Slack no longer has (`message_not_found`, `file_deleted`, `thread_not_found`) counts as gone.
- The note stays until a try a day or more after it finds nothing of the app's left, for a relay post under way as the chat was erased, which may land after the first try.

### Reports after a deletion

A report made by or about someone whose account was deleted (its `reporter_id` or `target_id`; spec/chat.md, Reporting and blocking) is kept at most a year (365 days, `REPORT_KEPT_MS` in `apps/server/src/report-retention.ts`) after the deletion, as handling abuse may need it, and then erased: its row in D1, with its notes in 記録 (`admin_actions`, spec/admin.md), and its message in Pochical's people's Slack channel, as Slack's `chat.delete`. Reports among people still here are kept as they are. Lines of a deleted account around another's reported line stay in that report as it was made.

- The Worker's cron (`triggers.crons` in `apps/server/wrangler.jsonc`, each day at 3:00 in Japan) erases the reports of every account noted deleted long enough ago that its year would be up before the next run, so none outlives its year.
- A report notes, as it is made, whether it is to be posted in Slack (`reports.slack_tried`, so when Slack is set up), before the post is tried, and keeps its message (`slack_ts`) once Slack says which it is. So it is one of three: never posted, with nothing in Slack to erase; posted, its message known; or posted with its message unknown, Slack's answer lost or the report's update after it failed, so its message may be there or not.
- A report's message goes first: by its `slack_ts`; or, when the report has none but its post was tried, found first in the channel's history by the metadata the post carries (`pochical_report`, with the report's id, read back with `include_all_metadata` as the relay's posts are, spec/admin.md), among the messages posted while the report's request could still post it (Workers end its `waitUntil` 30 seconds after the answer). One not found was never taken, and its report goes with nothing to delete. One Slack does not delete (other than one Slack no longer has, `message_not_found`), or a history Slack does not give, keeps its report, and its account's note, for the next day's run, saying why in the Worker's logs. The rest go, and an account's note once its year is up and no report names it. A run cut off part way is finished by the next.
- The note is made after the account's groups, chats and DO are gone, and before its sign-ins, so a report made in the moment of a deletion still names an account noted. A deletion that stops between the two leaves an account noted that is still here; the sweep takes only an account no longer in better-auth's `user`, so its reports stay until the deletion is done.
- A line taken back, and the app's notices, are not reported (the server answers `NOT_FOUND`): nothing of anyone's is in them, and so every report names someone whose account was there when it was made.

## Groups

`GroupService` (`proto/pochical/v1/group.proto`) makes groups and lets people into them; every call needs a session.

- Creating a group gives it a random id, sets up its Group DO with the name, the mark and the maker as its first member, and issues its first invitation code. A group's mark (`GroupMark`) is exactly one of an emoji (spec/text-limits.md, isEmoji), one of the mark icons (`design/src/mark-icons.ts`), letters of at most `textLimits.groupMark` characters, the last two in a color of the mark palette, or a photo; the server refuses any other mark, on creating and renaming alike. ## Sockets

Clients open one WebSocket to their User DO, at `/v1/me/socket`, one per group they are viewing, at `/v1/groups/{groupId}/socket`, and one to their chat with Pochical's people while 設定 or that chat shows, at `/v1/me/support/socket` (Chat). The Worker checks the session before either reaches a Durable Object, and lets a group socket through only when the user's own DO lists the group, so an id that is not theirs is refused (403) without waking or creating a Group DO. The Group DO then decides, as it decides who is in it: it accepts the socket of a member alone (403 otherwise, before any catch-up), asks at every frame, `Hello` first, whether its user still is one, and closes the sockets of someone taken out, gone or leaving, and everyone's as the group goes, with `socketRules.notMemberCloseCode`; so a socket open on a group is always a member's, and what it sends reaches members alone. The calls on a group (`GroupService`, `ChatService.Report`) and its photos ask the user's own DO and then the group the same way. A socket remembers the session it was opened with: when that session ends (the user signs out, or their account is deleted), the server closes the sockets it opened, on the user's DO, in their groups and in their chat with Pochical's people, and the device's next try gets 401 (Reconnecting). Every message is binary: clients send `pochical.v1.ClientFrame`, the server sends `pochical.v1.ServerFrame` (see `proto/pochical/v1/sync.proto`). Text messages are protocol errors, but for the keepalive text (Keepalive).

A device keeps its User DO socket open while the app is in the foreground, and one place's socket: that of the top page over the tabs that is of a place while one shows (a chat, or what it opens, or a group's page, spec/chat.md, The chat's page; a page of 設定, or one a group's settings open, is of the place of the page or tab it was opened from), else a group's while that group is open in the グループ tab and that tab shows, and the chat with Pochical's people's while the 設定 tab shows; one place's at a time, the app's own and not a screen's, so a cover over the place (a photo open large, an invitation, the QR code) or a list scrolling does not close it, and every screen over the place uses the one socket. It closes them as the app goes to the background, where the OS would soon stop them anyway, and a place's as another place or tab is opened, and opens them again when it comes back. If its outbox still holds edits then, it first asks the OS for a little time in the background (a background task on iOS, WorkManager on Android) to connect if need be and send them until they are acknowledged, so a shift changed just before leaving reaches the user's other devices and groups without waiting for the app to be opened again; it does the same for edits made outside the app, such as from a widget. A group's socket likewise stays until the group's chat outbox (Chat) is sent and acknowledged, in that same time when the app has gone to the background, so a line sent just before leaving, or before opening another group, reaches the others at once; a line not sent (its photo could not go, or it waited too long) waits for the member instead (spec/chat.md, Lines on their way). The group opened again meanwhile takes back the socket still closing rather than opening a second: two would send the same outbox side by side, and only a send is taken once by its `op_id`, so a reaction's, vote's or pin's on sent late on one could land after its off on the other.

When the device goes on as another user (switching to an account, signing out, deleting the account), it closes every socket, the user's and every place's, before it erases what it held, so nothing more of the user before is taken in or sent. One owner on the device decides who it is and opens every socket (iOS: `AccountSession`). Until the server has done its part of a change, the device goes on as it was, signed in as the user before: its sockets stay open and keep sending (a closing one's chat outbox too), and its calls, loads and uploads go on, while no other change begins; only once the server has done its part does the stretch end, before anything is erased. So a change that fails, as when the network drops, leaves everything as it was, with nothing to bring back: a photo loading comes, a photo going up goes, and a line waiting goes as the connection comes back, as Telegram and LINE send it, by the sockets' own reconnecting (Reconnecting). Signing out waits for the user's outbox to go first, the socket open after. Changes go one at a time: while the server answers one, nothing else changes who the device is (no other change begins, and もう一度つなぐ and はじめから使う, which only the session-ended screen offers, cannot be chosen), and a 401 to a socket meanwhile is noted, not acted on. The answer settles it in one place: done, the change goes on as done, as the change itself is the likeliest reason for that 401 (signing out and deleting end the session), so the person is never left signed out of an account they asked to leave with its data kept; failed, the device is as it was, or, should a 401 have come meanwhile (or the deletion itself been answered with one), the session ends as on any 401. Each stretch signed in as someone is counted, and what comes back for an earlier one (an answer, an upload, a frame on a socket) is dropped. The database also records whose data it holds: a fresh or erased one is no one's until the user signed in claims it, with what was entered before signing in, and a socket neither sends from nor takes into a database that is not its user's, checked in the same transaction as each read and write, so no order of events can carry one user's data to another. A switch goes in an order that leaves the device as it was when a step fails or the app ends part way: the server's part, then the erasing (every table but the device's own, named one by one), then the stored session replaced in one step; an erase that fails stops the switch and says so, the device staying who it was. Signing out and deleting cannot go back once the server has ended the session. From then until the device has forgotten the session and erased its data, the app shows none of it: only that the account is signed out (ログアウトしました) or deleted (アカウントを削除しました) and that this device's data is still being cleared, trying again after a wait that doubles, with 再試行 to try at once. The device notes it is erasing as soon as the server has answered, before it waits on anything else (the places' sockets closing included), so an app cut off meanwhile goes on erasing as it starts and is never signed in as the session that ended; only once both are done does it sign in anonymously as a new user. A database left by a user the device has no session for (a restore without the Keychain) is erased before the next user's sockets open, as nothing on the device can send what it holds any more. A call that needs a session while the device is signing in waits for it, for a while at most, rather than going as no one. The places held on screen go with the account: no page of the user before stays open, and the places of whoever the device is next are held anew. A change that fails before the server has done its part leaves the device as it was, its pages and the places they hold too, so the failure is said where it was asked; a switch whose erasing or Keychain fails after it goes back to what the device was as a new stretch, its pages made anew: signed in as the user it was, or, should a 401 have ended that session meanwhile, saying so (ログアウトされています), written to the stored session, and then going on as whatever the stored session holds (as it was, should that write fail; starting, as at a launch, should it not be readable), so the device is only ever what a relaunch would be. What the device fetched for the user (photos, links' pictures) is kept only in its own files, erased with the rest, never in the system's URL cache. It also takes away every notification it shows and the app icon's badge, which were the user before's, and sends its push token again under the session it has now (Push), so the user it is now hears at once, without waiting for the next launch. Then it connects as whoever it is now, the place open on screen at once and the others as they are next opened, a socket stopped by a 401 under the user before included (Reconnecting). はじめの設定 replacing the tabs (after signing out or deleting the account) holds no place's socket.

### Handshake

1. Before connecting, the client may call `SystemService.GetServerInfo` and ask the user to update when its protocol version is below `min_protocol_version`.
2. The first frame must be `Hello { protocol_version, cursor }`.
   - Below the server minimum: the server replies `ServerError { CODE_PROTOCOL_TOO_OLD }` and closes with 1008.
   - Otherwise it replies `Welcome { cursor, server_ms }` with the head of the DO's change log and the server's time, which the device corrects its clock by (HLC).
3. Any other frame before `Hello` gets `ServerError { CODE_BAD_FRAME }` and the socket is closed with 1008.

### Keepalive

The numbers are `socketRules` in `design/src/socket.ts`.

- While a socket is open, a device sends the text message `keepaliveText` every `keepaliveEveryMs`, and the server answers `keepaliveReply`. The runtime answers it (`setWebSocketAutoResponse`), so keeping a socket alive never wakes a hibernating Durable Object. With no answer within `keepaliveWithinMs`, the device takes the socket for dead, closes it and reconnects. A device that the OS says has lost its network closes its sockets at once rather than waiting for that, and connects again as the network comes back. Likewise when another network becomes the default while the one before is still up, as Wi-Fi coming back while cellular is connected: the OS says only that the new one is the default, keeps the one before a while and then tears it down, and a socket left on it may carry nothing meanwhile, so the device closes its sockets at once and connects over the new one (`spec/vectors/reconnect.json`, defaultNetwork). Android hears it as the default network callback's `onAvailable` for another network, with no `onLost` before it; iOS as `NWPathMonitor`'s path staying satisfied with another interface first among its `availableInterfaces`.
- `Ping { nonce }` is answered with `Pong { nonce }` by the Durable Object itself, after every frame it sent before. It is not for keeping alive: a device that sends one after `Welcome` knows, at its `Pong`, that its catch-up has all arrived. A device that cannot send that `Ping` gives the socket up and asks again on the next one, rather than staying open on a catch-up it never sees end.

### Reconnecting

- A device reconnects when a socket closes, or its keepalive goes unanswered. Before each try it waits a time drawn at random from 0 up to `reconnectFirstMs` doubled for each try before it since a socket last caught up, at most `reconnectMostMs` (`spec/vectors/reconnect.json`, waitMost and tries). A socket's catch-up coming to its end (the `Pong` to the `Ping` after `Welcome`, Keepalive) starts the count again, not the `Welcome` itself, so a socket that breaks right after its `Welcome`, again and again, still waits longer each time rather than hammering the server. The first try after it waits too, up to `reconnectFirstMs`; only a socket asked to be open, another default network (Keepalive) and `CODE_CLOCK_AHEAD` try at once, the count started again. The random wait keeps devices cut off together, as by a deploy, from coming back together.
- It tries at once, starting the count again, when the app comes to the foreground, the network comes back or another becomes the default (Keepalive): the person is waiting then.
- After `CODE_CLOCK_AHEAD` it reconnects at once (HLC).
- It does not reconnect after `CODE_PROTOCOL_TOO_OLD` until the app is updated, nor after a 401 to the upgrade, nor to a group after a 403 or a close with `socketRules.notMemberCloseCode` until that group is opened again (as after joining it again): the user is not in the group, which the group decided, and their own socket's `Membership` marked `left` drops it from their list.
- A 401 says the server does not know the session. Sessions last for good, so it should mean the user signed out or their account was deleted, on another device or by request; but a server misconfigured, or one whose `BETTER_AUTH_SECRET` was changed (the apps' tokens are signed with it), answers every device so at once. So a device never deletes anything on a 401 alone, and never answers it with a new anonymous sign-in, which would be a new user without their data. On a 401 to any of its sockets, or to deleting the account, it stops syncing, every socket closed, keeps what it holds and its outbox, and says so in place of the app, the session kept as ended (`StoredSession.ended`) so a relaunch or a new install says so too, trying nothing (ログアウトされています: ほかの端末でログアウトしたか、アカウントが削除されたため、同期できません。この端末のデータは、はじめから使うまで消しません。), until the person chooses: もう一度つなぐ asks the server about the session again (`GetMe`), as a server set right since knows it again, and goes on signed in as it only once the server answers, so the app never shows for a moment before the session ends again; a 401, or no answer (offline, or the server failing), leaves it ended as it was, the button showing it is asking meanwhile; はじめから使う, asked first (はじめから使いますか？ / この端末のデータが消えます。アカウントが残っていれば、Apple または Google でもう一度ログインすると同じデータを使えます。 / データを消してはじめる), erases what the device holds as signing out does and goes on as a new install, where a linked user whose account is still there signs in with Apple or Google again and has its data back. Android runs both in `SyncAccount`'s one command queue, as it does changes, each only while the session is ended, もう一度つなぐ once the server has answered and only for the session it answered about; it erases as after a deletion (Deleting an account), the database first, noting whose it was, then the session, which stays kept as ended until it is forgotten, so an app ended in between goes on erasing as starting afresh, and the note of whose it was goes as the next user claims the database, so signing in to that account again brings its data back; it shows the erasing titled ログアウトしました, as iOS does, and says nothing after. Starting afresh keeping the device's data (signing in anonymously as a new user and sending everything of the user's own it holds, days, patterns and their order, repeating orders, coworkers and their order, to the new User DO as edits with new clocks, the old user's groups and other devices lost) is not built yet (#802). Nothing on the device is ever cleared but by the person's own choice. `BETTER_AUTH_SECRET` is never changed: changing it signs everyone out (`apps/server/wrangler.jsonc`).

## Change log and cursor

Each DO keeps an append-only change log. Every accepted mutation (shift edit, message sent, message edited or deleted, read state moved) gets the next `cursor`, a `uint64` that only grows.

Each DO gives out cursors from one counter of its own (`log_head`, one row), and from nowhere else: `nextCursor()` moves it on by one and returns it, in the transaction of the write, and no code works a cursor out from the head or from another cursor. The newest cursor given out is never read off the values, since a DO that removes rows could take its head back, and a device already past it would miss what comes next. A write that turns out to change nothing leaves its cursor unused: cursors only grow, they need not follow each other, and a device takes the newest it was sent.

- After `Welcome`, the server sends every change after the client's cursor, then streams new changes as they happen.
- The client applies changes in cursor order and stores the last applied cursor in the same SQLite transaction.
- If the client's cursor is older than the oldest change the DO still keeps, the server tells it to reset: drop that DO's cache and load a fresh snapshot.
- A DO whose values are last-writer-wins registers (a User DO's days) keeps only each value's latest change, at the cursor it got then, so "every change after cursor N" is the values changed since N and reaches back any distance. Such a DO resets a client only when its cursor is ahead of the DO's head (the DO restored from an older copy): `Reset`, then a `Changes` with everything it holds.
- A device moves its cursor past every `Change` it is sent, those of a kind or with a field it cannot read (from an app newer than itself) too, so after the app is updated to read them they would not come again until they next changed. So each app keeps a sync schema, a number it raises whenever it starts reading a `Change`, or a field of one, it did not read before, and the device keeps the one it was synced under. A device whose app's sync schema is newer than its own, as the app opens its database, moves every cursor back to 0 (its User DO's and every place's) and takes the app's, in one transaction, keeping every value it holds and its outboxes. Its next `Hello`s then bring everything again, which replaces what it holds; it does not drop its values first, as a `Reset` does, so nothing goes from the screen while it is offline. Only its chats' lines go, as at a `Reset`: a catch-up from 0 brings each chat's latest page alone (Chat), so a change to an earlier line it held would never come again; they come again as pages. A new device starts at its app's sync schema, its cursors being 0. The iOS app last raised its (`Sync.schema`) as it started reading a chat line's `content`; the Android app's (`SYNC_SCHEMA`) starts at 1, reading the user's own values, their preferences and memberships, and the groups' members and shared values, and rises as it reads more.

## Shifts

### Conflict resolution

Only the owner edits their shifts, so concurrent edits happen only between the owner's own devices while one of them is offline. Each field of a day's shift (pattern, start, end, memo) is a last-writer-wins register ordered by HLC. No text or list CRDT is needed; two devices editing the same memo offline keep the later edit.

Deleting a day's shift writes a tombstone instead of removing the row, so a device that was offline cannot resurrect it by sending an older edit.

### HLC

A hybrid logical clock value is `(physical_ms, counter, device_id)`, compared in that order.

- On a local edit: `physical_ms = max(now, last.physical_ms)`; if it did not advance, `counter = last.counter + 1`, otherwise `counter = 0`. The counter is a `uint32`: at its end the clock moves to the next millisecond (`spec/vectors/hlc.json`, tick).
- On receiving a change: the device's last clock becomes the received one when that is later, so its next local edit orders after it (receive).
- `device_id` only breaks exact ties. It is the device's own id, written in ASCII letters, digits and `-` (a UUID as it is written), at most `syncLimits.idLength` long, so every platform orders two of them alike: Swift compares strings by Unicode scalars and JavaScript by UTF-16 units, which differ past the Basic Multilingual Plane. `server` is the server's own, for its corrections (Outbox step 5). The server acknowledges an edit with any other `device_id` without applying it.

HLC, not arrival order, decides the winner: an edit made offline at 10:00 and delivered at 12:00 must lose to an edit made online at 11:00.

`now` is the device's time corrected by the server's, so a device whose clock is set wrong cannot win over later edits, nor carry every device that takes its edits along with it:

- Each `Welcome` carries the server's time, `server_ms`. The device's offset is `server_ms` less the middle of the round trip, from when it sent `Hello` to when `Welcome` arrived, divided as whole numbers (offset). It keeps the last offset across launches, 0 before its first `Welcome`, and `now` is its own time plus the offset.
- The server refuses a frame of edits in which any clock runs more than `syncLimits.clockAheadMs` (`design/src/limits.ts`) past its own time: `ServerError { CODE_CLOCK_AHEAD }`, nothing in the frame is taken, and the socket is closed (ahead). A corrected clock stays well within it, so this catches edits stamped before the device's first `Welcome` or before its clock was changed.
- After `CODE_CLOCK_AHEAD`, the device reconnects, and once the new `Welcome` has corrected its offset, before sending its outbox, it starts its clock again from the later of `now` and the latest clock among the changes it has taken, dropping its own far-ahead one, and gives every unsent edit a new clock from a local edit's tick, in outbox order. Then it sends them. Its edits keep their order and come after everything it has taken; only on a device whose clock ran that far off do edits made offline lose their own times.

### Outbox

1. A local edit updates `my_shifts` and appends a row to the outbox in one SQLite transaction.
2. While connected, the client sends outbox rows in order, each with a unique `op_id` and its HLC.
3. The User DO applies each field only if its HLC is newer than the stored one, appends the result to its change log, sends what changed to every device as `Changes`, and then acknowledges the `op_id` to the sender with `Acked`. A repeated edit carries the same HLC, so it is acknowledged without being applied again.
4. The client deletes acknowledged rows. Unsent rows survive app restarts.
5. If the server rejects an edit (validation), it writes a compensating change with a newer HLC, which reaches every device through the change log.

An edit the device cannot keep (step 1's transaction fails, as on a device out of storage) is kept nowhere, and the app says so at once wherever the person edits: 保存できませんでした (もう一度お試しください。続くときは、端末の空き容量を確かめてください。) in an alert. The page stays as it was, its draft and all, so the edit can be made again; a page the edit was made leaving (a name kept as its field is left) is gone, and the alert shows over the page under it. The alert shows over whatever is on the screen: a sheet the edit is made in (a day's detail, 完了's question about the month's blank days, sharing days into a chat) stays open under it, and one going, a page being left or another alert closing finishes first, as does the app coming back to the screen when it was leaving. On the calendar, a shift not kept while entering leaves the same day to enter; in a chat, see Chat (Lines on their way, Drafts). The device does not try the edit again by itself, as the same write fails the same way until something on the device changes.

Free text is edited once it is written, when its field is left, not on each change (spec/calendar.md, Text fields).

What a device shows of a value while its edits wait (`spec/vectors/local-edits.json`). A value is what one change carries: a field of a day, a pattern, the patterns' order, the repeating orders, a coworker, the coworkers' order or a preference.

- A device keeps, for each value, the server's (the last `Change` it took for it) apart from its own edits of it still in the outbox, and shows the latest waiting edit's value if there is one, else the server's.
- A `Change` replaces the server's value and leaves the outbox alone, so a waiting edit keeps showing whatever arrives meanwhile. Its `Acked` ends the wait, and the device then shows the server's value, which by then is the edit's own, the correction for it, or the newer value it lost to: the server sends a frame's `Changes` before its `Acked`.
- So a device never compares clocks to choose between the server's value and its own; the server has done that.
- A new job's orders edit waiting in the outbox also hides the days' own values it takes back, comparing each value's clock with the edit's (`givesWay`, spec/vectors/order-clears.json): those set before it show cleared, while one set after it, by this device or another, shows. The server's clears for them come as `Changes` before its `Acked`; at the `Acked` the days show the server's values again, so orders that lost to newer ones take nothing back.
- A `Reset` drops the server's values and keeps the outbox.

### On the wire

The User DO socket carries a user's days (`proto/pochical/v1/sync.proto`); a Group DO socket refuses them.

- A `DayValue` is one field of one day: `date` ("YYYY-MM-DD"), `field` (`DAY_FIELD_PATTERN`, `_START`, `_END`, `_NOTE`, `_PEOPLE`), an optional `value` (unset clears the field) and its `Hlc`. A day whose `DAY_FIELD_PATTERN` is unset follows its repeating order, and has no shift where no order applies; a pattern of `dayRules.noShift` (`""`, `design/src/days.ts`) is a day with no shift, order or not (Repeating orders); keep it apart from no pattern everywhere, as its note there says.
- The client sends `DayEdits`, up to `syncLimits.editsPerFrame` a frame (`design/src/limits.ts`; every edit frame alike), each with its `op_id`. The server sends each value it changed, as `Changes`, to every device of the user that is past Hello, the sender included, so every device moves its cursor the same way, and then answers the sender with `Acked` for all of them (Outbox).
- An edit for no real day or field, or without a clock, is acknowledged and dropped: there is nothing to keep or correct.
- An edit whose value does not fit its field (a pattern that is neither `dayRules.noShift` nor an id, an id being up to `syncLimits.idLength` characters with no spaces as `apps/server/src/ids.ts` has it; a time not `HH:MM`; a memo past `textLimits.dayNote`) but whose clock is newer than the stored one is answered with the stored value (or none) under a clock just past the edit's, stamped with device `server`: the compensating change of Outbox step 5.
- After `Welcome`, a device gets its catch-up as `Changes` of up to `syncLimits.changesPerFrame` values each, in cursor order.
- Patterns go the same way, as `PatternEdits`: each pattern is one last-writer-wins `PatternValue`, sent whole (a deleted one has no `pattern`, kept so an older edit cannot bring it back), and the order they are shown in is one more, `PatternOrder`. They share the User DO's cursor with days, so a device catches up on both in one order. A pattern that does not fit (spec/shift-patterns.md: a blank name or one past `textLimits.shiftName`, a mark whose emoji is not one emoji, or whose letters are blank or past `textLimits.shiftMark`, a color past the palette, one time without the other, a `next_day` naming itself) or an order with an id twice is corrected as a day's value is.

### Repeating orders

How a day follows a repeating order is in spec/shift-patterns.md (Repeating orders). On the wire (`proto/pochical/v1/sync.proto`) and in storage:

- A user's orders are one last-writer-wins value, `RepeatOrders`, sent whole like `PatternOrder`: the timeline, each order with its `start` and `anchor` ("YYYY-MM-DD"), `sequence` (pattern ids), `holidays_off`, `holiday_shift` and `holiday_country` ("JP"). They are one value because they are one timeline: two of the person's devices editing it at once is rare, and keeping either whole beats a mix of both.
- Days are never written out from an order. `DayValue`s hold only what the person set on a day: an unset `DAY_FIELD_PATTERN` means the day follows its order, and `dayRules.noShift` means the day was cleared on purpose and shows nothing, order or not.
- Devices send them as `RepeatOrdersEdits` on the User DO socket, acknowledged and sent on as `Changes` like day edits.
- Every change of orders is one edit, `RepeatOrdersEdit`: the new `RepeatOrders`, and for a new job's order `clear_from`, its start. 繰り返し's changes (spec/shift-patterns.md, Repeating orders) send none, and so take back no days. The days' own shifts and times give way only if the orders do: when the server takes the new value (it fits and its clock is newer than the stored one), it clears `DAY_FIELD_PATTERN`, `_START` and `_END` on the days from `clear_from` whose values are older than the edit's clock, in the same transaction, and sends those clears to the user's devices as changes like any other. An edit that loses to newer orders, or does not fit, clears nothing; `clear_from` fits only as the start of the last order, the one being started.
- The server keeps each clear it made as a floor (`order_clears`: `clear_from` and the orders' clock). An edit of a pattern or time arriving later for a day from there, with an older clock, was made before the orders: the server answers it with the clear under the clear's own clock, so an edit made offline cannot bring back what they took, even on a day that had no value, while a later edit from the same device, made after the orders, still wins. Which values give way and which edits are held back is `spec/vectors/order-clears.json` (`apps/server/src/order-clears.ts`). Devices apply `givesWay` while a new job's order they started waits (Outbox); only the server keeps clears and holds edits back, and its changes settle what a device shows.
- A client works a day out as its own value, else its order's, with the holiday data of `design/scripts/holidays.ts` (`spec/vectors/repeat.json`). The server keeps and checks orders (`apps/server/src/order-values.ts`: real dates, starts that only grow, ids and counts within `syncLimits` in `design/src/limits.ts`, a country code of two capital letters, a `holiday_shift` whenever `holidays_off`), correcting ones that do not fit as it corrects a day, but never works days out; if it ever needs one, it uses the same logic against the same vectors.

Why not write the days out: a year of days is hundreds of values for every change of order, sent to every device and every group, and runs out a year ahead. An order is one small value without an end, and a holiday the law moves is fixed by an update of the apps' holiday data, not by rewriting everyone's days.

### Coworkers

The people a user notes on a day, like who is on the same shift. They are names only, not app users (/design's 一緒に働く人).

- Each coworker is a last-writer-wins `CoworkerValue` with an id and a name (`textLimits.personName` at most, not blank), sent whole as patterns are (a deleted one has none), and their order is one more, `CoworkerOrder`; devices send both as `CoworkerEdits`.
- A day's people are one more day field, `DAY_FIELD_PEOPLE`: coworker ids separated by spaces, in the order they were added; no id the apps make holds a space (`apps/server/src/ids.ts`). Days hold ids, so renaming a coworker changes one value; a deleted coworker's id is skipped where it is shown and needs no rewrite of days. When a device next writes a day's people, it leaves out the ids of coworkers no longer listed, so such ids go as the days are touched, without edits of their own.
- 設定 › 一緒に働く人 adds a person by name alone: on iOS in an alert with a text field, as iOS asks for one name (メモ's 新規フォルダ); on Android and /design in a field that opens in the list. Picking a day's people follows each platform's own way of choosing several (spec/calendar.md, A day's detail).
- A user keeps at most `COWORKERS_MAX` coworkers (`design/src/limits.ts`). Adding past it, in 一緒に働く人 or from a day, stops with a problem toast, 一緒に働く人は{n}人までです, and the User DO refuses a new coworker past it: it answers with the coworker deleted, as a value that does not fit. Their order holds at most as many ids; a longer one names coworkers the server refused, and is answered with the person's order of those they keep.
- Like the memo, coworkers and a day's people stay with their owner: they name people outside the app, so they are never pushed to groups.

### Preferences

How the person likes their screens is kept with the account, so each of their devices shows the same and a new phone, or signing in again, brings it back; what belongs to the device stays on it, as apps usually split settings that follow the person from those tied to one device.

- Kept with the account: the テーマ, the スタイル (the marks' shape and each shape's options, シフトの色), the calendar's week (the day it starts on, the colors of Saturdays, Sundays and holidays), シフトの期間, its heading (月と曜日, what a tap on the month's name does, and おたのしみ's sky), a picture's 休みの見せ方 and シフト名, and what 端末カレンダーに追加 puts in besides the shifts (メモも入れる, 一緒に働く人も入れる).
- Kept on the device: 外観, which follows the device's own by default; the app's icon, which the system sets for each device (iOS alone: an Android launcher shows one icon, switched only through activity aliases whose switch takes the icon off the home screen, so Android has no アプリアイコン and relies on the adaptive icon, its monochrome layer tinted by the themed icons of Android 13 on); the reminders, which the device sends itself, and would go off on every device; the calendar last added to, one of the device's own calendars; a picture's light or dark, the screen's until picked.
- Each preference is one last-writer-wins `PreferenceValue`, a key and its `message`, the message the key names encoded (`syncLimits.preferenceLength` bytes at most), sent as `PreferenceEdits` and acknowledged and sent on as `Changes` like coworkers. The server keeps a value without reading it: a key that is no id, or a value too long, is answered as a value that does not fit is. A value a device cannot read, one naming a shape or a look the app does not know among them, or a key it has none of, leaves the device's own, which also stands until the account holds one (`spec/vectors/preferences.json`).
- The keys and their messages (`proto/pochical/v1/preferences.proto`): `theme`, `ThemePreference`; `look`, `LookPreference`; `week`, `WeekPreference`; `period`, `PeriodPreference`; `heading`, `HeadingPreference`; `picture`, `MarkOptions`; `calendarAdd`, `CalendarAddPreference`. An app writes every field a message has, and a field added later reads as its zero in what an older app wrote, so a new field is named for its zero to be the app's own default.
- A device keeps them in its own settings too, which its widgets read, and takes each the account holds as it comes, sending only what the person changes on it. The account's are never pushed to groups, but for the shape the person draws their marks in (Profile).

### Deleted values

A deleted pattern or coworker is kept as a tombstone (a value without its pattern or name), so an older edit cannot bring it back. What names it keeps its id: deleting rewrites nothing else, as offline-first sync tools do, since a device offline at the time can still name it afterwards, and a rewrite would race the edits it meets. Every reader resolves a reference as it reads:

- A day whose own shift, or whose order's (its sequence or `holiday_shift`), names a pattern that is gone shows no shift and counts as blank (`spec/vectors/repeat.json`, shown).
- A pattern's `next_day` naming one that is gone fills nothing (`spec/vectors/entering.json`, enter).
- A day's people, and the patterns' and coworkers' orders, skip ids that are gone.
- When a device writes a reference field (a day's people), it leaves out ids that are gone, so they go as the values are touched (Coworkers).
- A device writes no new value for a pattern or coworker it holds as gone: an editor left open on one deleted from another device keeps nothing as it closes, as its newer clock would bring the value back. An editor that keeps a field as it is left writes only what was typed there, never the name it opened with, so a change from another device meanwhile stands.

Keeping the ids also lets a deletion be undone with what named it intact.

### Group projection

The User DO pushes what its groups see of the user to every Group DO the user belongs to. Values carry their HLCs, so the Group DO keeps each one only when it is newer: a push that arrives twice or late changes nothing.

- Only shared values are pushed: each day's pattern and times (named one by one, so a day field added later stays private until it is named too), never the memo or the people, the user's patterns, so members can draw their marks, and their repeating orders, so members' apps work their days out as the user's own do (`MemberRepeatOrders`). The patterns' order is the user's own.
- For each group the User DO keeps how far it has pushed (`pushed_cursor`, a cursor of its own log). After any change, and on joining or making a group, its alarm pushes each group the shared values changed after that cursor, then moves it. A group that cannot be reached keeps its cursor without holding back the others, and the alarm comes back for it, 10 seconds later and twice as long each time that group fails in a row, up to an hour, so the values reach it later. After about a day of failures in a row it stops coming back; the user's next change tries the group again.
- Each DO sets its alarm one way, for every alarm here (the User DO's pushes and its photos going, the Group DO's support relay, photo sweep and membership news): a time already past is now, as the runtime has it, and a time equal to the one the DO's latest run was set for is moved a millisecond later, as workerd keeps and never runs an alarm set for the time of the run it has taken up (cloudflare/workerd#7915). A first run that finds its own time stored as it begins, set after the runtime took it up and before it began, sets it again so, and runs once more for it; a retry of a run that threw finds its time kept by the runtime to retry it, and leaves it. A run ends by setting the alarm for what it still has to do, unless one set earlier stays, as one a change set while it ran. So storage never holds an alarm that will not run, and a change made while an alarm runs always has a run after it, at the time it asked or, when that is the run's own, a millisecond after.
- On joining, `pushed_cursor` starts at 0, so the group gets everything the user has.
- The Group DO takes a push (`takeMemberShifts`, `pochical.v1.Changes` as bytes) only from a current member, drops any day field that is not shared, keeps the rest at its own cursor and sends them to the members with the group open as `MemberDay` and `MemberPattern` changes. A group socket catches up from its cursor as a User DO socket does.
- On leaving, the Group DO deletes that member's projected shifts and sends members their `Member` marked `left`, on which devices drop that member's shifts and keep their name, which their lines in the chats still show.

## Chat

Chat has two orders that must not be mixed:

- `seq`: a message's position in the conversation, used for display and paging (`before_seq`, page size).
- `cursor`: the Group DO's change log, used for sync. New messages, edits, deletions and read states all arrive in cursor order.

The Group DO keeps the lines (`ChatLine`) and read marks (`ReadMark`) of its chats as values on its change log, beside its members' shifts. A group has its own chat (`thread_id` "group", 全体チャット) and a one-to-one chat for any two of its members.

A user's chat with Pochical's people is kept the same way, in a Group DO of its own named `support:{userId}` (spec/chat.md, Where a chat is kept): its `profile.kind` is `support`, its members the user and Pochical's people (`chatRules.pochicalMember`), and its one chat `thread_id` "group". The Worker reaches it at `/v1/me/support/socket` with the session's user, setting it up first (`setUpSupport`, which changes nothing once done and never makes a group one), so no one reaches another's. Nobody's joining is said in it, and neither member's profile is pushed to it. It takes what `chatPlaces.support` lets it, and gives no `setUnread` to Pochical's people, who have no User DO. To the user's User DO it gives its counts and notifications under the place id `chatRules.supportPlace`, which the User DO takes as one of the user's places beside their groups (counts, mutes, notifications and their taking back), and its notifications are worded as a one-to-one chat's but titled with the chat (`SUPPORT_TITLE`, 作っている人とチャット), which the Notification Service Extension leaves as they come, with no writer. Its photos are the place's (`PUT`/`GET /v1/support/photos/{id}`, kept as a group's are). Pochical's people write through the AdminEntrypoint (`answerAsPochical`, as their member, from the admin pages and Slack).

Outside the DO, D1 keeps an index of every user's chat (`support_chats`: the latest line, how many of the user's lines wait for an answer, the Slack thread) for the admin pages' list and for finding a Slack thread's chat, and which line each Slack message is (`support_slack`). The DO keeps them current as it keeps its groups' pushes: after any change its alarm tells D1 and the chat's Slack thread what changed after its relayed cursor (`support_relay`), then moves it; what each line's Slack message was told is kept beside it (`support_slack_lines`). A failure with D1 comes back later, and so does a new line Slack did not take: it stays untold, and the lines after it wait, until Slack takes it, never failing what the user did (spec/admin.md, Slack). The alarm comes back a minute after the first failure, twice as long after each in a row (`support_relay.failures`, since `failing_since`), up to ten minutes while what failed passes by itself (Slack rate limiting, a 5xx, Slack out of reach, D1) and an hour while it lasts (any other error Slack names: `not_in_channel`, `invalid_auth`, `channel_not_found`, ...), never sooner than a Retry-After Slack gave; a new change in the chat tries again at once all the same. The lines wait in their order rather than one Slack refuses being passed over: what Slack is sent stays within what it takes for any line (a line's words at most `textLimits.chatMessage` characters and, as the server takes no larger text, 32,000 UTF-16 code units, under Slack's 40,000 characters (spec/text-limits.md, Server); a photo shrunk before it is sent, Photos), so a refusal that lasts is the setup's, which every line waits on alike, not one line's. While it fails, D1's index says since when and Slack's word for why (`support_chats.slack_failing_since`, `slack_failure`), for the admin pages, cleared once all is told. A line is kept as told once Slack takes it, or once it is settled not to be posted (past `SUPPORT_LIMIT`, or Slack not set up), so it is not posted twice. Slack's answer may be lost after it took the line (Slack out of reach, a 5xx, `internal_error`, `fatal_error`, the DO stopped mid-call), and `chat.postMessage` has no key to tell a retry from a new message, so the relay marks the line it posts before the first call (`support_relay.posting_seq`, `posting_since`), clearing it once the line is kept or Slack's answer says it was not taken: a try that finds the mark looks for the line in Slack first (`conversations.replies` in its thread, or `conversations.history` for the message starting one, since the mark) and keeps the message it finds instead of posting again. Each message the relay posts carries the line in Slack's message metadata (`pochical_support_line`, with `seq` and `user_id`); a photo's message carries none, so its file is named for the line (`photo-{seq}.jpg`) and found by that. A photo Slack shared without saying where is not uploaded again. A reaction or a taking back Slack does not take is not told again.

### One-to-one chats

- Two members' chat is the thread `direct:{a}:{b}`, their two user ids in order (by UTF-16 code units; every id is ASCII), so either names it alike without asking the server (`spec/vectors/chat.json`, directThread). It exists once it has a line; there is nothing to create.
- Only its two members see it: the Group DO sends its lines and read marks only to their sockets, leaves them out of anyone else's catch-up, answers anyone else's `ChatPageRequest` for it with an empty page at its start, and drops anyone else's edits of it.
- A new line is taken only while the other is in the group; a member who left keeps their lines and the chat can still be read, but takes no more. The apps keep listing it under the group's chats, so it can be read and its unread lines cleared, and in place of the composer say 〇〇はグループを抜けました. A line counts as unread for the other member alone.
- Its lines and read marks share the group's change log with everything else, so a device's cursor still covers all it may see; the other members simply never receive those changes.

- A member writes through their group socket, from their outbox like a shift edit: `ChatEdits` of `ChatSend` (a new line at the end, its `content` a `ChatSendContent` of exactly one kind, as the line will be, spec/chat.md What a line is: words; 1 to `SHARED_DAYS_MAX` days as `YYYY-MM-DD`, each once and in order, drawn with everyone's shifts, spec/chat.md Long messages and shared days; photos; or a poll. A send of none, or of a kind the group does not know, is refused as not fitting), `ChatChange` (new words for one of their own lines, 編集), `ChatUnsend` (one of their own lines taken back, 送信取消), `ChatRecall` (one of their own lines taken back by its send's `op_id`, for a line taken back while it waited after it went out, whose `Acked` may be lost: the group takes it back as `ChatUnsend` does when it has the line, and else keeps the `op_id` (`chat_recalls`) and drops that send should it come after all, as from a socket that died with it on the way, for `chatRules.unsentAfterMs` from when it took the recall (the longest a device sends a line by itself, far past any send still on its way) and only while the member stays in the group; a send of photos is recalled with its photos (`photo_ids`), which go with the line, or at once when the group has no line, as none will ever carry them, and a recall naming more than `chatRules.photosPerSend` deletes none, as no send holds that many; someone else's line, or one taken back already, is left as it is), `ChatReact` (their reaction on any line put on or taken off; the line moves to a new cursor carrying all its reactions, spec/chat.md Reactions), `ChatPin` (any line pinned for everyone or its pin taken off; a line's `pinned_order` is the cursor it was last pinned at, the latest the greatest; a pin past `chatRules.maxPins` takes the oldest's off at the next cursor, and taking a line back takes its pin off, as `spec/vectors/chat.json` pins has it) `ChatVote` (they can come on one of a poll's days, 行ける, or take it back, until it is settled) and `ChatDecide` (a poll settled on one of its days by its writer, or by anyone once they left; it pins the poll as the vectors' `settle` step does, spec/chat.md Polls), and `ChatRead` (their read mark). A line of photos is a `ChatSend` of photos (`ChatSendContent.photos`, a `ChatAlbum`: 1 to `chatRules.photosPerSend` `ChatPhoto`s, each its id and size, each once; spec/chat.md, Albums), sent only after every one of them is uploaded: `PUT /v1/groups/{group_id}/photos/{id}` with the JPEG (members only, at most `chatRules.photoMaxBytes`), which the Group DO notes as the uploader's, so a line can carry only its sender's own photos, each once; members read it with `GET` on the same path. A group's photo never changes once stored: the Group DO notes every one before it is stored (`group_photos`, by who put it there and what holds it: not sent, sent, taken back (its line taken back, deleted from storage by the group's sweep, its note kept for good so its id is never stored or sent again, as devices keep a photo by its id), or shown as a face or the mark; a note goes only once storage has deleted its photo, so storage never keeps one the group has no note of, spec/admin.md What keeps the bucket clean), and storage takes it only where nothing is stored yet (R2's conditional put, `onlyIf: { etagDoesNotMatch: "*" }`, which stores nothing and answers null when the key holds an object). An upload is answered 204 for a new id, and for the uploader's own photo uploaded before, sent or not (the outbox uploading it again before it sends its line again, as after an `Acked` lost), which stores nothing again and keeps the bytes first stored, so a line's photo is never replaced after it went, nor a report's context with it; it is 409 for someone else's photo, for one taken back, and for the faces and the mark the group shows, which the server copies in and notes as shown before it stores them, so no upload under their ids takes them. Before each time it sends a line, the outbox uploads those of its photos it has not seen go up within half of `chatRules.unsentAfterMs`, timed from when each upload began (well within the time the group keeps them, whatever the device's corrected clock is off by), and drops a line one of whose photos is gone or refused. Taking the line back deletes its photos from storage, by the sweep, set for at once. A photo uploaded and not sent is deleted (its note marked as being deleted first, in the transaction that finds it, as other requests come in while storage deletes it; then storage; then the note, if still so marked: meanwhile no line can carry it, its uploader's upload of it is answered 503 to try again, which the outbox does as after any failure, and finds the id free, and a copy noted again stays so marked until the sweep has copied it in anew, once storage has deleted it, and is then shown again, a sweep that fails part way being finished by the next; so either comes out as if it came after the sweep) once its uploader has uploaded nothing to the group for `chatRules.unsentAfterMs` (`group_photos.uploaded_at`, which each upload sets on all of the uploader's photos not sent), as is a copy of someone's photo noted that long ago that neither the mark nor anyone in the group names (its group never made, or its push failed); one sent, or a face or the mark the group shows, is never one, so the sweep never touches them: every send comes within that time of an upload of its photos, so this only lets go of uploads whose line will never come, a line's later photos keeping its earlier ones while they go up. The Group DO's alarm does it, set by each upload for when that time is up and set again for the next, so the last upload of a group that goes quiet goes too. A poll is a `ChatSend` of a poll (`ChatSendContent.poll`) of 2 days at least, in the group chat only; its line's `ChatPoll` carries each day's voters in the order they said so (`votes`) and the settled day (`decided`), and taking it back takes them off. Lines need no clock: the group orders them as it takes them, giving each new line the chat's next `seq`. Each edit has an `op_id`; a send taken twice is one line, and the line carries its `op_id`, so the sending device swaps the line it showed while waiting for the group's. As on the User DO socket, the changes go to everyone with the group open first, then `Acked` to the sender.
- A change or unsend of someone else's line, or of an unsent one, a change of a line of days (it has no words), or words that do not fit (1 to `textLimits.chatMessage` characters, not blank) are refused: the line comes back to the sender as the group holds it, and the edit is acknowledged. A send the group does not take is named in its `Acked` too, under `refused` with why, and the sending device keeps its line as not sent (spec/chat.md, Lines on their way): `REASON_DOES_NOT_FIT` for what does not fit (its words or days, a photo not the sender's own one not sent, an `op_id` that is no id, a chat the sender cannot read, or what the place does not take), which an app never sends, so it tells of a bug; `REASON_NOT_IN_GROUP` for a one-to-one chat whose other member is no longer in the group. Only sends are refused so. A send taken before (its `op_id` again) or taken back before it came is acknowledged as taken, and so is a send to someone who blocked the sender, written as any other (Reports and blocks), so no answer tells a block. Taking a line of days back takes its days too.
- Catching up, a device gets every read mark and every change to a line written by its cursor, but of the lines written since, only each chat's latest `chatRules.pageSize` and every pinned line, for the pins over the chat; earlier ones it asks for as pages (`ChatPageRequest` with `before_seq`, 0 for the latest, answered by `ChatPage`: up to `chatRules.pageSize` lines before it, oldest first, and `at_start` once they reach the first). So a device away for long, or new, is not sent a chat's whole history.
- A chat's photos alone come the same way, without the lines between them, for the photo opened large to page through them all and the chat's list of them (写真, spec/chat.md, Photos): `ChatPhotosRequest` with a `seq` and whether `after` it, answered by `ChatPhotos` with the photos of the lines nearest it on that side, as many whole lines as `chatRules.photoPageSize` photos hold and at least one, oldest first, an entry a photo with its line's seq, writer and time, and how many of the chat's photos come before them (`offset`) and in all (`total`), as the group's change log stood when it answered (`cursor`, its head then). Those counted are the ones the reader sees: not a line taken back or hidden from them, nor in the place's own chat a member's they blocked (`spec/vectors/chat-photos.json`, seen and page). Anyone else's one-to-one chat answers with none. Only the group counts them: the device never adds to or takes from what it said. It follows the chat's photos on its own lines meanwhile, as pages come only when asked, and when they change (a photo come, taken back or hidden, or a block taken), it takes out those it no longer sees, forgets where its photos are among all of them, and asks again around the one shown; a page whose `cursor` is older than the group's cursor the device had read with that change was counted before it and is dropped (`spec/vectors/chat-photos.json`, run). The answers and the lines come on the same socket in the group's order, and the device's lines are only what the group sent, so a page asked after a change counts it.
- A reply's quote reads as the line it answers (spec/chat.md, Replies), however far back that is, so the group sends that line along wherever it sends a reply: catching up, with each reply it sends, the line it answers unless it is among them, as a change at the line's own cursor (which may be older than the device's: a device's cursor never moves back); a new reply to a line before the chat's latest page (which every device with the group open holds), to everyone with the group open after that line, likewise; and a `ChatPage`, in `quoted`, the lines its replies answer from before the page. The device keeps them with the chat's other lines, and changes to them reach it as to any line it holds.

The client caches messages by `seq` and records which contiguous ranges it holds (`cached_ranges(min_seq, max_seq)`).

- Scrolling past the edge of a cached range fetches the previous page and extends or merges ranges.
- A pinned or quoted line held outside them shows only as its pin or quote until a range reaches it.
- Edits and deletions arrive through the change log and update cached messages; changes to uncached messages are ignored.
- After a reset, the client loads the latest page as a new range. The gap to older ranges is filled when the user scrolls to it.

### Read states

A thread is a group's shared chat or a direct chat between two members. Each (user, thread) pair has one watermark, `last_read_seq`: everything up to it counts as read. Chat is read in order, so per-message receipts are not needed.

- The Group DO stores `read_marks(user_id, thread_id, last_read_seq)` and only moves a watermark forward (`max`), never past the chat's last line. Updates from several devices, out of order or repeated, converge without conflict resolution. No mark reads as nothing read.
- Watermark changes go through the change log, so members see read markers update live. A message counts as read by every member whose watermark is at or past its `seq`.
- Unread count for a thread: messages with `seq > last_read_seq` not authored by the user.
- A member who joins starts at the thread's current head, so history before joining is not unread: joining moves their mark there.

Clients advance the watermark to the newest message shown on screen, batching updates while the user scrolls. The update goes through the outbox like a shift edit; since the server applies `max`, redelivery is harmless.

### Unread summary

Tab and app icon badges need unread counts across every group, without a socket to each Group DO. When a line is sent, the Group DO counts each other member's unread lines in that thread, and how many of them mention that member, and gives both to their User DO (`setUnread`), with the group's cursor they were counted at; a read does the same for the reader. The same call carries the line's notification (Push).

- The User DO keeps one `unread_counts` row per group and thread, in its own log like the memberships, and sends each change to the user's devices on their socket as an `UnreadCount`. Counts can arrive out of order, so one counted at an older group cursor than the row's changes nothing. A failed call is put right by the member's next count.
- Leaving a group deletes its rows, in the transaction that marks the membership left at a newer cursor, so the head never goes back; devices drop a group's counts as they hear of the leaving, and joining again starts at the chats' end.
- A device shows the group's count, except in a chat where a read of its own still waits to be sent: there it counts the lines it holds past that read, so reading clears the badge at once. A group's icon adds up its chats' counts as what notifies, from the count and the mentions as the chat is on or off (Chat notifications), the グループ tab all groups' (spec/chat.md, Unread lines).
- Reading on one device clears the badge on the user's other devices through the User DO.
- The APNs `badge` is the User DO's total of these counts as what notifies, sent with each notification (Push); the app also sets it from its own counts as lines are read.

## Push

- Each launch, and each time it goes on as another user (Sockets), a device with notifications allowed sends its token (`UserService.RegisterPushToken`) and the service it is of (`platform`): an iPhone its APNs token (`sandbox` from a development build), an Android phone its FCM registration token, and again whenever FCM gives it a new one. D1 keeps it (`push_tokens`, with its platform) with the session it came under, not in the User DO: a token is one row, so it is one session's, and one user's, at a time, and sending it under another session moves it there, so a device never hears two accounts at once. A session's tokens go with its row as it ends (signing out) or its user is deleted (deleting the account, or the side not kept when switching to an account in use), by the foreign key in the same database, so no call that failed between the server's parts can leave a signed-out device hearing the user before. The User DO reads its user's tokens from D1, through their sessions, as it sends, each through its platform's service, and drops one the service says is gone (below).
- When a line is sent, the Group DO words a notification for each other member who may read the chat and has not blocked the writer, and gives it to their User DO with their new unread count and whether the line mentions them (`setUnread`). The User DO sends it to each of their devices when it notifies (Chat notifications), its badge the user's total of unread lines as what notifies.
- The server sends a localization key and its arguments (APNs `title-loc-key`/`loc-key` with their args), never words it has put together, so the app words them from its own strings: the title is the group's name (`CHAT_TITLE`), or the writer's in a one-to-one chat; the body is `CHAT_GROUP_{TEXT,PHOTO,DAYS,POLL}` with the writer's name first, or `CHAT_{…}` in a one-to-one chat. Words are sent with mentions as @name, cut at 200 characters. A character may take many bytes, so the whole payload is then held to the 4096 bytes APNs takes and FCM takes as data, by construction: measured as each service words it, the body's arguments are cut from the last, a message's own words, then the title's, each between characters and no more than it must be (`src/alert-size.ts`). The payload carries `groupId` and `threadId`, which a tap opens, and `thread-id` stacks a chat's notifications together.
- To an Android phone the same goes as an FCM message of data alone, at high priority, which the app words and shows itself as iOS's Notification Service Extension does (below): `data.alert`, the JSON of the notification as the server words it (`title` and `body`, each `{key, args}`; `groupId`; `threadId`; `line`, `{authorId, seq}`, for a chat line; `badge`; `recipientId`). The app drops one whose recipient is not the user whose data the device holds, as Android needs no entitlement to show nothing; it knows them from its database, without the network, as FCM may wake it in the background.
- On Android a chat's lines are one notification, the conversation's (MessagingStyle), as Android's messaging apps show them: each line a message from its writer, named as the group shows them (else as the server words them), and the group's chat titled with the group's name, its words worded as a one-to-one chat's (`CHAT_{…}`). Each line's `seq` is kept in the notification's own extras, in its messages' order (Android keeps no extras of a message), for a withdrawal to take the lines read out of it (spec/vectors/chat.json, withdrawn), and the notification away once none is left. The app keeps the notification it last showed for each chat as well, until it is tapped, dismissed or taken back, as the system lists one posted only after a moment and a line coming at once must still find the one before. An answer from Pochical's people is a plain notification of the latest, titled 作っている人とチャット, keeping every answer's `seq` it stands for, and goes once all of them are read. `badge` is not shown: Android's launchers count notifications themselves. The notifications go as the device lets go of the user, as it starts erasing (signing out, deleting the account, はじめから使う, offline too) or goes on as another user, not while a change waits on the server. The channels are チャット and 作っている人とチャット, which the person quiets or turns off in the system's settings. A tap opens the chat; until Android has the chats, a group's opens its place in グループ and Pochical's people's opens the app. Android 13's permission is asked from 設定 › 通知 › チャット's card (/design's PermissionCard), the system's settings opened once it was turned down for good. The device sends its FCM token, as it comes and as FCM gives it anew, under each user it goes on as while notifications are allowed; one the server did not take goes again as the app comes to the front. The Firebase project (`pochical-app`, the Google Cloud project of the Web OAuth client) is read from `apps/android/app/google-services.json`, which holds no secret and is checked in.
- Every notification's payload names whom it is for, `recipientId`, and asks for the app's Notification Service Extension (`mutable-content`), which shows nothing of one whose recipient is not the user the device is signed in as (the id the app keeps in the App Group): neither its writer nor its words, only 別のアカウントへの通知です, as dropping it altogether takes Apple's filtering entitlement (`com.apple.developer.usernotifications.filtering`): a token can still reach the device for a moment after it went on as someone else, before the server hears of it.
- A chat line's payload also names the line, `authorId` and `seq`, and the Notification Service Extension reads the writer and the group from the database the app keeps in the App Group and makes it a Communication Notification (`INSendMessageIntent`, its conversation `groupId/threadId`; a group chat's body worded again from `CHAT_{…}` and the arguments after the writer's name, which the system shows); its `category` `CHAT_LINE` is the one with 返信 (spec/chat.md, Notifications).
- Taking notifications back: the User DO keeps, per chat, the lines it notified the user's devices of and has not yet told them to take back (`chat_notified`, from `first_seq` to `last_seq`). The Group DO gives a reader's new read mark with their count (`setUnread`); when it reaches `first_seq`, the User DO sends each device a background push (`apns-push-type: background`, priority 5, `{"aps": {"content-available": 1}, "withdraw": {"groupId", "threadId", "readTo"}}`; to an Android phone an FCM message at normal priority whose `data.withdraw` is the JSON of `{groupId, threadId, readTo}`), which shows nothing, and keeps the lines after it, if any, for a later read. So a read sends at most one such push, and only when something it read was notified. iOS may hold back or drop background pushes, and does not wake an app the user closed, so a device also takes back what its counts show read (spec/chat.md, Notifications). Leaving a group drops its rows.
- Sent from the Worker straight to APNs over HTTP/2 with a token key (`APNS_KEY_ID`, `APNS_TEAM_ID`, the `.p8` as the `APNS_KEY` secret). Apple asks for a new JWT no more than once every 20 minutes on a connection and no less than once an hour, and takes one token from many servers; each isolate signs its own and reuses it for 50 minutes, pushes sent at once sharing the one being signed. A local `wrangler dev` cannot reach APNs, so it sends nothing to iPhones.
- Sent to Android phones through FCM's HTTP v1 API (`projects/{project_id}/messages:send`) with an OAuth 2 access token, which Google gives for a JWT signed with the Firebase project's service account key (RS256, scope `firebase.messaging`, the account's JSON key as the `FCM_SERVICE_ACCOUNT` secret). Each isolate keeps the token Google gave until a minute before it expires, pushes sent at once sharing the one being asked for, and asks again once FCM refuses it (401). Its asking is bounded (10 seconds), as every push of the isolate waits on it. Both JWTs are signed with jose (`src/jwt.ts`).
- No push fails unseen. Each one not sent is logged (Workers Logs, `push`: `sent` `gone` or `failed`, the HTTP status, APNs' `reason` or FCM's error code, or what kept it from reaching the service with the device's token left out, the push's kind, `alert` or `withdrawal`, the platform, sandbox), and every push is counted in Analytics Engine (`PUSH_OUTCOMES`, dataset `pochical_push_outcomes`). A token APNs says is dead (410 Unregistered, or 400 BadDeviceToken or DeviceTokenNotForTopic) is deleted from `push_tokens`, as is one FCM says is (its FcmError's code UNREGISTERED, SENDER_ID_MISMATCH for a token of another Firebase project, or INVALID_ARGUMENT with a BadRequest naming `message.token`); any other refusal keeps it, INVALID_ARGUMENT of the message's own fields among them, so a payload FCM refuses never costs a device its token. A run of TooManyProviderTokenUpdates (429) there would mean isolates share APNs connections, and the token would then move to one place all of them read.
- A notification is not shown while its chat is open on the device.

## Chat notifications

- `UserService.SetChatMuted` turns a chat's notifications off or on again, for the group's chat or a one-to-one chat of the user's (NOT_FOUND otherwise). The User DO keeps it (`chat_mutes`, one row a chat, kept when turned on again so devices catching up hear of it) and sends it to their devices as a `ChatMute` change.
- `UserService.SetChatNotifications` sets メンションはいつも通知 for the account (`chat_settings`), sent as a `ChatNotifications` change; before the user sets it none is sent, and it is on.
- The groups never hear of either: the User DO decides with them. A new line notifies in a chat that is on, or in one turned off when it mentions the user while メンションはいつも通知 is on; the counts follow the same rule (spec/chat.md, Notifications; spec/vectors/unread.json).

## Reports and blocks

- `ChatService.Report` keeps a report in D1 (`reports`): the reason, who reported whom, and what they saw, the line and the three on each side as the Group DO holds them, or the member's name. Only a member reports, only someone else, and only a line they may read. Nobody in the group is told.
- `UserService.SetBlocked` keeps the block in the user's User DO (`blocks`, one row a person, kept when unblocked so devices catching up hear of it) and sends it to their devices as a `Block` change. The User DO tells each of the user's groups (`member_blocks`) all of the user's blocks, before answering, so a group that missed one is put right by the next, and a group they join hears them too.
- A one-to-one chat's line from someone the other member had blocked when it was sent is kept with `hidden_from` and goes to that member with the hidden kind in place of its content (spec/chat.md, What a line is), so their device keeps its place and shows nothing; it never counts as unread for them. Group chat lines go to everyone as they are, and the blocker's device folds them.

## Ephemeral state

Presence and typing describe the present moment only. They are never written to the change log, SQLite or the outbox, and nothing is replayed after a reconnect. The Group DO relays them as their own `ServerFrame` kinds to the sockets that need them.

### Presence

Presence means "has this thread open on screen", not "online in the app": mobile OSes stop sockets soon after the app leaves the foreground.

- No heartbeats. The Group DO lists open sockets with `ctx.getWebSockets()`, which works across hibernation, and each socket's attachment records its user and open thread.
- On connect, close and thread switch, the Group DO sends the change to other sockets in the thread.
- A user with several devices is present while any of their sockets is.

### Typing

- While composing, the client sends a typing frame at most every `chatRules.typingSendMs` (`design/src/chat.ts`), and a stop frame when it sends the message or the field becomes empty.
- Receivers show the indicator for `chatRules.typingShowMs` unless it is refreshed, so a lost stop frame cannot leave it stuck.
- The frames are `Typing` (thread, on) on the group socket. The Group DO relays each, with the writer's id it sets itself, to the sockets of the other users who may read that thread (both members alone for a one-to-one chat), never to the writer's own devices, and keeps nothing. The app also stops when the chat closes.

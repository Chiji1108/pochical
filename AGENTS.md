# Repository Guide

Pochical is a monorepo: native SwiftUI (`apps/ios`) and Jetpack Compose (`apps/android`) apps, a Cloudflare Workers backend (`apps/server`), the web site, Astro on Workers (`apps/web`), the design documents and the prototype's demo (`apps/design`) and the prototype to keep on a phone (`apps/try`), and the admin site (`apps/admin`). The web apps' shared code sits in `packages/`: the prototype's screens, which the site's top page shows too, and the page around the phones that `apps/design` and `apps/try` show them on (`@pochical/prototype`), the Panda CSS config and the `css()` it writes (`@pochical/styled-system`), and the JSX runtime that breaks Japanese between phrases, with the same breaks for HTML that is not JSX (`@pochical/jsx`).

## Where things live

- Tool versions and tasks are in `mise.toml` (`mise run gen`, `mise run server:test`, `mise run ios:test`, ...).
- The TypeScript workspaces are pnpm's (`pnpm-workspace.yaml`, with the versions several of them share in its `catalog`). pnpm's version is in `packageManager` in `package.json` alone: mise reads it (`idiomatic_version_file_enable_tools` in `mise.toml`), and so does Workers Builds. Scripts written in TypeScript run on Node through tsx (`pnpm exec tsx <file>`), and the tests on vitest.
- Xcode's version is in `.xcode-version` alone, the one the `xcode-27` runner of GitHub Actions selects for the `ios` job of `ci.yml` and for the iOS release; raise it in a PR once the runner image has the new Xcode.
- Node's version is in `.node-version` alone: mise reads it (`idiomatic_version_file_enable_tools` in `mise.toml`), and so does Workers Builds.
- Generated files are never edited by hand; change their source and regenerate:
  - Wire types: `proto/` → `mise run gen` (into `apps/server/src/gen`, `apps/web/src/gen`, `apps/ios/Packages/PochicalProto/Sources`, `apps/android/proto/src/main`). A change to `Change` or anything it holds fails `mise run sync:check` until the iOS `Sync.schema` and Android's `SYNC_SCHEMA` (`apps/android/kit`) are raised and `mise run sync:check -- --write` records them.
  - Numbers every platform shares (limits, the chat's, days', invites', sockets', widgets'), design tokens, mark icons and holidays: `design/` → `mise run gen` (into `spec/design-tokens.json`, `apps/ios/Packages/PochicalDesign/Sources`, `apps/android/design/src/main`). Specs and code refer to them by name, never by value.
  - Icons: the marks' paths from Phosphor via `pnpm --dir design icon:marks`; the iOS app icons and the widgets' `PeekingPoodle` via `pnpm --dir packages/prototype icon:ios`, and Android's launcher icon (its `mipmap` layers and the background color) and the Play listing's 512-pixel icon (`apps/android/app/src/main/ic_launcher-playstore.png`) via `icon:android`, both painting with `scripts/app-icon.ts` as the site icon's `icon:site` does.
  - Workers' types: each Worker's `wrangler.jsonc` and the wrangler in `pnpm-lock.yaml`, with the workerd it pins → `mise run gen:worker-types`, which runs every workspace's `cf-typegen` (into `worker-configuration.d.ts` in `apps/server`, `apps/admin` and `apps/web`). A wrangler bump regenerates them too; CI runs `mise run worker-types:check`. A Worker with a `cf-typegen` and no secrets still declares `"secrets": { "required": [] }`, so its types never come from a computer's `.dev.vars` or `.env`.
  - SQL schemas are Drizzle and their migrations are generated, never written: D1 `apps/server/src/db/schema.ts` (`mise run db:generate -- --name <what>`; better-auth's tables via `mise run auth:schema` first), the Group DO `group-do-schema.ts` (`mise run group-do:generate`), the User DO `user-do-schema.ts` (`mise run user-do:generate`). CI runs `mise run db:check`.
- Behavior shared across platforms is specified in `spec/`. Logic every platform writes again is pinned by `spec/vectors/*.json`, read by `packages/prototype/tests/vectors.test.ts`, `apps/server/test/vectors.test.ts`, `packages/jsx/tests/phrases.test.tsx` (the phrases), PochicalKit's tests and Android's `:kit` tests; a new case goes in the JSON, not in one platform's test. Components are not generated: each platform builds its own, with /design as the reference.
- iOS: `apps/ios/Pochical/Pochical.xcodeproj` (app and widgets, App Group `group.app.pochical`). Hand-written shared code goes in `apps/ios/Packages/PochicalKit` (`mise run ios:test`). `xcodebuild` needs `-skipMacroValidation`. A Debug build in the simulator talks to `mise run server` at the build setting `POCHICAL_DEV_SERVER`, `http://localhost:8787` by default. To run your own server beside others, pick a free port and use it on both sides: `mise run server -- --port 8790`, `xcodebuild ... POCHICAL_DEV_SERVER=http://localhost:8790`, and `POCHICAL_DEV_SERVER=http://localhost:8790` in the environment of tools/chat-try, tools/api-try (`--local`) and the UI test runs (tools/ios-ui). Release builds and Debug builds on a device always use `https://api.pochical.app`. The server needs `apps/server/.dev.vars` (`BETTER_AUTH_SECRET`, any random value; the task sets `BETTER_AUTH_URL` from the port; the `SLACK_*` secrets only to post to Slack from this computer, and wrangler warns while they are absent) and the D1 migrations applied locally (`pnpm exec wrangler d1 migrations apply pochical --local` in `apps/server`).
- Android: the Gradle project is `apps/android` (Kotlin DSL, versions in `gradle/libs.versions.toml`): `:app` (the Compose app, `app.pochical`), `:kit` (what PochicalKit is on iOS, hand-written and below the screens: the clocks, the database and sync, its tests reading `spec/vectors` from the repository), `:design` (the code generated from `design/`) and `:proto` (the code generated from `proto/`, a plain Kotlin library). `mise run android:build` builds the debug APK, `mise run android:release` the minified release bundle (R8's keep rules in `app/proguard-rules.pro`, each one a runtime failure without it) and `mise run android:test` runs the unit tests and lint; both need the Android SDK in `ANDROID_HOME` (Android Studio's, or `local.properties`'s `sdk.dir`) with the `compileSdk` platform, and the JDK from `mise.toml`. A debug build in the emulator talks to `mise run server` at `http://10.0.2.2:8787`, as the iOS simulator's does at localhost; Android 17 counts it as the local network, so grant it once with `adb shell pm grant app.pochical android.permission.ACCESS_LOCAL_NETWORK`. Launched with the extra `sample` (`adb shell am start -S -n app.pochical/.MainActivity --ez sample true`), a debug build with no patterns puts in the sample month as an iOS Debug build does with `-sample`; it lives in `app/src/debug`, so a release build has none. `-PpochicalServer=http://10.0.2.2:<port>` points the debug build and the instrumented tests at a server on another port, beside another checkout's. `./gradlew :kit:connectedDebugAndroidTest` syncs two devices of one user through that server, turns the emulator's Wi-Fi off and on again to see the user's socket move to the new default network at once, and keeps a session in Block Store, so it needs an emulator image with Google Play; CI does not run it. Googleで続ける asks for a token for the server's Web client (the first of `GOOGLE_CLIENT_IDS` in `apps/server/wrangler.jsonc`, which the build reads), and Google gives one only to an app it knows by an Android OAuth client in that client's Google Cloud project, for `app.pochical` and the signing certificate's SHA-1: one for each computer's debug key (`./gradlew :app:signingReport`), one for the upload key and one for Play's app signing key. Appleで続ける opens Apple's web page in an Auth Tab by way of the server's `/apple/authorize`, for the Services ID (`APPLE_SERVICES_ID`, the same file), and comes back through the server's `/apple/callback` to `pochical://apple-sign-in` (spec/sync-protocol.md, Signing in); Apple returns only to a callback registered for the Services ID, so a local server's sign-in stops at Apple's page, and its handoff is tested by posting Apple's form to `/apple/callback` in its place.
- Admin (spec/admin.md): `apps/admin` is React Router 8 in framework mode, on Workers through the Cloudflare Vite plugin. It reaches the server only through `AdminEntrypoint` (`apps/server/src/admin-entrypoint.ts`), bound as `SERVER`, whose types come from the server's source (`mise run gen:worker-types`); each route's `./+types` come from `react-router typegen`, which `pnpm install` (prepare) and its `typecheck` run. `mise run admin` serves it in workerd at `http://localhost:3100`.
- Web: `apps/web`'s pages are `.astro` files in `src/pages`, prerendered unless one sets `prerender = false` (the invite page and its images, which ask the server through the `SERVER` binding); React runs only in islands a page marks `client:*` (the top page's phones and skies, `src/components/lp-screens.tsx`). Its middleware breaks the pages' Japanese and gives the on-request pages their headers. `pnpm run web` serves it at `http://localhost:3000`, beside `mise run server` for the invite page. The repo's `tsc` is TypeScript 7, but `apps/web` declares TypeScript 6 (`@typescript/typescript6` under the name `typescript`) for `astro check`, which needs the TypeScript JS API that 7.0 does not ship ([announcement](https://devblogs.microsoft.com/typescript/announcing-typescript-7-0/)); its `tsconfig.tools.json` is still checked by the root `tsc`. It moves to 7 once TypeScript 7.1 and Astro's `@astrojs/ts-content-mapper` are stable ([withastro/astro#17268](https://github.com/withastro/astro/issues/17268)).
- Design and try: two Workers built from `@pochical/prototype`, with no bindings. `apps/design` is the design documents and the tools beside them at `design.pochical.app`, open to everyone and kept out of search (`public/robots.txt` and the root route's `noindex`), so a search for Pochical finds `pochical.app` rather than them: Fumadocs on TanStack Start, its routes in `src/routes` (`src/routeTree.gen.ts` comes from TanStack Start's router plugin). Each document is an MDX file of `content/` (the sidebar's order and groups in its `meta.json`) showing pieces from `src/components`, with Tailwind CSS drawing Fumadocs UI's chrome and Panda CSS the pieces, in the layer order `src/styles.css` sets. The tools under `src/routes/_tool`, /demo and `/_render/share-image` (which `pnpm --dir apps/design image:share` photographs), are full pages outside Fumadocs UI's layout, drawn in the browser alone. `apps/try` is the installable app at `try.pochical.app`, open to everyone and kept out of search until release: a Vite SPA with no router, static assets with no Worker code and every unknown path answered with `index.html`, whose head takes the design tokens and launch images through `head.ts`. The site's top page and design link to try by `@pochical/prototype`'s `lib/try-url.ts`, Vite's `import.meta.env.DEV` choosing try's dev server under a dev server and `try.pochical.app` in every build, previews included. Locally, `mise run design` and `mise run try` serve `http://localhost:3200` and `3202`, try's port set once in `lib/try-port.ts` for its Vite config and `lib/try-url.ts`; `mise run design:layout` and `mise run design:demo-layout` measure the documents' and /demo's screens.

## How to build

- Plumbing comes from a maintained library before it is hand-written (check license, activity, fit; name it in the PR). MIT/Apache/BSD/ISC may be added; GPL/AGPL code (Signal, Telegram) is read for ideas only.
- What does the same thing in two places is one piece, not two copies: build on the existing one and make the difference an input. A change to one carries to the others in the same PR.
- Keep the code simple: that is why a root cause is fixed the way the platform or library intends, rather than patched over with timing hacks, sleeps or special cases that each need explaining. When the root cause is the platform's own bug, the simplest correct code wins: report it upstream, and keep the smallest workaround in one place, naming the upstream issue and the GitHub issue that removes it, rather than redesigning around it. A review finding whose fix would add more complexity than the risk it removes is answered instead, and filed as a GitHub issue if it is worth tracking; so is one whose conventional answer is to leave it.
- The apps are unreleased: change stored shapes directly, with no hand-written data migration, fallback or compatibility code for old saved data. On iOS that means editing a table where it is first created, never adding a migration step: any schema change erases the device's database in every build, TestFlight included, and it syncs again from the server. Likewise a kept session the app cannot read (the Keychain's; Android's in Block Store, `SessionStore`) is no session: it signs in anew (spec/sync-protocol.md, Signing in). Server SQL schemas still get their generated Drizzle migrations, as above. Android's stored data follows the same rule until release: any shape change raises `AppDatabase.VERSION` (`apps/android/kit`), whose destructive migration erases the database, and `mise run android:db:check`, after a build, fails when Room's exported schema of a version was rewritten instead. At release, turn iOS's `erasesOnShapeChange` off, for the database and the kept session alike, and Android's equivalent with it, and append migration steps from then on.
- Update `spec/` (and its vectors) in the same PR as any behavior change; fix spec drift when you see it.
- UI follows the platform first (iOS 26 / Material 3 conventions, system controls and buttons sized by the OS). When /design and a platform differ, judge on the merits and say which side changes. Motion the OS provides is left to the OS.
- TypeScript (`apps/web`, `apps/design`, `apps/try`, `apps/server`, `apps/admin`, `packages/`) is checked by Ultracite: run `pnpm exec ultracite fix`, and avoid `as` assertions other than `as const`. oxlint reads `.astro` files' frontmatter and scripts too, and oxfmt formats `.astro` by Astro's JSX whitespace rules, where a line break between text and a tag renders nothing. Astro's compiler does not apply those rules to text placed directly inside a component, such as `<Link>…</Link>`, and in Japanese a line break left there renders as a space, so a component that takes text trims its slot, as `Link` does.

## How to ship

- main takes pull requests only; name the GitHub issue in the PR, with `Closes #n` when the PR finishes it, and file skipped findings or follow-ups as GitHub issues. An issue in code, comments or `spec/` is named by its `#n`; the older `POC-n` name closed Linear issues, whose PRs `git blame` finds.
- Before merging: run `/code-review` and address it (answering a finding instead of changing the code counts, as in How to build), CI must be green, and review threads resolved. Never merge on red.
  - Merge main into the branch first when a related PR landed, so the two are checked together: one that touches the same files or behavior, the toolchain or dependencies (`mise.toml`, `packageManager`, `pnpm-workspace.yaml`, `pnpm-lock.yaml`, a Renovate update), or the sources of generated code the branch builds on (`proto/`, `design/`), landed since the checks last ran.
  - A PR that landed and is not related needs no merge: main's ruleset does not require the branch to be up to date, and the GitHub Actions checks run on the branch merged with main (`pull/<n>/merge`) as main stood when they ran. If a related PR lands while auto-merge waits, cancel it, merge main, and queue it again.
- The iOS checks are the `ios` job of `ci.yml`, on GitHub Actions like the others: a PR that leaves its paths alone skips it, which the ruleset counts as passing.
- Auto-merge (`gh pr merge --auto --match-head-commit <sha>`) may be used when `/code-review` is addressed and Codex's review of that head is clean; the required checks, `ios` among them, then decide when it merges.
- Deploys happen through Cloudflare Workers Builds on merge; never deploy by hand.
- Android releases happen on merge too: `.github/workflows/android-release.yml` builds the release bundle of each push to main that changes the app, signs it with Play's upload key and puts it on Play's internal testing track, from where it is promoted in Play Console. The upload key and the Play service account live only in the repository's secrets (`ANDROID_UPLOAD_KEYSTORE_BASE64`, `ANDROID_UPLOAD_KEYSTORE_PASSWORD`, `PLAY_SERVICE_ACCOUNT_JSON`) and reach Gradle as `pochicalUpload*` properties; without them the workflow is skipped, and a release build on a computer is signed with the debug key, which Play refuses. versionName is the iOS app's `MARKETING_VERSION`, read from the Xcode project, so a version is raised there once for both apps and reaches Android with its next release; versionCode is the workflow's run number, as the build number is in the iOS release, so the workflow keeps its file name and nothing is uploaded by hand after Play's first upload.
- iOS releases happen on merge too: `.github/workflows/ios-release.yml` archives each push to main that changes `apps/ios`, signs it and uploads it to App Store Connect, from where TestFlight hands it out. Its keys live only in the repository's `app-store-connect` environment, which only main may use: the App Store Connect API key with the Admin role (`APP_STORE_CONNECT_API_KEY`, the .p8's text; `APP_STORE_CONNECT_API_KEY_ID`; `APP_STORE_CONNECT_API_ISSUER_ID`), with which Xcode makes the provisioning profiles and signs for the App Store with the team's cloud-managed distribution certificate, and one Apple Development certificate (`APPLE_DEVELOPMENT_CERTIFICATE_P12_BASE64`, `APPLE_DEVELOPMENT_CERTIFICATE_PASSWORD`) that signs the archive, since a certificate Xcode made on a fresh runner would leave its private key behind. The build number (`CURRENT_PROJECT_VERSION`) is the workflow's run number, so the workflow keeps its file name; App Store Connect takes each once per `MARKETING_VERSION`.
- Renovate (`.github/renovate.json5`) opens the dependency PRs on Monday mornings: patches and minors in one PR (a 0.x package's minor, which may break, in its own), each major in its own, and what must move together in its own group at every update (vitest, protobuf and Connect, Kotlin and Metro) or at majors (TypeScript, React). They merge like any other PR, after the manual steps their bodies name, such as `mise run gen`.

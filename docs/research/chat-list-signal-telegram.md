# チャットアプリのベストプラクティス: Signal-iOS と Telegram-iOS から

調べた日: 2026-10-16。対象は `signalapp/Signal-iOS`（main の浅い clone）と `TelegramMessenger/Telegram-iOS`（最終コミット 2026-10-07、サブモジュールなし）。会話画面とその周辺（メディア、送信、既読、操作、テキスト、入力欄、通知、検索、性能、アクセシビリティ）を読み、Pochical の iOS（`apps/ios/Pochical/Pochical/Chat*.swift` ほか）と `spec/chat.md` の今と比べた。

## この文書の扱い（ライセンス）

- Signal は AGPLv3、Telegram は GPLv2。Pochical は両者のコードを写さず、近い言い換えもしない。ここに書くのは**振る舞いと手口の考え方**と、使われている**プラットフォームの API 名**だけ。コードの抜粋はない。
- 「どこにあるか」を後で辿れるよう、ファイルのパスだけ書く（Signal は `Signal/ConversationView/` ほかリポジトリ相対、Telegram は `submodules/` ほかリポジトリ相対。`TU` = `submodules/TelegramUI`）。
- 数値（件数・距離・秒）は、仕組みの説明に必要なものだけ。Pochical の値はこれらに合わせず、`design/src/` で決める。
- 「未確認」「見つからず」は、実際に探して確認できなかったこと。推測を事実として書いていない。
- Pochical に無い機能（音声メッセージ、通話、ステッカー、E2E 暗号化）は扱わない。
- 領域ごとの末尾の「Pochical との比較」は、**採り入れる / 変える / 捨てる / すでによい**の 4 つで判定した。プロダクトの判断が要るものは「要確認」と書いた。この文書は提案で、`spec/` やアプリは変えていない。

## 先に結論: 優先して埋めたい差（上から）

Pochical の iOS チャットは、リンクのプレビュー、ThumbHash、メンション、長文の折りたたみ、大絵文字、ピン、投票などはすでに両者並みかそれ以上。差が大きいのは次の所。

**P1（体験の穴・壊れ方が見える）**

1. **スクロールの根の修正**（領域0）。描画後の補正をやめ、レイアウトの更新の中でアンカー行を保つ。先読みで端末の窓の端に着く前に頼む。**UICollectionView ＋ ChatLayout（MIT）で作ると決まった**（領域0b）。レイアウトの位置保持、自己サイズの補正、挿入のアニメーション、固定する行（日付）はライブラリが持つ。**ライブラリが持たない**もの（キーボード、入力欄、先読みと読み込みの調停、スクロール先の指定、「ここから新着」、↓ボタン、浮かぶ日付、長押しメニューの位置、VoiceOver のフォーカス移動）は自前で作る。P1 の中で最も大きい作業で、他の項目（下書き、再送の UI など）とは独立に進められる。
2. **テキスト送信の失敗と再送**（領域2）。写真だけが「失敗→もう一度送る/削除」を持つ。テキストは失敗せずアウトボックスで待つだけで、待機中の行はコピー以外のメニューが無く、取り消しも捨てることもできない。両者とも失敗した行をタップで「再送/削除」にする。待ちが長いときに何も言わない点も詰める。
3. **下書きの保存**（領域6）。両者とも、チャットごとに本文・返信先・編集中を画面を離れる時とアプリが非アクティブになる時に保存する。Pochical は `@State` のみで、閉じると消える（grep で永続先が見つからず）。小さく作れて効果が大きい。
4. **フォトビューア**（領域1）。両者とも、ピンチ/ダブルタップのズーム、前後の写真へのスワイプ、元のサムネイルから広がる開閉の動き、下に引いて閉じる、を持つ。Pochical は下に引いて閉じる（背景が薄くなる）までで、ズーム・複数枚・元位置からの遷移が無い。
5. **通知を会話の流れに乗せる**（領域7）。両者とも Notification Service Extension を持ち、送信者の顔写真付きの通知（Communication Notifications）、通知からの返信、**他の端末や画面で既読になったら配信済みの通知を取り下げる**。Pochical は `thread-id` とバッジのみ。取り下げが無いと、既読にしたあとも通知が残る。

**P2（やると品質が上がる）**

6. **既読の付け方**（領域3）。両者とも「見えている最後の行まで」をスクロールの途中でも単調に進める。Pochical は最新の行に着いた時だけ（`spec` の "Lines count as read only once they are on the screen at the latest"）。途中までしか読んでいないときに、読んだ分の未読が減らない。**プロダクトの判断**（要確認）。
7. **メディア周りの資源管理**（領域1）。ぼかし用 NSCache に上限が無い、ディスクキャッシュに上限/掃除が無い、先読みが無い（見えてから取得）、取得失敗後にタップで取り直す導線が無い、進捗とキャンセルが無い。Signal は固定件数の LRU とロード/アンロードの可視連動、Telegram は表示サイズに合う最小の表現を選ぶ。
8. **画像のペースト**（領域6）。両者とも入力欄で画像を貼れる。Pochical は見つからず。
9. **スワイプで返信**（領域4）。両者とも持つ。Pochical のメニューには「返信」があるが、スワイプは無い。
10. **性能: テキスト整形のやり直し**（領域5, 9）。`textParts` から行ごとに毎回 AttributedString を作り、折りたたみの判定用に隠し Text も描いている。UICollectionView 化と同時に、行の描画材料をキャッシュする。
11. **アクセシビリティ**（領域10）。Reduce Motion が長押しメニュー・ビューア・浮かぶ日付に及んでいない。Bold Text / Increase Contrast 未対応。写真の説明が一律「写真」。写真の枠など固定 pt の Dynamic Type 追従は未確認。（Signal も会話画面の Reduce Motion は未確認で、ここは先行例が薄い。）

**P3（機会があれば）**

12. **チャット内検索と日付ジャンプ**（領域8）。Signal は全文検索（FTS5）、Telegram はカレンダーで日付へ。Pochical はどちらも無い。シフトのアプリなので、日付ジャンプは領域に合う（要確認）。
13. **複数選択・転送・共有シート**（領域4）。両者とも持つ。Pochical の規模（グループの内輪のチャット）で要るかは要確認。
14. 入力中の複数人まとめ表示、ダブルタップでリアクション/編集、送信時の触覚（領域3, 4, 10）。

**捨ててよい（Pochical には要らない）**: 動画/GIF の自動再生と省電力設定、自動ダウンロードの方針（種別×回線×サイズ）、スポイラー、クラウド下書き同期、独自 UI 一式（Telegram の自作ノード基盤）、予約送信。

## 領域0: リスト構造・スクロール・ページング

（以下は最初に書いた調査。別セッションの UICollectionView 化の計画の下敷きで、この節の見出しは一段下げてある。）

### 要点（先に結論）

1. **両者とも、スクロール中の「見えている行を動かさない」補正を、UIKit のレイアウトの流れの中か、自前の 1 回の更新の中で済ませている。** 描いたあとで offset を直す作りは、どちらにもない。Pochical の今の作り（`KeepsSeenLines` が描画後に頼み直す）が壊れる根はここ。
2. Signal は **UICollectionView（反転しない）＋自前の UICollectionViewLayout**。行の高さは**あらかじめ計算してレイアウトに渡す**（セルの自己サイズ変更に頼らない）。ページが入る前後は `UICollectionViewLayoutInvalidationContext.contentOffsetAdjustment` で補正する。
3. Telegram は UICollectionView **ではない**。旧来の `ListView`（UIScrollView を偽の巨大キャンバスで使い、行を手で動かす）、そして 2026 年に既定になった新しい自前リスト `CoreList`。どちらもリスト全体を 180° 回転して「最新が先頭」にする。補正は自前の 1 回のトランザクションの中でやる。Pochical が真似るのは構造ではなく**考え方**（アンカー行と、その行の画面上の位置を保つ）。
4. 先読みは Signal が「画面 3 つ分」手前、Telegram が「表示が窓の端から 5 行以内」。どちらも**ページは端末にある前提**（Signal は全部端末、Telegram は穴だけ裏でネットワークから埋める）。Pochical の「端末の 50 行を越えるとサーバー待ちで止まる」は、どちらの前提とも違うので、サーバーの先取りは Pochical 固有の設計になる。
5. Signal は**窓の上限（500 行）を持ち、反対側を落とす**。Telegram は**窓が常に約 44 行**で、端に近づくたびに新しい窓へ作り直す。Pochical の「`openMax` 200 行まで広げ、あとは足す」は、どちらよりメモリ側に寛容。

### 1. Signal-iOS

#### 1.1 リストの作り（反転しない UICollectionView）

- 画面は `ConversationViewController`（`ConversationViewController.swift` と `+Scroll`, `+UIScrollView`, `+CVC`, `+OWS` などの拡張に分割）。リストは `ConversationCollectionView`（UICollectionView の小さなサブクラス）と、自前の `ConversationViewLayout`（`UICollectionViewLayout` の直接の子）。
- **反転しない。** 1 セクション、1 行 1 セル、最新が一番下。上端が「読み進む方向」、下端が「最新」。ページングは上端と下端の両方向（窓を持つので、新しい側へも読み進む）。
- 日付ヘッダー、「新着」の区切り、入力中の表示、スレッド冒頭の説明なども**普通の 1 行（セル）**として並ぶ。専用の supplementary view は、「前のメッセージを読み込む」の上端/下端の帯（`LoadMoreMessagesView`）にしか使わない。
- セルは `CVCell`。中身は Signal 独自の「コンポーネントの木」（`CVRootComponent` など）で、UIStackView 風に組む。SwiftUI ではない。
- 理由は読み取れた範囲では、(a) 高さを事前に確定したい、(b) offset の補正を完全に自分で制御したい、(c) 行の種類が多く、行ごとに間隔の規則が違う（同じ送り手の続きは詰める等）。反転を選ばなかった理由は、コードからは断定できない（未確認）。

#### 1.2 見ている行を動かさない（本題）

**行の高さは先に決まっている。** 読み込みの段階（`Loading/CVLoader.swift`, `CVRenderItem.swift`）で、各行の「描画用のデータ」と「測った大きさ」（`CVCellMeasurement`）を組み、レイアウトはその大きさをそのまま使って frame を積み上げる（`ConversationViewLayout.swift` の `buildLayoutInfo` 周り）。セルが自分で大きさを返す `preferredLayoutAttributesFitting` 方式ではない。`CVCell` に `systemLayoutSizeFitting` の上書きはあるが、レイアウトの高さの源ではない。結果、「描いたら高さが変わって上の行がずれる」が構造的に起きにくい。画像や長文の高さが変わるときは、新しい測定結果を持つ新しい描画状態として**ロード全体をやり直して**反映する。

**補正の手口は 2 本立て**（`ConversationViewController+CVC.swift` の `updateWithDiff` 内のコメントが自分で説明している）。

1. **レイアウトの `invalidateLayout(with:)` に `contentOffsetAdjustment` を渡す**（主）。ロードの結果を適用する直前に、(a) 適用前に取っておいた「継続の目印（token）」＝そのときのレイアウト全体と、見えていた行の id の一覧、(b) 適用後のレイアウト、を比べて、アンカー行の y の差を計算し、それを 1 回の無効化で offset の補正にする。`performBatchUpdates` を呼ぶ直前に行う。タイミングが肝（コメントにも "delicate" とある）。
   - アンカーの選び方: 呼び出し側が指定した行があればそれ。なければ「見えていた行のうち、上基準なら一番上、下基準なら一番下」。それも無ければ前後に共通する行のどれか。**メッセージとして安定しない種類の行（日付ヘッダー、新着の区切り、入力中、スレッド冒頭）はアンカーに使わない。**
   - **基準は読み込みの種類で変える**: 「前を読み込む」は上に見えている行を基準（上に積まれるので）、「新しい方を読み込む」「最新へ」「同じ位置で再読込」「周辺を読み込む」は画面の下を基準。
2. **`targetContentOffset(forProposedContentOffset:)`**（補助）。`reloadData` 中、画面サイズの変更（回転）、「最新へスクロール」「アニメーションなしのスクロール指定つき更新」など、1 を使えない場面で使う。ここでは「**最後に知っていた、下端までの距離**」から offset を再現する（`+Scroll.swift` の `lastKnownDistanceFromBottom`）。この値はスクロールのたびに更新される。

どちらもレイアウトの更新の最中（UIKit がレイアウトを確定する前）に効くので、描いたあとに動かす段階がない。

**減速中・ゴムひも中**: 専用の分岐は見つからなかった（未確認）。ただし「前を読み込む」の直後に `isUserScrolling` や `hasScrollingAnimation` を見て、スクロール中はアニメーションを重ねない配慮はある。`scrollViewShouldScrollToTop`（ステータスバータップ）のコメントが示す通り、**アニメーション付きの上端スクロールが、行き過ぎ→戻りの途中で「前を読み込む」を呼び、読み込みがアニメーションの offset を踏む**問題を避けるため、前の続きがあるときは自前の単純なアニメーションに差し替えている。

**読み込みを「着地してよいとき」まで待つ**（`Loading/CVLoadCoordinator.swift`, `loadLandWhenSafe`）。キーボードのアニメーション中、複数選択モードの切替中、長押しメニュー表示中、セルのアニメーション中は、読み込み結果を適用しない。ごく短い間隔（約 1 ミリ秒）で再試行して、終わり次第すぐ着地させる。読み込み要求は優先度つきでまとめられ（`CVLoadRequest.Builder`）、同時に 1 本だけ走る。**リストの更新同士・UI のアニメーションとの競合を、「着地を遅らせる」ことで避けている**のが特徴。

**非アニメーションのバッチ更新**には、UIKit の例外を避ける小技（`performBatchUpdates` を 0 秒の `UIView.animate` で包む）が `ConversationCollectionView.swift` に入っている。UIKit の既知の落とし穴として覚えておく価値がある。

**その他の細工**（`ConversationCollectionView.swift`）: frame/bounds の 0 サイズへの一時的な変更を無視、内容サイズが決まる前の「offset を 0 に戻す」UIKit の内部処理を無視、アニメーション付きの offset 変更の開始をデリゲートに知らせる。

#### 1.3 ページング

- **窓**: 1 度に持つのは最大 500 行（`MessageLoader.swift` の定数）。超えたら**読み込んだ向きと反対側を落とす**（前を読み込んだら新しい側、それ以外は古い側）。落とした側は「まだ読み込める」に戻る。
- **件数**: 最初は「画面の長辺 ÷ 平均 35pt」行（最低 10 行）。前後へのページは**その 2 倍**。周辺（引用・検索）は最初と同じ件数を、中心の前後に半々。**「表示単位」で数える**（連なる同種のシステム行は 1 単位にまとめ、途中で割らない）。
- **先読みの距離**（`+CVC.swift` の `autoLoadMoreIfNecessary`）: 読み込み済みの端から**画面の長辺の 3 倍**以内に入ったら頼む。上端も下端も同じ規則。
- **頼む契機**: スクロールのたびに 0.1 秒のタイマー（RunLoop の common モード。スクロール中も動くため）を張り、発火したときに判定する。スクロール終了・減速終了でも判定する。
- **連打の抑え**: 直前の「前を読み込む」から 2 秒以内なら見送り、1 秒後にもう一度判定する。
- **端末内か通信か**: すべて端末のデータベース。通信の待ちはこの層にはない（メッセージの到着は別の経路）。したがって「読み込み中の表示」は、データベースを読む間の短い間だけ。
- **読み込み中の表示**: リストの先頭/末尾の**固定高さの帯**（`LoadMoreMessagesView`, supplementary header/footer）。「まだ読み込める」あいだは出しっぱなしで、「読み込み中のときだけ」ではない。これで、先読みが追いつかなかったときにも「ここで終わりではない」ことが見える。
- **本当の先頭**: 帯が消え、先頭にスレッド冒頭の行（相手の紹介など）が出る。

#### 1.4 開く位置、新着の区切り

`scrollToInitialPosition`（`+Scroll.swift`）の優先順は次の通り。

1. 外から指定された行（通知・検索・リンク先）→ 上揃えで。
2. 「新着」の区切りの行があればそこ → **上揃え**（区切りが画面の上端）。
3. なければ「前回見えていた最後の行」→ **その行が画面の下端に、前回見えていた割合（画面にかかっていた割合）で**。前回の位置は、スクロールが止まって少しした時点でスレッドごとに保存する（`+LastVisibleSortId.swift`）。
4. それも無ければ最新。ただし、最後の行と入力中の表示があるときは、入力中が見える最下端へ。

開く瞬間の作法（`+CVC.swift` の `updateShouldHideCollectionViewContent`）: **最初の読み込み・安全領域・幅などが揃うまでリストを隠し、揃ったら offset を決めてから見せる**（最大 2 秒で諦めて見せる）。つまり「最新で一度出してから動く」ことをしない。VoiceOver の最初のフォーカスも、区切りか前回の行に置く。

#### 1.5 最新に付いていく、↓ボタン

- 「下端にいるか」は、**更新を適用する前の時点で**（`CVUpdateToken` に取っておく）判定する。許容は 5pt。適用後のレイアウトで判定すると、新しい行の高さのぶん下端ではなくなってしまうため。
- 追従は**挿入された行の種類で決まる**: 自分が送った行 → **スクロール位置に関係なく**アニメーション付きで最下端へ。相手の行・入力中・通話・システム行が挿入され、下端にいて、ユーザーが指でスクロール中でなければ → 同じく最下端へ。上を読んでいるときは動かさない。
- **↓ボタンが出る条件**（`+UIScrollView.swift` の `configureScrollDownButtons`）: 下端までの残りが**画面 1 枚分（見える高さ）を超える**、または最新側にまだ読んでいない行が（画面外や窓の外に）ある。0.2 秒のフェード。録音中は隠す。
- **未読数の出どころ**: ボタンの数はスレッドの未読件数（データ層のもの）で、画面に出た行を数えているのではない。メンション専用の別ボタンが ↓ の上に並ぶ。
- **押したとき**: 「新着」の区切りが下にあり、いま区切りより上にいるなら、**まず区切りまで**（上揃え）。それ以外は最新へ（窓の外なら「最新を読み込んでから」下端へ）。

#### 1.6 引用・ピンなど遠くの行へ

`ensureInteractionLoadedThenScrollToInteraction`（`+Scroll.swift`）: すでに窓にあれば直接スクロール。なければ **「その行の周辺」を読み込む**（窓を作り直し、中心の前後を半々）。着地したら読み込み要求に付けておいたスクロール指定（上揃え・中央・下揃え＋「画面にどれだけかかるか」）を実行し、行を目立たせる動き（ハイライト）をする。まとめ表示（collapse set）の中の行なら、先にそれを開く。ユーザーが指でスクロール中なら、スクロール指定は実行しない。窓を作り直すときは前の窓から**共通の行を再利用**して、描画し直しを減らす。遠くへ飛ぶときの専用のアニメーションは見つからなかった（スクロール指定の `animated` だけ）。

#### 1.7 自分が送ったとき

挿入を含むバッチ更新をアニメーション付きで適用し、`bottomForNewMessage`（アニメーション付き）のスクロール指定を同じ更新に付ける。**挿入のアニメーションと下端へのスクロールを、UIKit が 1 つの更新のアニメーションとして動かす**。同時に補正の仕組みは「デリゲートの targetContentOffset」側に切り替えて、下端への移動が補正に邪魔されないようにしている（`shouldUseDelegateScrollContinuity`）。

#### 1.8 キーボードと入力欄

- `keyboardDismissMode = .interactive`。入力欄は UIKit の `keyboardLayoutGuide` の上に張り付く（`+BottomBar.swift`）。**入力欄はコレクションビューの上に重なる別のビュー**で、リストの `contentInset.bottom` を入力欄の高さに合わせることで、行が入力欄の下に隠れないようにする（`+OWS.swift` の `updateContentInsets`）。
- そのインセット更新は**デバウンス**される。対話的に引き下げている間、セーフエリアが短い間隔で何度も変わり、判定が暴れるため。
- インセットが変わったときの offset: (a) 指でドラッグ中は何もしない（UIKit がやる）、(b) 下端にいたなら**アニメーションなしで下端へ**、(c) 上を読んでいたなら**インセットの変化量だけ offset をずらす**（キーボードと一緒に動く）、(d) 長押しメニューが出ている間は何もしない。(c) のずらしは、キーボードのアニメーションのブロックの中で呼ばれるのでキーボードと同じ曲線で動く。
- 入力欄の高さが変わる（複数行になる）ときも同じ `updateContentInsets` を通る。

#### 1.9 日付ヘッダーと既読

- 日付ヘッダーは**リストの 1 行**で、レイアウトが `shouldInvalidateLayout(forBoundsChange:)` を常に true にして、**スクロールのたびに「いま張り付くべきヘッダー」の位置を上端（ナビバーの下）に移した属性を返す**（`ConversationViewLayout.swift` の `ensureTranslatedLayoutInfo`）。1 つ前のヘッダーは、次のヘッダーに押し出されるように位置を計算する。張り付いたヘッダーは z-index を上げる。キャッシュは bounds/offset/inset のどれかが変わったら破棄。つまり**「浮かぶ日付」は別の overlay ではなく、本物のセルを動かす**。スクロール中だけ出して止まったら消す、という挙動は見つからなかった（常に張り付く。未確認）。
- 既読: 一番下に見えている行の sortId（レイアウトの属性から計算）が、既読にした最後の sortId を超えたら、**その手前までを既読にする**（`+Misc.swift` の `markVisibleMessagesAsRead`）。スクロールの 0.1 秒タイマー、画面の表示、アプリの復帰で呼ぶ。条件: 会話が最前面、他の画面を重ねていない、通話画面でない。**単調**（戻らない）。1 回に 1 本だけ非同期で書く。

#### 1.10 アクセシビリティ・長押しメニュー

- VoiceOver: 行ごとの追加操作（`accessibilityCustomActions`）を、セルが表示される（`willDisplay`）たびに付け直す（`+CVC.swift`, `CVLoadCoordinator.swift`）。スクロール指定のあと、目的の行の根のビューに `screenChanged` を投げてフォーカスを移す（`focusVoiceoverElementAfterScroll`）。
- 長押しメニューは `UIContextMenuInteraction` ではなく**自前の `ContextMenuInteraction`**（`+MessageActions.swift`）をコレクションビューのジェスチャで起動する。スクロールが始まると**進行中の長押し認識を取り消す**。メニュー表示中は読み込みを着地させず、インセット更新もしない（上の 1.2, 1.8）。メニューのために「その行の画面上の位置」は、レイアウトの属性（コレクションビューの座標）から取る。

### 2. Telegram-iOS

**注意**: Telegram は今、リストの実装が 2 つある。

- 旧: `submodules/Display/Source/ListView.swift`（約 5,500 行）。
- 新: `submodules/TelegramUI/Components/CoreList/`（`CoreVirtualListView`）。チャットの反転リストでは**既定**（`ChatHistoryListNode.swift` の初期化で選択。サーバー設定に切り戻しのスイッチがある）。経緯・設計・失敗談が `docs/chat/corelist-chat-history-backend.md`、`submodules/TelegramUI/Components/CoreList/CLAUDE.md`、`.../docs/plans/` に長く書かれており、**Telegram が今どう考えているかを知るには、コードよりこの文書が早い**。

チャット画面は `submodules/TelegramUI/Sources/ChatController.swift`（画面）、`ChatControllerNode.swift`（配置・ローディング・ボタン）、`ChatHistoryListNode.swift`（リストと読み込みの司令塔）、`ChatHistoryViewForLocation.swift`（どの窓を読むか）、`PreparedChatHistoryViewTransition.swift`（差分とスクロール指定の組み立て）。

#### 2.1 リストの作り（UICollectionView ではない、180° 回転）

- 旧 `ListView`: `ListViewScroller`（UIScrollView）を**スクロールの入力装置**としてだけ使い、行（`ListViewItemNode`、AsyncDisplayKit のノード）は普通のサブビューとして**自分で frame を動かす**。スクロールのたびに、全ての行を delta ぶん動かす。内容サイズは**偽の巨大キャンバス**（前後に各 1 万pt）で、本物の高さが分かるのは両端の行が読み込まれたときだけ。ここで初めて境界のゴムひもが本物になる。
- 行は、表示範囲＋上下それぞれ約 500pt（先読みが有効なとき。無効なら 20pt）の分だけ作る。
- **反転は、リスト全体と各行をそれぞれ π 回転する**ことで実現（`ChatHistoryListNode` と `ChatMessageItemView` が各々回転、合成すると正立）。リスト内の順序は index 0 = 最新で、リストの座標では「先頭」が最新。理由（読み取り）: 下に寄せる配置（`stackFromBottom`）より、「最新が先頭」のほうが、最新側への挿入・削除で既存の行が動かず、先頭の「ゴムひも・固定」の規則をそのまま使えるから。
- 新 `CoreList`: 同じ「最新が先頭」の回転を維持したまま、中身を作り直した**仮想化リスト**。`UIScrollView`（内容サイズ 1,000 万pt の偽キャンバス）を入力装置にするか、自前の物理スクロールを選べる（`ScrollEngine` という継ぎ目）。読み込んだ行は「窓」（行の列と frame の値型）として持ち、**変更は `applyChanges` という 1 つの入口**から、1 回のトランザクションで: 差分（挿入・削除・移動）、測り直し、アンカーの解決、新しい窓の構築、アニメーション、の順に行う。

#### 2.2 見ている行を動かさない

- 旧 `ListView`: 更新の 1 回のトランザクションの中で、削除・挿入・更新のあと、**「動かさない行」（`stationaryItemRange`）や、スクロール先の指定を、行の測り直し（非同期レイアウト）が済んだ時点で解決**して frame に反映する。UIKit のレイアウトの前後という概念がなく、行の位置・offset・内容サイズが同じ関数の中で一緒に決まる。高さが変わった行は、「見かけの高さ」(`apparentHeight`) を別に持ち、アニメーションしながら新しい高さへ寄せる。
- 新 `CoreList`: アンカーを「古い上端のインセットの位置にまたがっていた行」から選ぶ **「見えている内容を保つ」モード**（`.preserveVisibleContent`）を、**無限に読み込むリスト専用**に持つ。その行が、画面の上端からどれだけ離れていたかを保つ。消えた行なら下、なければ上の生き残りをアンカーにする。**画面の外の古い行は測り直さない**。そして描いたあとに offset を直す段階が**ない**と明記されている。
- 高さが変わる行（ストリーミング中の返信）や、引きずられる入力欄のインセット変化では、**補正を「どの時計で、どの値から」アニメーションさせるか**で細かい不具合が続いた記録が長い。要点は次の通り。
  - 内容サイズの変化を「補正で吸収する」と二重に動く。指でスクロールしているのと、**同じ指がキーボードを引き下げて入力欄の高さも変えている**場合、スクロール量とインセット補正が重なって指の 2 倍動く。→ **指が乗っている間はインセット変化の補正を止める**（旧 ListView 由来の規則を新実装にも移した）。
  - **キーボードを引き下げる指の離し際に、リストが勢いで流れてしまう**のを、「その離しは使用済み」として止める。
  - **テストが全部通っても、実機で崩れた**例が繰り返し書かれている（先頭/末尾の端、固定 id の行がある、行の高さが不揃い、などテスト用データがきれいすぎた）。**端（最初・最後・空・1 行）を必ず試す**、**実機で見る**が教訓として明記。

#### 2.3 ページング

- **窓**: 読み込む件数の基準は 44 件（`ChatHistoryListNode.swift` の `historyMessageCount`）。開く・周辺（引用）は 40 件前後、検索の一部は 128 件。データは `MessageHistoryView`（`holeEarlier`/`holeLater` で「ここから先は端末に無い」を表す）。
- **窓の作り直し方（先読み）**: 画面に出ている行の範囲を見て、**表示が窓の端から 5 行以内**（アルバムなど複数行をまとめた行があれば 1 行以内）になったら、窓を**その端の行を中心に作り直す**。新しい側が窓の外にあれば新しい方へ、古い側なら古い方へ。**窓はずっと約 44 行のまま、端へ寄るたびに滑る**（反対側は落ちる）。窓の位置を指すのは 1 つの値（`chatHistoryLocationValue`）で、連打されても最新の 1 件に収束する。
- **端末内か通信か**: 窓を作るのは端末のストアだが、窓の端に「穴」があれば、`trackHoles` によって裏でネットワークから埋める。穴を埋めている間は、窓が「読み込み中」状態を返す（空窓か、窓の端がまだ穴のとき）。**スクロールの先読みは、ストアに対して行い、通信は穴の補充として別系統**。
- **読み込み中の表示**（`ChatControllerNode.swift` の `updateIsLoading`）: 個人チャット以外では**骨組みのような吹き出し（スケルトン）**の全画面プレースホルダー（`ChatLoadingPlaceholderNode`）、個人チャットでは小さなスピナーだけ。「前を読み込み中」の状態は別フラグ（`isLoadingEarlier`）で、プレースホルダーの組み立て方も変わる。読み込めたら、スケルトンがメッセージへ移り変わるアニメーション（`animateOut`）。
- **本当の先頭**: 穴がなくなり、先頭にチャットの紹介行（`ChatInfoEntry`）が出る。

#### 2.4 開く位置、新着の区切り

`ChatHistoryViewScrollPosition`: `unread`（新着の区切りへ）、`positionRestoration`（前回の行と、その行の相対位置）、`index`（指定の行へ、位置・アニメーションの向き・ハイライト付き）。

- 新着の区切りへ: 区切りの行（`UnreadEntry`）を探して、反転した座標の**下端揃え**＝**画面の上端**に置く（Signal と同じく上揃え）。区切りが見つからなければ、未読の最初のメッセージを同様に。**アニメーションなし**。
- 新着の区切りを画面にきちんと置き直す処理（`enableUnreadAlignment`）がある。ナビゲーションバーの高さが開いている途中に変わる（報告バーが出る）と、区切りの位置がずれるので、**インセットが変わるたびに、区切りが張り付いていたなら張り直す**。新しい `CoreList` 移行時に「死んだコードになっていた」不具合の記録つき。
- 最初の窓がまだ穴なら `.Loading` を返して、窓が埋まるまで待つ（フェードインで表示）。

#### 2.5 最新に付いていく、↓ボタン

- 「最新にいる」判定の許容は 10pt（`visibleContentOffset` が既知で ≤ 10）。
- 最新への追従は**「端に固定する行」(`pinToBottomEdge`)** の仕組みで表す。指が触れた瞬間（ドラッグ開始）にその固定は**恒久的に解除**され、スクロールで戻っても自動では復活しない（新しい明示的なスクロール指定だけが戻す）。これでストリーミングの返信が伸びても、読んでいる行が動かない。送信すると固定を落とすかどうかも、この仕組みの「固定されているか」を見て決める。
- 到着した行は**ひとかたまりで、最新側の外から滑り込む**（`animateInsertedBlock`）。窓の端に着いたときだけ。
- ↓ボタン（`ChatHistoryNavigationButtons`、`ChatControllerNode`）の細部は未確認。
- 既読: 画面に見えている**受信メッセージの最大 index** を追い、アプリが読んでよい状態（`canReadHistory`）のときだけ、**単調に**既読を進める（`ChatHistoryListNode.swift` の `maxVisibleIncomingMessageIndex`）。

#### 2.6 遠くの行へ・窓の入れ替え

- 窓ごと作り直す（`InitialSearch` / `Navigation`）。スクロール指定は「中央」などの位置と「向きのヒント」（行き先が古い側か新しい側か）。窓が丸ごと別物になるジャンプは、**2 つの帯がそのまま平行移動する「カルーセル」**として動かす（旧窓を滑り出し、新窓を滑り込ませる。フェードはしない。固定 id の行が両方に居ても「新しい内容か」で判定する）。
- スクロール先の位置は、**行を測ってから解決する関数**で渡す（高さが必要な「中央」「下揃え」を、窓の外の行にも使えるように）。この関数は純粋で、リストを書き換えない。
- 引用の位置まで中央に寄せる（吹き出しが画面より高いとき）処理が、スクロール指定側にある。

#### 2.7 自分が送ったとき

入力欄の位置から吹き出しが飛び出す**モーフのアニメーション**（`ChatMessageTransitionNode`）を、行ノードの子として動かす。リストのスクロールに乗るので、始点の補正だけが必要。リスト側は、挿入の淡いフェードを**自動では付けない**（モーフと二重にならないよう、パス単位で抑止）。モーション低減や広告表示中は、モーフなしで出る。

#### 2.8 キーボード

- ウィンドウ全体に**キーボード引き下げ用のパン認識**（`Display/Source/WindowContent.swift`）があり、リストのパンと**同時に**動く。そのため 2.2 のように「1 本の指がスクロールとインセット変更の両方を起こす」。指の離し際の流れ（`shouldStopScrolling`）を止める専用の継ぎ目も入れた。
- 入力欄の高さ・キーボードの高さは、リストの**ビューポート（サイズとインセット）の更新**として毎回リストに渡される。リストはそれを、アンカー保持と同じトランザクションで処理する。

#### 2.9 日付ヘッダーと浮かぶ日付

- 日付やアバターは `ListViewItemHeader`（行に付く、固定される「付属品」）。`CoreList` では `CoreListAttachedItem` に写され、固定する向き・結合する規則（同じ日付どうしを 1 本にまとめる）は旧 ListView の計算をそのまま使う。
- **日付の丸いラベルは、スクロール中と、止まってから 0.3 秒だけ見える**（「固定位置にいる間は隠れる」を避けるため、「スクロールで点滅」と「固定距離」が 1 つの機能になっている）。新着の区切りは**日付の列を切る**ので、同じ日付の途中に区切りがあると、ラベルが 2 つ浮かんでしまうのを避けるため、区切りも「日付の列に属する行」として扱う。

#### 2.10 セルの高さ、アクセシビリティ、長押しメニュー

- 高さ: 各行（ノード）は**自分で非同期にレイアウトして高さを返す**（Texture/AsyncDisplayKit の流儀）。窓の外の行は測らない（推定高さなし）。幅が変わったら測り直し。画面外では、高さの確定している行だけが積まれる。ストリーミング中の返信は 1 トークンごとに高さが変わり、その補正が上の細かい不具合の元。
- 長押し: `ContextGesture` を行ごとに持ち、**スクロールの開始で、読み込んだ全ての行の進行中の長押しを取り消す**（`CoreListChatHistoryBackend` の「ドラッグ開始」）。
- アクセシビリティ: `ListView` の `accessibilityElements` を作る処理は**コメントアウトされている**。`accessibilityScroll` を対象に転送するだけで、私が読んだ範囲では行ごとの VoiceOver 対応の工夫は見つからなかった（未確認）。ここは参考にならない。

### 4. Pochical への比較と提案

比較したのは `apps/ios/Pochical/Pochical/ChatScreen.swift`、`ChatScrolling.swift`、`spec/chat.md` の「Unread lines and typing」と、`design/src/chat.ts`（`pageSize` 50、`openMax` 200、`floatingDayMs` 1500）。計画は別セッションの `chat-collectionview-plan.md`（共有ノート）に従い、UICollectionView（反転しない）＋ `UIHostingConfiguration` を前提に書く。

#### 4.1 今の作りとの違い

- **今**: SwiftUI の ScrollView＋非 lazy の VStack。行の高さは常に正確（全部を測る）。補正は描画後（`KeepsSeenLines` → `ChatScroll.pushedDown` → 次の runloop で `scrollTo`）。前を頼むのは上端のスピナーが見えてから。端末の 50 行を越えると、サーバーを待って止まる。
- **両者に共通**: 補正をレイアウトと同じ更新の中で済ませる。先読みは、端の**手前**で動く。Pochical は「端に着いてから」。
- **Telegram の `.preserveVisibleContent` と、Signal の token 方式は、本質的に同じこと**を言っている: 「アンカーの行を 1 つ決め、更新の前後でその行の画面上の位置を同じにする」。計画の `LinesAnchor.item(id, top)` はこれに当たり、方向性は正しい。

#### 4.2 spec/chat.md に **採り入れる**もの

1. **先読み（まだ spec に無い）。** 「上端の近く」ではなく、**見える高さの数倍手前**で頼む。Signal は画面長辺の 3 倍、Telegram は窓の端から 5 行。計画の「見える高さ × 2」は妥当。spec には「先読み」の一言と、その距離を `design/src/chat.ts` に置く（`chatRules.prefetchScreens` のような名前）。端末の窓とサーバーの先取りは別の定数にする。
2. **連打を抑える。** Signal は「前回から 2 秒以内は見送り、1 秒後に再判定」。Pochical も、同じ ask を重ねないための規則（頼み中は頼まない＋着地後に再判定）を spec に書くとよい。数値は同じにしなくてよい。
3. **「着地を遅らせる」規則。** キーボードのアニメーション中、長押しメニュー表示中、**指の乗った引き下げ中**は、前のページの着地やスクロール指定を待たせる（Signal）。Pochical の spec には無い。入れる価値がある。特に**長押しメニューが開いている間は、リストを動かさない**。
4. **許容の違いを数値で書く。** Signal は下端判定が 5pt、Telegram が 10pt、だが Signal は**更新を適用する前の時点**で判定する。計画の「`following ⇔ アンカーが .foot`」は、この判定を更新前に確定させる意味でも有効。spec の「Whether the chat follows…」に「更新の前に決める」を足す。
5. **新着の区切りの扱い。** 両者とも**区切りを画面の上端に置く**（spec と同じ）。加えて、(a) 区切りは**アンカーにしない**（Signal は日付・区切り・入力中をアンカーから除く）、(b) **ナビゲーションバー等が開いている間に高さが変わったら張り直す**（Telegram）。Pochical の pins バーの開閉に当たる。spec に「ピンのバーが開閉しても区切りの位置は保つ」を。
6. **↓ボタンを押したときの順序。** Signal は「区切りが下にあり、いま区切りより上にいるなら、まず区切りへ。それ以外は最新へ」。spec の今の文面は「最新へ」だけ。**採り入れる候補**（プロダクトの判断なので、変更前に確認する）。
7. **開く瞬間は、位置が決まるまで隠す**（Signal、最大 2 秒）。spec は「The lines show once where they open」と同趣旨で、すでにある。実装は `placed` の細工から、**最初のレイアウト確定後に offset を決めてから見せる**に置き換えられる。
8. **窓の上限。** Signal は 500 行、反対側を落とす。spec は `openMax` 200 行と「足す」のみで、上限と落とす規則がない。長く開いたままの端末のメモリのために、**上限と、落とす向き**を決めておく。Android の LazyColumn では窓の概念がそもそも要らないので、プラットフォーム共通の spec には「上限を超えたら反対側を落としてよい」程度に留める。

#### 4.3 **変える**もの

1. **「前の行は、見えている行を動かさず入る」の書き方。** 今の文は「even when held at the very top, when pages come one after another, and as the page's own lines settle」と**症状を並べている**。両者の作りは、症状ごとの規則ではなく、**「更新の前後でアンカー行の画面上の位置を保つ」という 1 つの規則**で足りることを示している。spec は 1 つの原則に畳み、症状は検証項目（受け入れの確認）に移す。これで「accretion」の山が減る。
2. **「Unread lines and typing」の段落を分ける。** 今は 1 段落に、開く位置・追従・続きを読む・送信・既読・ページング・浮かぶ日付が全部入っていて 600 語近い。両者のコードも「開く位置」「追従」「ページング」「ジャンプ」「既読」を別の関心事として扱う。spec も **「開く位置」「追従と↓」「前の行を読む」「遠くの行へ」「既読」「浮かぶ日付」** の小見出しに分ける（今回の依頼の範囲外なので、別の PR で）。
3. **サーバーの先取りの位置づけ。** 今の「from the device when it holds them, else asked for」は、端末の窓から前を頼む順序の話。Signal は通信がなく、Telegram は穴だけ裏で埋めるので、**どちらも「先読みが通信を待つ」状況を、ほぼ作らない**。Pochical が同じ状態に近づけるには、計画の「サーバーから 1 ページ先取り」（端末に前の行が pageSize 未満になる前に頼む）が、spec 上の規則として必要。「スクロールが端末にある行より先に届きうる」ことを前提に、**上端にだけ出るスピナー**（Signal の帯、Telegram の「前を読み込み中」に相当）を spec に。
4. **スピナーの出方。** Signal は「続きがある限り常に帯を出す」。Pochical の今の `EarlierLines` は、見えたときだけ。先読みを導入すると、スピナーは**サーバー待ちのときだけ**で足りる（計画の通り）。Signal 式の「常時の帯」にはしない（Pochical は端末の窓が小さく、帯が常に見える状態になるため）。

#### 4.4 **捨てる**もの

1. 描画後に `scrollTo` で offset を戻す手口一式（`KeepsSeenLines`, `ChatScroll.moveLinesBack`, `scrolled(to:)`, `letGo`, `edge`, `Lifts`/`lifting`/`lifted`）と、それを支える spec の文言（「even when held at the very top…」の列挙）。両者とも、この手口を使っていない。
2. 「`following` を、SwiftUI の `defaultScrollAnchor(.bottom, for: .sizeChanges)` と `onScrollGeometryChange` で追う」作り。Signal は更新の前に下端を判定し、Telegram は固定行の仕組みに載せる。
3. 「新着の区切りまで行けるか」の事前判定（`unreadTop`/`linesHeight`/`seen`）。オフセットを [min, max] に clamp すれば済む（両者ともレイアウト側で clamp している）。

#### 4.5 UICollectionView ＋ UIHostingConfiguration に合う方式

結論: **Signal の構造（反転しない UICollectionView＋自前レイアウト）を、考え方だけ借りる。Telegram の構造は借りない**。ただし 1 点だけ Signal と**違えるべき**ところがある。

- **借りる**:
  - 反転しない collection view＋自前の `UICollectionViewLayout`、1 セクション。
  - 補正は `invalidateLayout(with:)` の `contentOffsetAdjustment`（行の出入り・ページ・サイズ変化の主経路）と、`targetContentOffset(forProposedContentOffset:)`（回転・下端への移動など補助）の 2 本立て。
  - アンカーは「見えている行のうち 1 行」、**日付・区切り・入力中の行は除く**。
  - 継続の目印（token）を、**更新の前に取る**。更新後のレイアウトと比べて、同じ id の行の y の差を補正にする。
  - 「下端にいるか」は**更新の前に**確定する。
  - キーボード: `keyboardDismissMode = .interactive`、`contentInset.bottom` で入力欄の分を空け、下端にいたなら下端のまま、いなければインセットの変化量だけずらす。インセット更新は**デバウンス**し、**ドラッグ中はやらない**。
  - 読み込みの着地を、キーボードのアニメーション・長押しメニュー表示中は待たせる。
  - 日付は、本物のセルを張り付かせる方式は、SwiftUI の行ではやりにくい。**別の overlay（今の `FloatingDay`）のままがよい**。
- **違える（Signal と）**: Signal は高さを**読み込み時に事前計算**する。Pochical は行が SwiftUI のビューなので、事前計算できず、**`UIHostingConfiguration` の自己サイズ（preferred layout attributes）**に頼る。したがって Signal より、**「高さが後から確定する」ことに強いアンカー方式が要る**。具体的には、(a) 未測定の行は推定高さで積む、(b) 高さが確定したとき、`invalidationContext(forPreferredLayoutAttributes:withOriginalAttributes:)` で、**アンカーより上の行なら `contentOffsetAdjustment` に同じ差を入れる**（計画の 2.1 の通り）。Signal にこの経路は無いので、**参考にできるのは ekazaev/ChatLayout のような自己サイズ対応の既存実装**。別セッションの計画が ChatLayout を挙げているのは筋が通る。自前で書くなら、ここが一番の難所。
- **借りない**:
  - Telegram の 180° 回転。SwiftUI の行を回転して置くのは、VoiceOver の読み順（`accessibilityElements`）・テキスト選択・Dynamic Type・ハイライトなど副作用が多い。Telegram 自身も行ごとに回転を打ち消すために専用の手当てを重ねている。Android も `reverseLayout = true` でネイティブに反転できるので、**共通の spec は「最新が先頭」を前提にしない**。
  - Telegram の偽の巨大キャンバス＋手動の frame。UICollectionView がやってくれる仮想化を、自前でやり直すことになる。`CoreList` が **約 1,500 行の運用メモと 10 以上の設計文書**を要していること自体が、規模の目安。
  - Telegram の「窓を約 44 行に固定して滑らせる」方式。端末の窓がそもそも小さい Pochical は、`pageSize` 50 を最初に持って、必要なら足す今の作りのほうが単純。

#### 4.6 検証について（両者から学ぶこと）

- Telegram の文書が繰り返し言うのは、**自動テストが通っても、実機で崩れた**こと。原因はテスト用データが「きれいすぎる」こと（行の高さが揃っている、先頭/末尾に触れない、固定 id の行がない）。Pochical の確認も、(a) 窓の**端**（最初・最後・空・1 行）、(b) 続けて来るページ、(c) 画像・リンクのカードが後から描かれる、(d) キーボードを指で引き下げながら、を実機の画面録画のコマ送りで見る。計画の「PR 2 の確認」と同じ方向。
- 「更新の同時進行」が最大の危険（Signal は着地を待たせ、Telegram は再入を直列にする）。Pochical も、**ページの着地・送信・キーボード・ジャンプが同時に来たとき**の順序を、先に表にして決めておく。

## 領域0b: ChatLayout（ekazaev/ChatLayout, MIT）との比較

見た版: 2.5.2（2026-09-21）。`ChatLayout/Classes/Core/CollectionViewChatLayout.swift`（約 1,000 行）が本体で、`Model/StateController.swift`（約 1,300 行）が行の大きさと位置を持つ。Example は `Example/ChatLayout/Chat/`。対応は iOS 15〜27、Swift ツールは 6.2 以上（Xcode 26 系が要る）。MIT なので使える。ここでは仕組みを自分の言葉で書く。

### どういう作りか

- **反転しない `UICollectionView` ＋ 自前の `UICollectionViewLayout`**（Signal と同じ選択）。README が「回転しない、`adjustedContentInset` などの標準の動きをそのまま使える」と明言。1 本のレイアウトで、セクション（日付などの区切り）と行を扱う。
- **自己サイズが前提**（Signal と違う点）。デリゲートの `sizeForItem` で**推定の大きさ**か**確定した大きさ**を返し、確定していない行はセルの `preferredLayoutAttributesFitting` の結果で後から確定する。Signal のような「事前計算して渡す」ことも、確定した大きさを返せばできる。
- 付属の汎用ビュー（`ContainerCollectionViewCell` など、中身の View を包んで寄せ・幅を整える）は任意。使わなくてよい。
- 更新は標準の `performBatchUpdates` か diffable データソースのまま。`ChatLayoutDiffableDataSource` は `reconfigureItems` をレイアウトに伝えるための薄い代用品。

### 位置を保つ手口と、それが働く段階

Signal の「`contentOffsetAdjustment` を無効化のコンテキストに入れる」と同じ UIKit の口を、**4 つの段階**で使い分ける。

1. **バッチ更新の最中**（`prepare(forCollectionViewUpdates:)` → `finalizeCollectionViewUpdates`）。挿入・削除・更新を処理して、各行が動いた高さの合計を覚え、更新の終わりに**1 回の補正**（`contentOffsetAdjustment`）を入れる。この補正は `keepContentOffsetAtBottomOnBatchUpdates` が真のときだけ働き、**基準は下端**（画面の下の行を動かさない）。画面より上に行を足す（前のページ）と、見えている行はそのまま留まる。Example の前ページの読み込みも、特別な処理はなくこの経路に乗っている。
2. **自己サイズが確定したとき**（`invalidationContext(forPreferredLayoutAttributes:withOriginalAttributes:)`）。行の高さが推定から変わったら、**その行が画面の下端より上にある場合だけ**、高さの差ぶん `contentOffsetAdjustment` を入れる。だから、上の行の画像が後から読めて高くなっても、下の見えている行は動かない（下基準）。下の行が育つ分には何もしない。高さの差が丸めて 0 なら無効化しない（往復を止める）。
3. **位置のスナップショットで復元**（`getContentOffsetSnapshot(from:)` と `restoreContentOffset(with:)`）。「上端（または下端）に一番近い行と、その行の端からの距離」を更新の**前に**取り、更新の**後に**復元する。復元は内部で `layoutIfNeeded` を挟みながら無効化のコンテキストに補正を入れる。Example では**回転と `contentInset`（キーボード）の変化、初期の最下端への配置**で使い、基準は通常は下端（日付の固定行を使う特別な場合だけ上端）。
4. **アニメーション付きの `bounds` 変化**（`prepare(forAnimatedBoundsChange:)` と `targetContentOffset(forProposedContentOffset:)`）。キーボードや回転で見える高さが変わるとき、高さの差から補正を計算して提案のオフセットに足す。

つまり、**描いたあとに `scrollTo` で戻す手口はどの段階にもない**。Signal と同じく「レイアウトの更新の中」で補正する。

**ただし基準が下端であること**に注意。Pochical の spec には「続きを読む」は行の**上端を留めて下へ伸ばす**とある（`spec/chat.md` の Unread lines and typing）。ライブラリの自己サイズ補正は下基準で、上の行の成長は下の行を固定する（上端が動く）。作者自身も issue #69 で「再読み込みで内容が育つと上が押し上げられるのは正しい挙動。特別な場合は `keepContentOffsetAtBottomOnBatchUpdates` を一時的に切って自分で扱う」と答えている。したがって、前のページを足すことは標準の経路で足りるが、**「続きを読む」（上端を留める）と「ここから新着から開く」は、フラグを切るか、上端のスナップショットを取って復元する**経路を自分で書くことになる。

### 前のページ・フリング

- Example の前ページの読み込み: 上端から見える高さ 1 つ分以内で呼ぶ。**読み込み中は再呼び出しを止める**（読み込みの最中に offset が変わるため、また呼ばれてしまうので）。**ユーザーがスクロール中ならアニメーションなしで入れる**。`scrollViewShouldScrollToTop` で、ステータスバーのタップによる「上端へ」を、上端に着いてから読み込む形にする（Signal の同じ罠への対処と同じ）。
- 更新のアニメーション中にユーザーが指で触れたら、その更新のアニメーションを打ち切る（空白が見えるのを避ける）。Example の `scrollViewDidScroll`。
- 減速中に補正が効くか（`contentOffsetAdjustment` が減速を止めないか）の専用の説明は見つからず。**実機で確かめる項目**（共有ノートの計画のリスクと同じ）。

### ライブラリが「持つ」もの

- 位置の保持（上の 1〜4）、挿入・削除のアニメーション（`initialLayoutAttributesForInsertedItem` などのデリゲートで出入りの見た目を決める）、**内容が画面より短いとき下に寄せる**（`keepContentAtBottomOfVisibleArea`）、**固定する行**（`pinningTypeForItem` で `.top` / `.bottom`。Example は**日付の区切りの行を `.top` で固定**している）、行の寄せ（左右）と行間・セクション間の間隔、タイピング表示用の行。
- 固定する行は、**日付の「行」そのものが画面の上に張り付く**方式（Signal の本物のセルを張り付かせる方式に近い）。Pochical の「浮かぶ日付」は、スクロール中だけ出て止まると消える別の overlay（`floatingDayMs`）なので、**これはそのまま使わず、今の overlay を残す**ほうが仕様に合う。日付の区切りの行を本文に入れるかは別の判断。

### ライブラリが「持たない」もの（自前で作る）

README が明言している: **キーボード**（`contentInset` を自分で更新する）、**入力欄**（Example は第三者の InputBarAccessoryView）。ほかにコードを見て持たないと分かったもの:

- **キーボード**: Example はキーボードの frame 変化を購読して `contentInset.bottom` を更新し、更新の前後に位置のスナップショットを取って復元する。`keyboardDismissMode = .interactive` は普通に使える。Pochical は入力欄が SwiftUI なので、**入力欄の高さ ＝ `contentInset.bottom` の更新**を自前で橋渡しする（Signal の `updateContentInsets`、領域6 の知見：デバウンス、ドラッグ中は何もしない）。
- **入力欄の高さが変わったとき**: Example の issue #94（入力欄が高くなると一番下へ飛ぶ）は、Example 側の `scrollToBottom` の呼び出しが原因で、削除すると解消した。**自前で下端へ動かす処理を、入力欄の高さ変化に結び付けない**。
- **吹き出しの形**: Example に Bezier の吹き出し（`BezierMaskedView`）、画像のマスクがあるが、ライブラリ本体にはない。Pochical の既存の SwiftUI の吹き出しをそのまま `UIHostingConfiguration` の中に置く想定なので、影響なし。
- **長押しメニュー**: ライブラリは何も持たない。Pochical は自前の `MessageActions`（行の位置を `.global` で受ける）を持つ。セルが UICollectionView の中に入ると、外側のスクロールで SwiftUI の `.global` の更新が来ない恐れがある（共有ノートの計画のリスク）。行の位置はセル → ウィンドウの座標変換で与える。
- **先読みの判断、読み込みの調停（キーボードや長押しメニュー中は待つ）、スクロール先の指定、「ここから新着」の置き方、↓ボタンと未読数、既読の判定**: すべて自前。Example にあるのは最小の版で、Signal のような「着地を待つ」は無い。
- **ジェスチャ**: Example に `SwipeNotifier`（スワイプ）、`EditNotifier`（編集）があり、スワイプ返信の参考になる（領域4）。ただしライブラリ本体にはない。

### 既知の issue（GitHub、2026-10 時点で open は 0 件）

- **`UIHostingConfiguration` / SwiftUI セル**: 検索で該当する issue は見つからず（SwiftUI 関連は「SwiftUI から使うには」の質問 #65 のみ）。Example の行はすべて UIKit のビューで、**SwiftUI のホスティングセルでの実績は確認できない**。ここは共有ノートの計画のとおり、PR の最初に実機で確かめる項目。自己サイズの往復（2 回に分けて高さが決まる）に対して、ライブラリは「高さの差が丸めて 0 なら無効化しない」を持つので、往復が収束する前提には沿う。
- **iOS 26 / 27**: #95「対話的なキーボードの引き下げでメインスレッドが固まる」（2026-04、実機の iOS 26.2〜26.4）。作者の調査では、原因は ChatLayout ではなく、Example が使う入力欄 InputBarAccessoryView の**下端を safe area の下端に張る制約**（iOS 26 のバグとの組み合わせ）で、入力欄が「無限のレイアウトのループ」を起こす。safe area の下端への張り方を変えると直る。入力欄側に報告されて close。**教訓**: Pochical の入力欄（SwiftUI）がキーボードの safe area と `contentInset` を行き来して再レイアウトを繰り返さないか、**実機で指を離さず引き下げて確かめる**（シミュレータでは再現しなかった）。README の対応は iOS 15〜27 と書かれている。

### 判定（Signal・Telegram との比較を踏まえて）

- **採り入れる（ChatLayout を使う）**: 反転しない UICollectionView ＋ 自前レイアウト＋自己サイズ ＋ `contentOffsetAdjustment` による位置の保持という骨組み。Signal と同じ考えを、自己サイズに対応した形で用意してくれる。自前でレイアウトを書くよりも、上の 4 つの段階を一通り扱ってくれる点が大きい（Signal の `ConversationViewLayout` は約 1,150 行、`CollectionViewChatLayout` は約 1,000 行＋`StateController` 1,300 行で、規模は近い）。
- **自前で足す（ライブラリが持たない）**: 上の「持たない」の全て。特に **(1) 先読みの調停と、キーボード/メニュー中に読み込みの着地を待つ規則（Signal）**、**(2) 上基準の復元（続きを読む・ここから新着から開く）**、**(3) 入力欄の高さ ＝ `contentInset.bottom` とその橋渡し**、**(4) 「ここから新着」とスクロール先の指定（Telegram/Signal の上揃え）**。
- **変える**: 共有ノートの計画の「アンカーを `.foot` か `.item(id, top)` で持つ」は、ChatLayout では**スナップショット（行と距離）** ＋ **`keepContentOffsetAtBottomOnBatchUpdates`（追従中は真）** の二つに対応する。追従中と前ページの追加は下基準のフラグを真のまま使い、続きを読む・ここから新着から開く、のときは偽にして上基準の復元で扱う、と**モードを切り替える**設計になる。
- **捨てる**: 自前のレイアウト（約 300 行）を書く案。自己サイズの往復、挿入のアニメーション、回転、固定する行の分まで自前で書くことになるため。
- **注意**: 対応 OS と Swift のツールのバージョン（Swift 6.2 以上）を Pochical の Xcode と合わせる。`UIHostingConfiguration` の実績は無いので、**最初の PR で、(a) 高さが後から変わる行、(b) 続けて来るページ、(c) 指を離さずキーボードを引き下げる、の 3 つを実機で録画して確かめる**。うまくいかなければ、ライブラリを雛形にして一部を自前で書き換える道がある（MIT）。

## 領域1: メディア（写真）

### Signal

- **ぼかし**: 送信側が BlurHash（4×3 成分）を作って添付に付ける。元画像を長辺 200px に縮めてから計算。受信側は未取得の添付にその hash があれば、**16×16 の小さな画像**に描いてセルいっぱいに引き伸ばす（大きく描かないのが性能の肝）。hash の文字列をキャッシュキーにする。優先順はバックアップのサムネイル > BlurHash > 無地。`SignalServiceKit/Messages/Attachments/BlurHash.swift`, `Signal/ConversationView/CellViews/CVMediaView.swift`
- **サイズの選び方**: サムネイルは 4 段（小/中/中大/大）。セルは「描画の長辺が、その段の 1/0.8 倍以内に収まる最小の段」を選ぶ（25% の余裕。段が粗いので 1 段上げるコストが大きい）。元画像が収まるなら元をそのまま使う。生成物は暗号化したディスクキャッシュで、生成は同時 1 本の直列キュー。`SignalServiceKit/Messages/Attachments/V2/Thumbnails/*`, `CellViews/CVMediaAlbumView.swift`
- **キャッシュ**: 会話ごとの `CVMediaCache`。静止画 16 件、アニメ画像 8 件の LRU。メディアのビュー自体も LRU で持ち、**ビューに「所有者」を持たせて、セルが再利用されても同じ添付のビューを取り戻せる**（戻りスクロールで再デコードしない）。画面を離れる・非アクティブ・メモリ警告で全消去。`CVMediaCache.swift`
- **読み込み制御**: セルが見えている（画面が表示中かつアプリ前面）間だけロードし、再利用されたらアンロード。状態は 未/中/済/失敗の 4 値で、重複ロードを避け、キューに着いた時点で不要なら捨てる。デコードは共通の直列キュー 1 本。`UICollectionView` の `isPrefetchingEnabled` は**初回表示を速くするため最初は切り、表示後に入れる**。メディア専用の先読みは見つからず。
- **進捗・取消・再試行**: 円形の進捗（44pt）。タップでダウンロード / 不定 / 進捗%。自動ダウンロードは種別ごとの設定に従う（小さなものは常に自動、200MB 超は自動しない）。自動でないときは吹き出しに「ダウンロード」ボタン。進捗をタップで取消、**手動で取り消したものは自動再開しない**。通信の失敗は指数バックオフで自動再試行、ユーザー起動のものは永続再試行しない。`CVAttachmentProgressView.swift`, `SignalServiceKit/Messages/Attachments/V2/Downloads/*`
- **ビューア**: `UIPageViewController`（前後の添付を供給）、`UIScrollView` 派生でズーム（最大 4 倍、ダブルタップ 2 倍、1 タップで UI の出し入れ）。開閉は `UIViewControllerAnimatedTransitioning` の自前実装で、**元のセルの画像の frame を座標変換して取り、吹き出しの位置から 4 隅の角丸を個別に計算してマスクを動かす**（0.25 秒）。閉じるはインタラクティブ（パン 88pt で完了、`UIPercentDrivenInteractiveTransition`）。元のセルが画面外ならフェード。`MediaPageViewController.swift`, `Transitions/MediaZoomAnimationController.swift`, `MediaInteractiveDismiss.swift`
- 動画/GIF: ループ動画は専用の `AVPlayerLayer` ビュー（見えている間だけ再生、複数ビューを同期）。通常の動画は静止サムネ＋再生ボタンで、ビューアで再生。

### Telegram

- **ぼかし**: メッセージに**数百バイトの極小 JPEG（インラインサムネ）が同梱されて届く**。共通のヘッダ/フッタに挟んで復元し、ネットワークなしで最初のフレームからぼかし絵を出す。本画像が来たら置き換える。`submodules/TinyThumbnail`, `TU/Components/Chat/ChatMessageInteractiveMediaNode/Sources/ChatMessageInteractiveMediaNode.swift`
- **寸法が先に分かる**: 画像の幅・高さがメッセージに入っているので、画像が来る前にセルの高さが確定する（レイアウトのジャンプなし）。
- **同期描画**: 描画ノード（`TransformImageNode`）はキャッシュにあれば**同期で即描画**し、空白→画像のちらつきを避ける。初回表示・ジャンプ直後は「同期ロード」のヒントで、ディスクキャッシュ済みの画像を同期で出す。スクロール中は非同期。
- **サイズの選び方**: 画像は複数の大きさの表現を持ち、**表示幅 × 1.2 以上で最小のもの**を選ぶ。プログレッシブ JPEG は表示サイズに応じて**先頭の一定バイトだけ**を範囲取得する。リサイズ済みの表現はディスクに id 付きで保存し、大きさ違いが既にあれば使う。`submodules/DirectMediaImageCache`, `submodules/PhotoResources`
- **先読み**: `TU/Sources/InChatPrefetchManager.swift` が、**見えている付近のメッセージのメディアだけ**を、設定・回線・チャット種別に応じて「全取得」「先頭だけ」「しない」と判定。対象から外れたら取得を取り消し、重複は 1 回。**優先度はスクロールの向きと順序**。実際の取得は `FetchManager` が「ユーザー操作 > 昇格 > 前景の先読み」の順で走らせる。
- **進捗・取消**: 円形の進捗（`RadialStatusNode`）。進捗 0 でも最小の弧（約 2.7%）を見せて「始まっている」と示す。タップで、取得中→取消、未取得→取得開始、取得済み→開く。送信中の取消は「その送信を消す」と同じ扱い。
- **ビューア**: `GalleryUI`。横ページング、ピンチ/ダブルタップのズーム。開く動きは**元のノードのコピーを元の位置から最終位置へ、位置・bounds・拡大を同時に約 0.25 秒のバネで動かす**。背景はフェード、チャット側はわずかに奥へ押し込む。閉じるは縦スワイプ（平衡点からの距離で背景の透明度が下がり、離した距離/速度で閉じるか戻るかを決める）。元のサムネは遷移の間だけ隠す。`submodules/GalleryUI/Sources/*`
- **動画/GIF**: 自動再生は（設定）かつ（取得済み）のときだけ。見えている間だけデコーダを繋ぎ、外れたら切り離す。省電力モード（既定は電池 15% 以下）で自動再生や半透明を落とす。

### Pochical の今

ThumbHash を送信時に作って送り、サーバーが保持（上限 25 バイト、`spec/vectors/thumbhash.json`）。表示側はぼかしを NSCache に持ち、写真が 200ms でフェードイン。ThumbHash の無い古い写真は呼吸するグレー（Reduce Motion で静止）。チャットには長辺 960 の小さい版、開くときはフル。表示サイズ×スケールの画素に ImageIO でダウンサンプル。送信前は長辺 2048・4MB 以内に縮め、EXIF/GPS を除く。画面外では画像を持たない（`whileInSight`）。ディスクは App Group の Caches。ビューアは `fullScreenCover`、下に引いて閉じる（背景が薄くなる）、ビューア内でぼかし→写真のフェード。（`Kit/ChatPhotos.swift`, `App/ChatPhotoViews.swift`, `ChatScreen.swift:508`）無いもの: 先読み、進捗%、取消、バックグラウンド URLSession、キャッシュの上限、ぼかし NSCache の cost 制限、取得失敗後にタップで取り直す導線、ビューアのズーム/複数枚/元位置からの遷移/共有シート。

### 判定

- **すでによい**: ThumbHash の同送とフェードイン（Signal の BlurHash、Telegram のインライン極小 JPEG と同じ考え）。送信前の縮小と EXIF 除去。画面外で持たない。小/大の 2 段の取得（段数は Signal の 4 段より少ないが、写真が小さい用途では十分）。
- **採り入れる**:
  - ビューアに**ズーム（ピンチ/ダブルタップ）、前後の写真へのスワイプ、元のサムネから広がる開閉の動き**。両者とも持つ定番。UIKit の `UIViewControllerAnimatedTransitioning` か SwiftUI の `matchedTransitionSource` / `navigationTransition(.zoom)`（iOS 18+）。元のセルが画面外ならフェードに落とす（Signal）。
  - **寸法をメッセージに含めて、画像が来る前に高さを確定**する（Telegram）。UICollectionView 化の高さのずれを減らす。Pochical が既に比率を送っているかは**要確認**。
  - **取得失敗後のタップで取り直す導線**と、**手動で取り消したら自動再開しない**規則。
  - ぼかしのキャッシュに cost 制限、ディスクキャッシュに上限（Caches 任せにしない）。
  - 先読み: 見えている付近の写真だけを、スクロールの向きの先から。優先度は「ユーザー操作 > 先読み」（Telegram）。UICollectionView の `UICollectionViewDataSourcePrefetching` が使える。
  - 写真の送信は、アプリがバックグラウンドに行っても続くように、バックグラウンド `URLSession`（今は背景タスクで補っている）。
- **変える**: 進捗の見せ方。Telegram は 0 でも弧を少し見せる。Signal は 3 表示（タップで取得/不定/%）。Pochical は送信中の `ProgressView` のみなので、%と取消（×）を付けるなら円形の進捗に統一。
- **捨てる**: 自動ダウンロードの設定（種別×回線×サイズ）、動画/GIF の自動再生、省電力時の挙動、スポイラー。

## 領域2: 送信（楽観的表示・順序・失敗・編集/取消・オフライン）

### Signal

- **楽観的表示**: 送信ボタンの瞬間に DB へメッセージを書き、受信者の状態を「送信中」にしてからジョブを積む。画面は DB の変更観測で再描画。画像はローカルのファイルから即表示し、進捗のリングを重ねる。時刻は端末時計から作り、連打でも同値にならないよう調整。`SignalServiceKit/Jobs/MessageSenderJobQueue.swift`, `Messages/MessageTimestampGenerator.swift`
- **キュー**: 永続ジョブ（再起動後も続く）。リトライは**二層**: 下位は「相手の端末が足りない」などを即再試行するだけ、上位のジョブキューが一般のエラーを指数バックオフ（起点 2 秒・乱数 0.75〜1.25 倍）で最大 110 回（約 24 時間未満）。**到達性の回復・接続が開いた、のどちらかが来たらバックオフを待たず即再試行**する（取りこぼし防止に「試行前にフラグを消す」順序も守る）。起動時、古い「送信中」のまま残ったものを「失敗」に落とすジョブ。`Util/OWSOperation.swift`, `Messages/FailedMessagesJob.swift`
- **状態表示**: 吹き出しのフッター右にアイコン（送信中は回転、保留は止まる、送信済、配達済、既読）。**失敗は時刻の代わりに赤系の文言**（一部だけ届いたときは別の文言）。失敗をタップするとアクションシート「再送/削除」。安全番号が変わった相手がいれば確認を挟む。`Components/CVComponentFooter.swift`, `ResendMessagePromptBuilder.swift`
- **編集**: 長押しメニュー→入力欄が編集モード（上に編集ラベルと元のサムネ）。送信できるのは元の送信から 24 時間、1 件あたり最大 10 回。受信側はさらに緩く受理。条件外は理由を ActionSheet で言う。編集済みバッジと履歴シート。ダブルタップで編集開始（間隔 0.2 秒と短く、1 タップの判定を遅らせすぎない）。`SignalServiceKit/Messages/Edit/EditManagerImpl.swift`, `DoubleTapToEdit/`
- **全員から削除**: 一定時間内の自分の発言のみ（サーバーの設定値）。削除の送信中も「送信中」の動きを見せる。削除済みの再送は本文ではなく削除メッセージを再送する。
- **オフライン**: 会話内のオフラインバナーは見つからず。「保留のまま待つ＋回復で自動再開」で表す。

### Telegram

- **楽観的表示**: ローカルの名前空間のメッセージを DB に即追加（時計アイコン）、サーバーの応答でクラウドの id に置き換え。重複防止の乱数 id。同じ相手への要求は「後の id は前の id に依存」という依存タグで直列化し、**id 昇順を保証**。アルバムは 1 要求にまとめる。メディアは「アップロード（並列可）→コミット（順序厳守）」の 2 段。ライブ入力ドラフトの間は送信を保留し、解除時にまとめて吐く。`submodules/TelegramCore/Sources/State/PendingMessageManager.swift`
- **状態表示**: 日時のノードに、送信中=針の回る時計、送信済=チェック 1、既読=2。`TU/Components/Chat/ChatMessageDateAndStatusNode`
- **失敗**: 自動再試行はネットワーク復帰で未送信 id を再処理。**恒久的なエラー（制限・スパムなど）だけ「失敗」にして止め、理由をトースト/アラートで言う**。失敗した吹き出しの左に赤い警告アイコン（バブルを詰める）、タップで「再送 / すべて再送 / 削除」のメニュー。アルバムは 1 グループ単位。
- **削除**: 「自分だけ消す」は**即時には確定せず、リストで隠して上に Undo のトースト**（猶予後に確定）。「全員から消す」は即時でUndoなし。
- **編集**: 入力欄が編集モード。送信ボタンに進捗。編集の要求は専用のマネージャが管理、失敗はアラート。編集中は「入力中」を送らない。
- **オフライン**: タイトル下のサブタイトルが「ネットワーク待ち / 接続中 / 更新中」に差し替わる（通常のオンライン表示や入力中の代わり）。送信中は時計のまま残り、復帰で自動再開。画面を閉じても送信は続く（アカウント側のマネージャが保持）。`TU/Components/ChatTitleView/*`

### Pochical の今

送信は SQLite の `chatOutbox` に積まれ、`chat.state.waiting` として時計アイコン付きで即表示（時刻の幅を確保してバブル幅を変えない）。group socket が id 順に送り、`op_id` で冪等、届いた行と `op_id` で入れ替え（`Kit/ChatValues.swift`, `spec/sync-protocol.md`）。写真は先にアップロード、失敗した写真は後ろに回して再送（後続の行を止めない）。再接続はランダム指数バックオフ、前面復帰・ネット回復で即再接続、keepalive の無応答で切断。「接続中…/更新中…」を `statusShownAfterMs` 後にタイトル下へ。バックグラウンドへ移るときは、未送信を送り切るまで背景タスクで保持。編集・送信取消は実装済み（確認アラート後）。弱い: **テキストの行は失敗の状態を持たず、手動の再送/破棄が無い**（`.retry` は写真のみ）。待機中の行のメニューはコピーのみで、**取り消すことも捨てることもできない**。サーバーが拒否したテキストの扱い、長時間待機の表示、送信中の行の取消は見つからず。

### 判定

- **すでによい**: 永続アウトボックス＋`op_id` の冪等（両者と同じ考え）。id 順の直列化。再接続のバックオフと即時再接続。接続状態をタイトル下に出す（Telegram と同じ）。編集と送信取消。
- **採り入れる**:
  - **失敗の状態をテキストにも**。「恒久的な拒否（サーバーが拒否した）」と「一時的な失敗（通信）」を分け、前者だけを失敗にして理由を言う（Telegram）。失敗はタップで「再送/削除」（両者）。Signal のように**時刻の欄を赤い文言に置き換える**のは、Pochical の「時刻の幅を確保する」設計と合う。
  - **待機中の行を捨てられる**ようにする（取り消し）。送れない状態が続くと詰まる。
  - **到達性の回復・接続が開いた、を契機にバックオフを待たず再試行**（Signal）。Pochical は前面復帰・ネット回復の即再接続を持つので、その延長で送信側にも通す。
  - 長時間待機の見せ方（例: 一定時間後に「送れていません」の控えめな文言）。
- **変える**: 写真の失敗だけ後ろに回す扱いを、テキストも含む全体の規則に整理（後続を止めない/順序を守るの線引きを spec に書く）。
- **捨てる**: 編集の期間・回数の上限（Signal の 24 時間/10 回）、「自分だけ消す」の Undo（spec/chat.md に「自分だけ消す」は見当たらない）。**要確認**: 送信取消に Undo を付けるか（Telegram は付けず、Signal は確認シート）。今の確認アラートで十分。

## 領域3: 既読・未読・入力中

### Signal

- **既読**: 画面表示中、0.1 秒周期のタイマーで「画面内の最後の行の sortId」を見て、新しい値があれば**そこまでを既読にする**（直列、処理中は重複起動しない、単調）。レイアウトの更新中・他の画面を重ねている・通話表示中・最前面でないときは既読にしない。画面を離れる/非アクティブ化でも既読化。画面内の最後の判定には `indexPathsForVisibleItems` を使わない（`scrollViewDidScroll` の中ではまだ古いため）。レイアウト属性を可視の矩形で引く。他人への既読レシートはバッチ化（リンク端末へは処理後 3 秒待ってまとめ送り）、設定でオフ可。`ConversationViewController+Misc.swift`, `+LastVisibleSortId.swift`, `SignalServiceKit/Messages/OWSReceiptManager.swift`
- **未読**: 初回ロード時に最古の未読を記録し、その直前に区切りを**1つだけ**入れる。後続の未読はまとめない。↓ボタンに未読の件数（スレッドのデータ層の値）。
- **入力中**: 送る側は、文字入力から 3 秒の無入力で「停止」、入力が続く間は最初の 1 通のあと **10 秒ごとに「入力中」を再送**。送信時は即停止。受ける側は (送信者, 端末) ごとに 15 秒で自動消去、停止で即消去、複数人なら先に始めた人。表示は**リスト末尾の 1 行（セル）**として差分更新に乗る。設定でオフにすると送受信とも無効。`SignalServiceKit/Util/TypingIndicators.swift`, `Components/CVComponentTypingIndicator.swift`

### Telegram

- **既読**: 画面に見えている**受信メッセージの最大 index**を追い、「既読にしてよい状態」と合成して、**index が前回より進んだ時だけ**「そこまで既読」の 1 個の値を送る（個別でなく最大値）。既読にしてよい状態 = アプリ前面かつチャットが最前面（シート/メニュー/ブラウザが上にない）。メニュー表示中・背面では既読にしない。`TU/Sources/ChatHistoryListNode.swift`（`maxVisibleIncomingMessageIndex`）
- **見た通知**: メンションやリアクションが見えたことは、**遅延付きのバッファで重複を除いてまとめて送る**（メンション 0.2 秒、通常 1 秒、リアクションは同一 id を 4 秒間隔に抑制）。`TU/Sources/ChatMessageThrottledProcessingManager.swift`
- **未読**: 区切りの行を履歴の一部として入れ、読まれた瞬間に未読の強調を落とす（セルに未読範囲の更新を通知）。右下のボタンに未読数、別のボタンでメンション数/リアクション数。「返信元へ飛んだ」ときは**ジャンプ元のスタック**に積み、戻るボタンで 1 つずつ戻る。`TU/Sources/ChatHistoryNavigationButtons.swift`, `ChatHistoryNavigationStack.swift`
- **入力中**: 送る側は文字変更ごとに「入力中」、**4 秒後に自動で false**（続けて入力すれば延長）。送信・編集・予約の表示中は送らない。受ける側は 8 秒で失効、更新が来れば延長。表示はタイトルのサブタイトル枠に「入力中」とドット。**複数人で種類が違うときは汎用の「入力中」に畳む**。オフラインのときは出さない。`submodules/TelegramCore/Sources/State/PeerInputActivityManager.swift`, `submodules/ChatTitleActivityNode`

### Pochical の今

既読は group の `last_read_seq`（最大値だけ前進、サーバー側）。クライアントは**最新の行が画面に入った時だけ**100ms 待ってから読む（`ReadKey` の task、`ChatScreen.swift:392`）。scenePhase が active でないと読まない。他人に既読は見せない。未読数は User DO の `unread_counts` で、通知の対象と一致（ミュート中はメンションのみ）。チャット内は「ここから新着」と↓の数。入力中は 3 秒でスロットル送信、5 秒で失効、ブロックは非表示、3 点バウンスの吹き出し、VoiceOver「〇〇が入力中」。揮発（DB に保存せず、再接続でも再生しない）。複数人は人数分の行が並ぶ。

### 判定

- **すでによい**: 他人に既読を見せない（プライバシーの選択として明確）。未読数と通知の対象の一致。入力中の間隔（Signal の 3 秒停止/10 秒再送、Telegram の 4 秒に近い）。入力中を DB に保存しない。ブロックの非表示。
- **変える（要確認）**: **既読を「見えている最大の受信行」まで、スクロールの途中でも単調に進める**（両者）。Pochical は「最新に着いた時だけ」なので、途中まで読んだ人の未読数が減らない。ただし spec の "Lines count as read only once they are on the screen at the latest" は意図した選択（unread の ↓ の数え方と対）なので、変えるのはプロダクトの判断。
- **採り入れる**:
  - 既読の送信を**単調・直列・重複なし**にする規則（今も `max` のみだが、クライアントでも「前回より進んだ時だけ」を明文化）。
  - 既読にしてよい状態の条件に「長押しメニューや他のシートが上にある間は既読にしない」を足す（Telegram）。
  - 複数人の入力中は 1 行に畳む（例: 「〇〇さん、△△さんが入力中」）。
- **捨てる**: 既読レシートの送信、視聴済み、メンション/リアクションの見た通知（Pochical にそれらの機能が無い）。

## 領域4: 操作（長押しメニュー・リアクション・返信・選択・コピー）

### Signal

- **長押しメニュー**: `UIContextMenuInteraction` ではなく**自前**（`Signal/src/ViewControllers/ContextMenus/CustomContextMenus/*`）。長押し 0.2 秒、元のビューが縮むバウンス、中強度の触覚、背景はぼかし＋暗幕、**吹き出しを浮かせて上にリアクション帯、下にアクション一覧**。バネ（0.4 秒、damping 0.8）。吹き出しの左右寄せに合わせて配置（RTL 対応）。自前の理由は、`UIContextMenu` では吹き出しの上にリアクション帯を置けないこと（推測）。
- **アクション**: 内容に応じて 返信/コピー/転送/選択/編集/読み上げ（Speak Selection が有効なときだけ）/ピン/詳細/削除/画像の共有・保存。優先度で並べる。`MessageActions.swift`
- **リアクション帯**: 既定 6 種（ユーザーが差し替え可）、右端「+」でフルの絵文字ピッカー。自分が選んだものは丸で強調、再タップで取消。DB に即反映→非同期で送信。集計のピルをバブルの下に、タップで人別の詳細シート。
- **スワイプ返信**: 会話全体に**水平専用の `UIPanGestureRecognizer`**（縦が勝つときは無効にして縦スクロールを邪魔しない）。55pt で返信確定、超えたら移動量を 1/4 に減速（ゴムバンド）、**しきい値到達の瞬間に軽い触覚**、アイコンは 0→55pt でフェードイン。離すとバネで戻る。**進捗を行の id ごとに保持し、リロードでセルが作り直されても途中の位置を復元**する。左スワイプ 55pt は「メッセージ詳細」への interactive push。`ConversationViewController+GestureRecognizers.swift`, `Components/CVComponentMessage.swift`
- **引用とジャンプ**: 引用のタップ→元のメッセージを読み込んでスクロール→到達後に吹き出しを暗く点滅（0.4 秒で暗転、0.8 秒保持）。表示だけで状態は保存しない。
- **複数選択**: 長押しメニュー「選択」→各セルにチェック、下のツールバーは「削除」「転送」のみ。転送できないもの（閲覧 1 回限定・削除済み・投票）は選択項目ごとに除外。
- **コピー/転送/共有**: コピーは本文のメンションの範囲を保ったままペーストボードへ。転送は宛先を複数選び、順序を保って 1 件ずつジョブに積む（コメント付き可）。共有は画像だけ UIActivityViewController。

### Telegram

- **長押しメニュー**: 吹き出しが「抜き出される」ノードを持ち、`ContextGesture`（開始の遅延 0.12 秒→0.2 秒の進行）で、背景ぼかし＋暗転のオーバーレイへ吹き出しを移す。下にアクション一覧（サブメニューは積み重ねで遷移）、上にリアクション行。メニュー項目は**メッセージの状態を非同期に集めてから**組み立てる。**メニュー表示中は「既読にしてよい」を落とす**。`submodules/Display/Source/ContextGesture.swift`, `TU/Sources/ChatInterfaceStateContextMenus.swift`
- **リアクションピッカー**: 上部に頻出、末尾の展開ボタンで全絵文字へ。**ドラッグでハイライトし、離すと選択**、ハイライトが変わるたびに触覚。**ダブルタップでクイックリアクション**（ダブルタップ待ちが要る要素は 1 タップを少し遅らせる）。`submodules/ReactionSelectionNode`
- **スワイプ返信**: 専用の認識（縦の成分が横の半分を超えるか 2pt 超なら失敗、横が優勢と判定された時だけ開始）。バブルを `bounds.origin` で横に動かし、アバターも連動。しきい値は受信 45pt/送信 60pt、超えたらゴムバンド（係数 0.4）、最大 180pt。アイコンは円弧が進捗で伸びる。**到達の瞬間に重い触覚を 1 回だけ**。離すと返信モードに入り、バブルは 0.3 秒のバネで戻る。**開始時にキーボードの対話的な引き下げを取り消す**。`TU/Components/Chat/ChatSwipeToReplyRecognizer`
- **引用**: 引用ブロックは引用範囲（文字列と位置）を持ち、タップで該当メッセージへスクロール＋ハイライト。テキスト選択から「引用して返信」。長い引用は展開/折りたたみ。
- **複数選択**: 各セルの左端にチェックが出入りし、バブルが右へずれる。選択中は専用の入力パネル（削除/転送/共有）。選択状態は永続対象の状態の一部。
- **コピー/転送/共有**: コピーはエンティティ付きで。転送は宛先選択（複数）→オプション（コメント付き、引用名を隠す）。

### Pochical の今

**自前の長押しメニュー**（`MessageActions.swift`）。250ms で軽い触覚＋背景が暗く、メッセージは元の位置で少し持ち上がり、上にリアクションバー、下にメニュー（収まらなければ入れ替え/移動/縮小）。**指を離さず滑らせて選べる**（滑る間は selection の触覚）。キーボード表示のまま開ける。VoiceOver にはアクション「リアクションとメニュー」、`.isModal` と escape。リアクションは 👍❤️😂👀🙏🎉＋「+」でシステムの絵文字キーボード。ピル、自分のは強調、タップでトグル、長押しで名前の一覧。返信（引用タップで該当行へ、必要なら前ページを遡って取得し、リングを出す）。ピン最大 5 件。リンク長押しはリンク専用のメニュー。メニュー: 返信/コピー/保存(写真)/ピン留め/編集/決め直す/送信取消/通報。無いもの: スワイプ返信、複数選択、転送、共有シート、ダブルタップでのリアクション、バブル内のテキスト選択。

### 判定

- **すでによい**: 自前の長押しメニュー（吹き出しの上下にリアクションとメニューを置く点で両者と同じ構成）、滑って選べる操作、キーボードを閉じない、VoiceOver のアクション、リアクションの集計とトグル、引用からのジャンプとリング、ピン。ここは両者と同水準。
- **採り入れる**:
  - **スワイプ返信**。横専用の認識（縦が勝てば失敗）、到達の瞬間に触覚 1 回、ゴムバンド、**進捗を行の id ごとに持つ**（UICollectionView 化で行が作り直されるため。Signal の知見）、開始時にキーボードの対話的な引き下げを取り消す（Telegram）。しきい値は 55〜60pt 程度。実装は UIKit 側（collection view の pan）が素直。
  - **メニュー表示中は既読にしない／リストを動かさない**（領域3, 0 と共通）。
  - 引用に飛んだあとの「戻る」（ジャンプ元のスタック）は、長い履歴で効く。優先度は低い。
- **変える**: ダブルタップでリアクション／編集は、1 タップとの競合で挙動が重くなる（待ち時間が要る）ので**入れない**ほうが無難。Signal は編集に 0.2 秒の短い間隔を使って緩和している。
- **要確認（プロダクト）**: 複数選択・転送・共有シート。内輪のグループチャットで「他のチャットへ転送」が要るか。「コピー」で足りるなら捨てる。バブル内のテキスト選択は、長い文面の一部をコピーしたい場面で要望が出やすい（Signal は Speak Selection のみ別扱い）。
- **捨てる**: 管理者削除、編集履歴シート、リアクションのアニメ絵文字基盤。

## 領域5: テキスト（リンク・プレビュー・メンション・折りたたみ・大絵文字・レイアウト）

### Signal

- **リンク**: 表示側は `NSDataDetector` 系で URL・電話・日時などを検出し、`CVTextLabel` のリンク項目にする。メッセージリクエスト中の相手には linkify しない。折りたたみで切った末尾の「…」を巻き込んだ検出は捨てる。タップは種類ごとに分岐（招待リンクなどはアプリ内、他は OS で開く）。`Components/CVComponentBodyText.swift`
- **プレビュー**: **送信側が取得して添付する**方式。入力中に URL が出ると状態（なし/取得中/済/失敗）を管理し、前回の取得は取消、×で却下したら以後取らない。応答の上限 2MB、画像は長辺 2400px 超なら縮小、タイトル最大 2 行・説明最大 3 行。巨大な本文（2KB 超）にはプレビューを付けない。`SignalUI/LinkPreview/*`
- **メンション**: 本文に専用のプレースホルダ文字を置き、別の配列（範囲）にアカウントを紐づける。表示時に「@表示名」へ展開して背景を付ける。名前の解決は会話単位のキャッシュ。入力は @ でピッカー、メンションは入力欄内で**原子的**に扱い、隣の入力属性を引き継がない。`SignalServiceKit/Messages/BodyRanges/*`, `SignalUI/Views/BodyRanges/*`
- **長文**: 表示は最大 512 グリフ・15 行で切り、「…」＋「続きを読む」。タップで、描画サイズの推定が 8KB 以内ならセルをその場で展開（その行だけリロード）、超えるなら別の画面を push。展開状態は viewState に保持。送信上限 64KB、受信 128KB、2KB 超は添付（.txt）にする。`Signal/util/DisplayableText.swift`
- **大絵文字**: 空白以外が絵文字のみで 5 個以下なら拡大。倍率は個数が少ないほど大（1 個 3.5 倍 → 5 個 2.25 倍）、body の Dynamic Type 上限付きサイズが基準。
- **レイアウトのキャッシュ**: 計測を**背景キューで事前に**行い、結果（`CVCellMeasurement`）を行に持たせ、セルは測定済みのサイズで固定。ラベル計測用の LRU（500 件、キーは文字列属性・フォント・最大幅・行数）。本文は `UILabel`/`UITextView` でなく**自前のラベル**（独自の `NSTextStorage` + `NSLayoutManager` + `NSTextContainer` で直接描画、リンクの当たり判定も自前）。`SignalUI/ConversationView/CVText.swift`, `CVTextLabel.swift`

### Telegram

- **リンク**: 受信はサーバーが付けたエンティティ（URL・メンション・ハッシュタグなど）を属性付き文字列にする。テキストノードが属性ごとの矩形を持ち、タップ座標から該当のアクションを引く。送信側の入力中の検出は `NSDataDetector`（URL）で、**検出した URL の集合が変わった時だけ**プレビューを要求。`submodules/TextFormat`, `submodules/Display/Source/TextNode.swift`
- **プレビュー**: サイト名・タイトル・説明・画像。取得中は**リンクの文字が光る（シマー）**ことで保留を表す。入力欄の上のプレビューは×で破棄。
- **メンション**: 入力はカーソル直前の「@クエリ」を検出して候補パネル（メンバー検索）、選んだらエンティティ付きのトークンとして挿入。自分宛てのメンションは未読メンション数の集計に入る。
- **長文**: チャット内は**行数で切らず全文**。行数制限が効くのはコンテキストメニュー内のプレビューだけ（6/9/12 行、「続きを読む」のトークンを自前で描く）。長い引用ブロックだけ展開/折りたたみ。
- **大絵文字**: 本文が絵文字のみでエンティティもメディアも無く、設定が有効なら、バブル無しの別のセルクラス（ステッカーと同じ）で描く。1 文字でアニメ絵文字があれば動かす。
- **レイアウトのキャッシュ**: `TextNode` は「レイアウト計算（CoreText、背景キュー可）」と「描画（非同期のレイヤ描画）」を分け、**同じ幅・同じ属性なら再計算しない**。選択・アクセシビリティ・リンクの当たり判定もこの結果を使い回す。

### Pochical の今

リンクは独自の規則（`textParts`、`Kit/ChatText.swift`、`spec/vectors/chat-text.json`）で、スキーム付き http(s) のみ、`NSDataDetector` は使わない。プレビューは**サーバーが取得**（クライアントはページを取りに行かない、プライバシー）、入力中に最初のリンクが 400ms 安定したら取得、×で外せる、間に合わなければ送信後にサーバーが付与。サーバーは SSRF 対策、3 リダイレクト/5 秒/512KB/画像 2MB、URL 単位 1 日キャッシュ。招待リンクは専用カード。メンションは `<@id>` で保存し表示時に現在の名前へ解決、@/＠ で候補。長文は 10 行で「…」＋続きを読む（幅に応じて実測、`ViewThatFits` と独自 Layout）、展開は画面を開いている間保持。大絵文字は 1〜3 個で 48pt・バブル無し（`@ScaledMetric`）。弱い: **レイアウトのキャッシュなし**。`pieces`/`words` は body の中で毎回 `textParts` から AttributedString を作り、折りたたみの判定のために隠し Text も余分に描く。行の高さの事前計算もない（SwiftUI 任せ）。

### 判定

- **すでによい（むしろ先）**: サーバー取得のプレビュー（Signal の送信側取得より、受信者のアドレスを守る点で強い）、招待リンクカード。長文の折りたたみ（Signal と同じ考え。Telegram は折りたたまない）。メンションの現在名への解決。大絵文字（Signal は 5 個まで/倍率が個数で変わる、Pochical は 1〜3 個で一定。好みの範囲）。リンクを `NSDataDetector` に頼らず規則で決める点は、全プラットフォームで同じ結果にするため理にかなう。
- **採り入れる**:
  - **行の描画材料（AttributedString、リンクの範囲、折りたたみの要否）を行ごとにキャッシュ**する。キーは（本文、幅、Dynamic Type）。Signal の計測 LRU、Telegram の「同じ幅・属性なら再計算しない」。UICollectionView 化の自己サイズの往復（2 回測る）を減らす効果もある。
  - 折りたたみの要否を、隠し Text で毎回測るのをやめ、キャッシュした計測から出す。
  - 展開が重い場合の扱い: Signal は推定 8KB を超えるなら別画面。Pochical は `chatMessage` の上限が `textLimits` で決まっているので、その上限まででセルの展開が重くならないか**要確認**。
- **変える**: プレビュー取得中の表現。Telegram のシマーのように、保留を軽く見せる（今は送信後に付与されるまで何も出ない）。優先度は低い。
- **捨てる**: 電話・日時の自動検出（両者にあるが、Pochical は仕様でリンクのみ）、メッセージリクエスト中の linkify 抑止、巨大本文の添付化。

## 領域6: 入力欄（下書き・添付・ペースト・キーボード）

### Signal

- **下書き**: スレッド単位で DB に保存（本文＋メンションの範囲、引用返信、編集対象）。**保存の契機は画面を離れる時とアプリが非アクティブになる時**で、変更があるときだけ非同期で書く。入力のたびの自動保存は見つからず。復元は入力ツールバーの生成時。`ConversationViewController+ConversationInputToolbarDelegate.swift`
- **入力ツールバー**: 高さは全体 56pt、テキストは 35〜98pt（iPad は 142pt）。**`inputAccessoryView` ではなく `keyboardLayoutGuide` に下端を張る**（iOS 26 の初回高さの不具合を避ける回避策あり）。添付は入力欄の `inputView` を差し替える専用キーボード（最近の写真、カメラ、ギャラリー、ファイル、連絡先）。写真の権限が限定のときの案内。入力欄の上に引用返信・編集ラベル・リンクプレビュー・メンションピッカーを積む。`ConversationInputToolbar.swift`, `ConversationViewController+BottomBar.swift`
- **ペースト**: 入力の `UITextView` の paste を上書きし、ペーストボードが添付になり得て本文が無ければ**添付の承認画面**へ。`canPerformAction` で貼り付けメニューの出し分けも。`ConversationInputTextView.swift`, `Signal/Attachments/PasteboardAttachment.swift`
- **添付の承認画面**: 複数枚、並べ替え、キャプション、画像編集、動画トリム、送信時の画質（標準/高）。画質は長辺 512〜4096px の 7 段、既定はリモート設定の 2 段目。共有拡張ではメモリ制約で低品質固定。`SignalServiceKit/Util/ImageQuality.swift`

### Telegram

- **下書き**: `ChatInterfaceState`（本文・返信先・転送予定・編集中・選択・**スクロール位置**・時刻）を保存。**画面が消える時とアプリが非アクティブの時**に保存（送信/破棄でも更新）。スクロール位置も一緒に持ち、次に開くとき位置を復元する。クラウド同期あり（空白のみで返信先なしなら下書き無し扱い）。一覧に「下書き:」を出す。`submodules/ChatInterfaceState`
- **添付**: 下から出るシート（写真グリッド、カメラ、ファイル、位置、連絡先、投票）。写真は選択順の番号付き、キャプション、送信前の編集、送信オプション（静音/予約/画質）。送信時に圧縮。
- **ペースト**: 入力欄が「画像を貼れる」ことを宣言し、GIF・MP4・HEICS・PNG/JPEG などを判別して、**確認画面で送信前にプレビュー**。マークダウン形式のテキストを貼るとリッチな入力に変換。`TU/Components/Chat/ChatTextInputPanelNode`, `submodules/MediaPasteboardUI`
- **キーボード**: 高さと「対話的に変化中」のフラグをウィンドウ層から受け、リストの下端と入力パネルが追従。絵文字パネルとシステムキーボードの高さを共有（切替時に高さが跳ねない）。対話的な引き下げは**ウィンドウ全体のパン認識**が指の位置を入力欄の境界に反映、離した位置/下向き速度で閉じるか戻るかを決める（戻りは 0.25 秒のバネ）。

### Pochical の今

`ChatDraft` を `@State`（別の Observable で、1 文字ごとに全行を再描画しない）で `ChatScreen` が持つ。**チャットごとの永続化は見つからず**（画面を閉じると消えるはず）。添付: `PhotosPicker` 最大 4 枚、トレイに 64pt 角と×、共有する日、日にち投票。ツールは入力開始で › に折りたたむ。**画像のペーストは見つからず**。`ComposerField` は `UITextView` のラッパー（文字数制限）。キーボード: `.scrollDismissesKeyboard(.interactively)`、メッセージ領域のタップで閉じる、入力欄はキーボードと一体で上昇、長押しメニュー中もキーボード維持。`inputAccessoryView` は使わない。送信ボタンは空/読み込み中で無効、残りが少ないと N/上限を出す。メンション候補は欄の上（最大 180pt）。送信時に askOnce で通知権限を求める。

### 判定

- **すでによい**: `inputAccessoryView` を使わず、キーボードと一体で動く入力欄（Signal と同じ選択）。対話的な引き下げ。入力欄の上に積む引用/編集/プレビュー。メンション候補。写真の縮小と EXIF 除去。
- **採り入れる**:
  - **下書きをチャットごとに保存**（本文・返信先・編集中）。契機は**画面を離れる時とアプリが非アクティブになる時**だけ（Signal/Telegram）。変更があるときだけ書く。チャット一覧の行に「下書き:」を出すのも自然。
  - **画像のペースト**。入力欄が画像を受けられると宣言し（`UITextView` のペースト処理の差し替え）、貼ったら**送信前のプレビュー**を挟む。
  - 下書きの復元は入力欄の生成時（Signal）。UICollectionView 化とは独立。
- **変える**: 添付の承認画面は、複数枚の並べ替え・キャプション・編集をまとめて持つ重い画面。Pochical は「トレイ＋×」で足りている。**要確認**: 送信前の確認が要る場面（ペースト）にだけ薄い確認を付ける。
- **捨てる**: 添付キーボード、動画トリム/画像編集、画質の 7 段、送信オプション（静音/予約）、クラウドでの下書き同期、リッチ入力へのマークダウン変換。

## 領域7: 通知

### Signal

- **NSE**（Notification Service Extension）で受信・復号して文面を作る。**開いている会話の通知は抑制**（他の会話は出す）。本文の出し方は 3 段（名前+内容 / 名前のみ / 無し）で、**返信・既読・👍 のアクションは「名前+内容」かつ画面ロックが無効のときだけ**付ける。`SignalNSE/*`, `SignalServiceKit/Notifications/NotificationPresenterImpl.swift`
- **スレッド**: `threadIdentifier` に会話の id を入れて iOS 標準のグルーピング。同じメッセージの再通知は同じ identifier で置換。
- **既読の端末があるとき**は 20 秒遅らせて出し、先に既読になれば取り消す。**既読にしたら該当の通知を取り下げる**。未読リマインダは会話ごとに初回の遅延後に再通知。
- **タップ**: 会話を開き、最初の未読へスクロール（アプリが前面でなければアニメーションなし）。特定のメッセージを指す通知はそのメッセージへ。`Signal/Notifications/NotificationActionHandler.swift`
- **通知から返信**: `UNTextInputNotificationAction`。元メッセージを引用つきの下書きにして、その場で送信ジョブに積む。空文字は無視。
- **メンション**は抑制の規則を貫通して通知。

### Telegram

- NSE が復号・整形し、`threadIdentifier`（会話単位）、`categoryIdentifier`（返信できるか等の種別）、バッジ、音、添付（画像）を設定。**送信者のアバター付きの `INSendMessageIntent`（Communication Notifications）**を作り、通知に相手の顔写真/グループ名を出す。`Telegram/NotificationService/Sources/NotificationService.swift`
- カテゴリはアプリ起動時に登録（返信可の個人/グループ、チャンネルは返信なし、リアクション、ストーリー）。返信は `UNTextInputNotificationAction` 1 種。プレビュー非表示時の代替文言も登録。
- **通知から返信**: アプリを起動せずバックグラウンドで送信を積み、**同時にそのメッセージまで既読に**する。送信が完了する（未送信の一覧から消える）まで完了ハンドラを保留し、短いバックグラウンド延長を要求。
- **タップ**: 通知内の URL があればそれ、無ければ該当チャットへ（チャンネルとリアクションは該当メッセージまで）。**アプリが未起動でも、コンテキストの準備ができるまで待ってから開く**。
- **前面**: 今開いているアカウントの通知は OS では出さず、アプリ内の自前バナーで出す。
- **既読で取り下げ**: `ClearNotificationsManager` が、通知 id に含まれるメッセージ id と各チャットの既読位置を比べ、配信済み/保留中の通知を削除。`TU/Sources/ClearNotificationsManager.swift`
- バッジ数はサーバー算出値をペイロードに載せる。

### Pochical の今

ペイロードに groupId/threadId、タップで `Notifications.opening` から該当チャットへ（`App/Notifications.swift`, `apps/server/src/apns.ts`）。前面で開いているチャットの通知は出さない（`willPresent`）。`thread-id` は "groupId/threadId"、`badge` はサーバー計算の未読数、`loc-key`/`loc-args` で本文。チャットごとのオン/オフ、「メンションはいつも通知」、権限カード。タップ後は「ここから新着」で開く。無いもの: **通知からの返信、通知のカテゴリ/アクション、Notification Service Extension**（`mutable-content` なし）、送信者の顔写真付き通知、**既読になったときの配信済み通知の取り下げ**、`apns-collapse-id`。

### 判定

- **すでによい**: スレッド化（`thread-id`）、バッジのサーバー計算、開いているチャットの抑制、メンションの貫通、タップで該当チャット→最初の未読、`loc-key` によるローカライズ。
- **採り入れる**:
  - **既読になったら配信済みの通知を取り下げる**（両者）。他の端末や、チャットを開いて既読になった時に、そのチャットの通知を `removeDeliveredNotifications` で消す。サーバー側でサイレントプッシュを使うか、アプリが既読にしたとき自分の端末で消す。複数端末なら前者。
  - **通知から返信**（`UNTextInputNotificationAction`）。通知のカテゴリを登録。Telegram は返信と同時に既読にし、**送信が済むまで完了を保留**する（短いバックグラウンド延長）。Pochical は送信がアウトボックス経由なので、**アウトボックスに積んだ時点で完了**でよいか、socket に出るまで待つかを**要確認**。
  - **送信者の顔写真付き通知**（Communication Notifications）は NSE が要る。Pochical は名前と顔（`memberFaces`）がグループごとに違うので、グループでの名前/アイコンを使える利点がある（Pochical の独自性）。NSE を足す工数が要るので P1 の中では後ろ。
- **変える**: 通知のタップで開く位置。今は常に最初の未読。**特定のメッセージを指す通知**（メンションなど）は、そのメッセージへ飛ぶ（Signal/Telegram）ほうが自然。**要確認**。
- **捨てる**: 未読リマインダ、アクション（👍/既読）、プレビューの 3 段の設定、アプリ内の自前バナー。

## 領域8: チャット内検索・日付ジャンプ

### Signal

- 検索: `UISearchController` を会話画面に載せる。2 文字以上で開始、同じ文字列の再検索は省略、**入力のたびに前回のタスクを取り消して新しいタスク**（古い結果は破棄）。DB は SQLite **FTS5**（スニペット付き）、グループでは送信者名でも検索、最大 500 件。結果は前へ/次へのバーで巡回、選ぶと該当メッセージを画面の中央寄りにスクロールし、**ヒットした語を本文内でハイライト**（検索語を描画に渡し、リロードで反映）。`Signal/ConversationView/ConversationSearch.swift`, `SignalUI/Search/FullTextSearcher.swift`
- 日付ジャンプ: 見つからず。

### Telegram

- 検索: ナビバーに差し込む検索バー、上下ボタン、件数。**クエリごとにサーバーへ検索**（1 回 100 件、0.2 秒の遅延）。結果は昇順の配列で、**現在位置は前回の結果の近くを保つ**（結果が更新されても跳ばない）。残りが半分になったら次のページを足す。該当メッセージの語をハイライト。結果の一覧ビュー。送信者・リアクション・タグ（写真/動画等）のフィルタ。`TU/Components/Chat/ChatSearchNavigationContentNode`, `TU/Sources/ChatControllerUpdateSearch.swift`
- **日付ジャンプ**: `CalendarMessageScreen`。月単位のカレンダーを縦に並べ、日ごとにメディアのプレビュー。日をタップ→その日の最初のメッセージへ窓を作り直して移動（読み込み中の状態を出し、完了後にスクロール＋ハイライト）。日ごとのデータは「日ごとの最初のメッセージを疎に取る」専用の問い合わせ。空の日にも遷移できる。`submodules/CalendarMessageScreen`, `TU/Sources/ChatControllerOpenCalendarSearch.swift`

### Pochical の今

チャット内検索と日付ジャンプは**どちらも見つからず**。近いもの: 引用/ピン/共有された日からのジャンプ（`jump(to:)`、"A chat opened from a shared day"）、スクロール中に浮かぶ日付（`floatingDayMs`）、↓で最新へ。

### 判定

- **採り入れる（P3）**:
  - **日付ジャンプ**は Pochical の領域（休みを決めるアプリ）に合う。カレンダーを出し、その日に付いたメッセージのある日だけを目印にして、その日の最初のメッセージへ飛ぶ。窓を作り直して飛ぶ処理は、引用/ピンのジャンプ（`jump(to:)`）と同じ経路が使える。
  - **チャット内検索**。端末のデータで検索する（端末に全部ある範囲）なら SQLite の FTS5 が軽い。サーバー側の検索は不要。Signal の「入力のたびに前の検索を取り消す」「2 文字以上」「ヒット語のハイライト」「前へ/次へ」を借りる。端末に無い古い行へは、検索結果の行へ飛ぶ経路（引用ジャンプ）で取りに行く。
- **要確認**: どちらもプロダクトの判断（使われるか）。ログに「検索したい」の声があるかを見てから。

## 領域9: 性能（メインスレッド・再利用・差分・背景レイアウト）

### Signal

- 読み込みは**専用の直列キュー**で、DB の読み取りから行の組み立て・計測まで一括（1 トランザクション）。メインスレッドは結果の**着地**だけ。着地は、スクロールのアニメーション・前回の着地・キーボードのアニメーション中は待つ（領域0）。`Loading/CVLoader.swift`, `CVLoadCoordinator.swift`
- **差分**: 前回の描画状態と新しい描画状態を比べて、「変化なし / 全リロード / 項目ごと（挿入・削除・移動・更新）」のどれかにする。更新も「同等 / 状態が変わった / **隣の行によって見た目が変わった**」を区別する。永続の状態と一時の状態を分け、プロフィール変更や時間経過での再計算の範囲を絞る。`Loading/CVUpdate.swift`, `CVRenderItem.swift`
- **セル**: 測定済みのサイズを即返して自動サイズ計算を省く。`prepareForReuse` で中身を初期化。UIKit のスタックビューではなく**手動のレイアウト**で測定結果を直接適用。再利用識別子は今はほぼ共通（コメントに課題）。`CVCell.swift`
- 初回表示を速くするため、初回のロードが済むまで高コストの処理を飛ばし、prefetch を後から有効にする。画面外のメディアはアンロード、メモリ警告でキャッシュ全消去。

### Telegram

- **AsyncDisplayKit** のノード（レイヤ背景、非同期描画）。小さな部品はレイヤ背景で軽く。各ノードの `asyncLayout()` が「状態を捕まえた計算クロージャ」を返し、**第 1 段（背景キュー可）でサイズと描画命令を決め、第 2 段（メイン）で適用**する。`TU/Components/Chat/ChatMessageItemImpl`
- **差分**: 履歴のエントリを stableId ベースで前後比較（`MergeLists`）。隣のメッセージとの連結（同じ送信者、日付の区切り、アルバム）は**エントリを作る段階**で決める。`TU/Sources/ChatHistoryEntriesForView.swift`
- 重い処理は `ThrottledProcessingManager` で束ねる（既読・メンション・リアクション・翻訳など）。メディアは可視外でデコーダを切り離す。`CpuProfiler` モジュールがある。
- 同期ロードのヒント（領域1）。

### Pochical の今

`ScrollView` + 非 Lazy の `VStack`。開くときに最新 50 行（最大 200 行）を一度にレイアウトし、spec も「一度に全行をレイアウトする」と明記している。`ChatScroll` と `ChatDraft` は別の `@Observable` にして、スクロールや 1 文字ごとに全行を作り直さない。`onScrollGeometryChange` を用途別に 3 系統。写真の縮小/デコードは `Task.detached`。DB は GRDB/SQLiteData の `ValueObservation`。弱い/不明: `textParts` の毎 body での構築、ぼかし NSCache の無制限、Instruments の計測の記録なし、ヒッチ/メモリのテストなし（`PochicalTests` は 1 ファイル）。

### 判定

- **すでによい**: 状態を別の Observable に分ける設計（再描画の範囲を絞る）。重い処理を `Task.detached` に出す。DB 観測。
- **採り入れる**:
  - **行の描画材料の事前計算とキャッシュ**（領域5）。背景で作ってメインで適用する 2 段（Signal/Telegram どちらも）。
  - **更新の種類を分ける**: 「変化なし / 内容が変わった / 隣によって見た目が変わった」。Pochical では、同じ送り手の続き（時刻や顔を省く）や日付の区切りが隣で変わると見た目が変わる。UICollectionView の diffable データソースで `reconfigureItems` を使うときの判断材料になる。
  - **着地を待つ**（領域0）。
  - 計測の習慣: Animation Hitches を実機で見る。Signal/Telegram の知見は「テストが通っても実機で崩れる」。
- **変える**: 非 Lazy VStack の「全行を一度に」は、UICollectionView 化で解消（領域0）。
- **捨てる**: AsyncDisplayKit のような自作の描画基盤。

## 領域10: アクセシビリティ・Dynamic Type・触覚・視差軽減

### Signal

- **Dynamic Type**: `UIFontMetrics` で**最大ポイント数を決めて**スケール（スタイルごとの上限表）。固定サイズに落とすと動的対応が失われる、というコメントがある。文字サイズの変更を通知で受けて、引用プレビューなどを作り直す。`SignalUI/UIKitExtensions/UIFont+OWS.swift`
- **VoiceOver**: 吹き出しに組み立て済みのラベル（送信者名・本文・メディア・時刻を、順序を意識して連結）。メッセージごとのカスタムアクション（長押しメニューと同じアクションを再利用）。背景のコンテナは隠す。スクロールの到達後に `UIAccessibility.post` でフォーカスを移す。
- **触覚**: スワイプ返信のしきい値（軽）、長押しメニューの出現（中）、入力ツールバーのボタン（軽/中）。選択や削除などには付けていない。
- **Reduce Motion**: 会話画面では参照が見つからず（未確認）。

### Telegram

- **VoiceOver**: セルごとにラベルを状態込みで組み立てる（「〇〇からの写真」「あなたのメッセージ」「送信中」「失敗」「既読」「選択中」）。カスタムアクションに「返信」「メッセージメニューを開く」（スワイプ返信・長押しの代替）。テキストのリンク領域をアクセシビリティ要素にするオーバーレイ。`TU/Components/Chat/ChatMessageItemView/Sources/ChatMessageItemView.swift`
- **フォントサイズ**: OS の Dynamic Type に連動する（最も近い自前の段階に丸める）か、自前の 7 段のスライダー。`adjustsFontForContentSizeCategory` ではなく独自のレイアウトに値を流す方式。
- **触覚**: スワイプ返信のしきい値で重い触覚を 1 回（`prepareImpact` で事前準備）、リアクションのハイライト移動、長押し開始。
- **Reduce Motion**: 画面遷移や一部の演出の簡略化に使うが、網羅度は未確認。省電力の設定で動きと半透明を落とせる。

### Pochical の今

VoiceOver: 行は `.combine`/`.contain`、メニューのアクション「リアクションとメニュー」、写真は isImage と「写真」ラベル、送信失敗は label+hint、「〇〇が入力中」、未読件数、ピン/引用のボタン、リアクションは絵文字+名前+選択状態、↓のラベル、メニューは `.isModal`+escape。Dynamic Type: 本文は body に追従、大絵文字は `@ScaledMetric`。`spec/haptics.md` あり: 長押し開始（軽）、メニュー上の滑り（selection）、保存/コピー完了（success）。Reduce Motion: 送信時の下からのせり上がり、入力中のドット、写真の呼吸を止める。弱い/不明: **写真の説明が一律「写真」**。写真の枠・アバター・メタ情報の固定 pt が Dynamic Type に追従するか、アクセシビリティサイズでの配置切替は**未確認**。**長押しメニュー・ビューア・浮かぶ日付の Reduce Motion 対応は見つからず**。Bold Text / Increase Contrast は未対応。送信・受信・リアクション確定の触覚は見つからず。

### 判定

- **すでによい**: VoiceOver のラベルとアクションの作り込みは両者と同水準かそれ以上（メニューを `.isModal` にする、リアクションの状態を言う）。長押しメニューが VoiceOver のカスタムアクションを持つ点も同じ。触覚の方針（`spec/haptics.md`）。
- **採り入れる**:
  - **スクロール後・ジャンプ後のフォーカス移動**（`UIAccessibility.post(.screenChanged, …)`）を UICollectionView 化の機に入れる。開くときの最初のフォーカスを「ここから新着」の行に（Signal）。
  - **Reduce Motion を長押しメニュー・ビューアの遷移・浮かぶ日付に広げる**（「動きを減らす」は、動かさないのでなく、フェードなどに置き換える）。Signal にも先行例が無いので、Pochical の側で決める。
  - **写真の説明（alt）**は、送る側が付けられる設計にしないと付けようがない。優先度は低い。
  - Dynamic Type: 固定 pt の部品（写真の枠、顔、時刻）の追従を点検。`UIFontMetrics` の上限指定（Signal）の考えを借りる。
- **変える**: 触覚を足す場面（送信の確定、リアクションの確定）。Signal も最小限なので、**足しすぎない**。`spec/haptics.md` に沿って 1 つずつ。
- **捨てる**: 自前の文字サイズのスライダー（Telegram）。OS の設定に任せる。

# Replicate標準クライアントへの移行検証

検証日: 2026-09-24

## 結論

標準クライアントと、認証済みユーザーから同期領域を決めるサーバー側アダプターの組み合わせで、個人カレンダーの作成・更新・削除は動作した。ただし現時点ではアプリを移行しない。
`view` と書き込みフックの設定だけでは、同期データの認可を満たせない。
サーバー側の同期・復元経路の補完、または上流の修正が必要。
読み取り・復元の分離は補完できたが、書き込み検証は既存実装を再利用している。さらにクライアントの再送・初期表示にも対応が必要なため、「認可だけを追加すれば全面的に任せられる」とは言えない。

アプリ・デプロイ済みAPI・依存パッケージは変更していない。

## 実行した検証

対象はインストール済み `@trestleinc/replicate@2.0.0-preview.0`。
`tests/replicate-standard-client.test.ts` は標準の `collection.create` が生成した
関数と実際のReplicate Convex componentをconvex-test上で実行する。
検証用の関数はテスト内だけに存在し、デプロイされない。

- material: 本人のデータだけ返し、別ユーザーには空配列、未認証にはエラー。
- delta: 閲覧対象外の変更にも `exists: false` と一緒にCRDTバイト列が含まれる。
  実際にデコードすると非公開メモを取得できた。
- recovery: `document` と `vector` を指定した復元経路は `view` を実行せず、
  未認証でも既知の文書IDの内容を取得できた。

後者2件は不具合の再現を成功条件にした調査テストであり、安全性の合格テストではない。
上流修正後は期待値を拒否・非公開データ不在へ変更する。

既存の `tests/replication.test.ts` も併せて実行し、合計9件・33アサーションが通過。
現在アプリが使っている専用同期では、別ユーザーの読み書き拒否、再起動後の
未送信データ復元、再送、アカウント引き継ぎの既存テストが通った。

## 上流とクライアントのコード確認

上流mainの確認時点コミット:
`f21c275126a51ab425c0223e1bec8a918d76a462`

https://github.com/trestleinc/replicate/blob/f21c275126a51ab425c0223e1bec8a918d76a462/packages/replicate/src/server/index.ts

この版でも、`enrichChangesWithExistence` はバイト列を除去せず、
`createDeltaQuery` の復元分岐は `view` より先に返る。
最新mainはソース確認のみで、上記の実行テストは導入済み版に対するもの。

導入済みクライアントには以下の確認事項もある。

- コレクション名を `api.delta` の関数パスから決め、内部contextもその名前で共有する。
- 購読引数は `{ seq, limit }`。公開設定に任意の `groupId` を渡す項目がない。
  複数グループを個別購読するなら追加の接続処理が必要。
  所属グループ全体をユーザー別に同期し端末で絞る案は別途評価できる。
- 起動時にローカル文書の `recover()` をawaitしてから `markReady()` する。
  起動時の即時表示・オフライン起動は実機検証が必要。
- 再接続の処理にブラウザーのonline/offlineイベントがある。
  React Nativeでの通信復帰と未送信変更の再送は別途検証が必要。

## アカウント切り替えの方針

ユーザーの希望に従い、複数アカウントのローカルデータを保持しない。
別アカウントへの切り替えは、旧購読・保留処理を停止してローカル保存とメモリーを
破棄し、新しいアカウントのデータを取得する。匿名から新規正式アカウントへの
引き継ぎでは保存内容を維持する。既存正式アカウントへのログインは切り替え扱い。
未送信変更を含むリセットのタイミング、旧購読の遅延応答の破棄は実装時に確認する。

## 移行前に必要な実証

1. material・delta・recovery・write・presenceすべてで同じ認可を適用。
   書き込みは申告JSONだけでなくCRDT内の所有者情報との整合性も確認する。
2. 権限喪失と削除、同期カーソルの進行を保ちながら非公開データを返さない。
3. 標準クライアントとop-sqliteによる実機の保存、オフライン再起動、通信復帰後の再送。
4. 切り替え時のローカル破棄と匿名データ引き継ぎ。

## 続行した実行検証

`tests/replicate-scoped-client.test.ts` は実際の標準クライアントを、convex-testに接続する
インプロセス通信アダプターで実行した。サーバー側はテスト専用の
`tests/fixtures/replicate-scoped-probe.ts`。ライブラリ本体の変更なしで以下を確認した。

- クライアントからの新規作成・更新・削除と、サーバー上の結果。
- 本人の同期ストリームと別ユーザーの空ストリーム。
- 別ユーザーの文書復元・上書き拒否、未認証の復元拒否。

サーバー側アダプターはユーザー別のコンポーネント領域を選び、標準のdelta形式を返す。
書き込みは既存の `api.shifts.replicate` に接続する。CRDTの所有者検証・競合統合・削除の
復活防止は既存実装を残している。標準クライアントの削除マーカー `_meta._deleted` と
既存アプリの `meta.deleted` の変換も必要だった。

これは本番用アダプターではない。materialのページ取得、presence、グループ同期、
カーソルの大量データ処理・圧縮は対象外。presenceは通信アダプターで無処理にしている。
認可だけで書き込み実装を全削除できるという検証ではない。

`tests/replicate-client-runtime.test.ts` は標準クライアントと公開の
`persistence.native.sqlite.create` を実行し、SQL実行部分だけをBun SQLiteに接続した。
SQLiteはテスト内のメモリDBをクライアントの破棄・再作成にまたがって保持している。
op-sqliteのネイティブ実装、プロセス強制終了時の耐久性を検証したものではない。

- 未応答のmutationを持つクライアントを破棄・再作成すると、SQLiteから新規文書を復元できた。
- 復元後にサーバーqueryが正常応答しても、元の未送信insertは再度mutationされなかった。
  アカウント切り替え・ローカルリセットを一切行わなくても再現する。
- 復元時のqueryを保留すると、ローカル文書が存在してもpreloadが完了せず、表示用collectionに
  文書が現れなかった。queryを解放すると文書が現れた。

実行結果: 関連4ファイルで12テスト、48アサーションが通過。再送欠如と表示待ちは
現状挙動の再現を成功条件としており、期待するアプリ動作の合格ではない。

## 判断

認可を組み込むこと自体は可能。端末側のYjs操作とSQLite保存を標準化できる見込みはある。
ただし導入済み版では、同一アカウントでの再起動後の再送とネットワークを待たない復元が
不足する。公開APIに明確なrecover/retry呼び出しもなく、ブラウザーのイベントを擬装して
内部復帰処理を起動するような方法は移行案に採用しない。

したがって「認可アダプターを足すだけ」の移行は現段階では推奨しない。次の実装候補は
上流への修正、またはバージョンを固定した小さなクライアント修正とその回帰テスト。
アプリ独自の永続送信キューを追加する方法は、保守を減らす目的と逆行する。
最新mainに対して上記クライアント実行テストを行ったわけではない。

アカウント切り替え時の未送信破棄は、ユーザーが提案した警告・確認で扱える。
これは同一アカウントの通常再起動後に再送されない問題とは別。
標準クライアントとop-sqliteによる実機のエンドツーエンド検証は未実施。
